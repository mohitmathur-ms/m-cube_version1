# HTML Report Generator

Produce a single self-contained `.html` file that gives a **quick overview** of a target file plus a **representative sample** of its contents. The output must open in any browser with no external assets, and must use the **dark-themed component system** defined below.

## Workflow

1. **Identify the target file.** If the user named a path, use it. If not, ask before proceeding.
2. **Read the file** with the appropriate tool. Stat the size first; for files >10 MB, only read the first/last few KB.
3. **Detect the type** from extension + a first-line sniff (shebang, JSON/CSV cues, magic bytes).
4. **Build the report** using the section structure below and the matching per-type recipe.
5. **Write the output** to `./reports/<input-stem>-report.html`. Create `reports/` if missing. If a file with that name exists, append a timestamp.
6. **Confirm the path** and offer to open it in the browser.

## Paired-description pattern (THE CORE RULE)

Every section that introduces a concept, statistic, or example **must** present it with **two paired descriptions, then the example**, in this exact order:

1. A **`.simple` "Plain English" block** — describe it the way you'd describe it to a non-technical colleague. One short paragraph. No jargon.
2. A **`.callout-tech` "Technically:" block** — the same information from a technical angle: the actual parsing rule, data type, schema detail, regex, or arithmetic. Start with **`<strong>Technically:</strong>`**.
3. The **example itself** — a `.filebox` above the sample `<table>` or `<pre>`, OR a worked-arithmetic example with a `.callout-ok` "Check." block after it that verifies the numbers.

A section without all three of these pieces is incomplete. If there's genuinely nothing technical to add (e.g. the File Information section is just metadata), the technical block can be omitted, but every section that shows an example or explains a rule needs the full triplet.

## Section structure (every report has these in order)

1. **Cover header** (`<header class="cover">`) — gradient banner with the report title (filename) and a subtitle line describing what the report is. Include a `.meta` line with generation timestamp + file size.
2. **Intro `.callout`** — 2–4 sentences naming what this report covers (file type, what's in each section). End with a bulleted list of section titles.
3. **Section 1 — File information** — small metadata `<table>`: path, type, size, last-modified, encoding, line count. (Metadata-only — no paired descriptions needed here.)
4. **Section 2 — What this file is** — the paired-description triplet: `.simple` plain-English description of the file's purpose/shape, then `.callout-tech` with the technical detail (encoding, delimiter, schema, language version, etc.), then a small example block (could be the column list, the JSON root schema, or the first non-empty line).
5. **Section 3 — Overview** — type-specific stats as a `<table>`. Prepend a one-line `.simple` block explaining what the stats mean in plain English; if any stat needs technical context (e.g. how "comment lines" are counted), add a `.callout-tech` after the table.
6. **Section 4 — Sample content** — the paired-description triplet again: `.simple` saying what the sample is and which slice it represents, `.callout-tech` describing how it was extracted (line range, parsing assumptions, type inference), then `.filebox` + the sample `<table>` or `<pre>`. If the sample contains numeric aggregation (sum/mean/count), follow with a `.callout-ok` **"Check."** block that walks the arithmetic.
7. **Section 5 — Notes** — any warnings, redactions, parse errors, or observations. Use the appropriate `.callout-*` variant.
8. **Footer** — "Generated by html-report-generator" + ISO timestamp.

Use `<h2 id="sec-N">` for each section so anchors work. Skip the table-of-contents nav for short reports (4–5 sections); add it only if the report grows beyond ~8 sections.

## Per-type recipes

### CSV / TSV
- **What this file is** (§2): `.simple` saying "a CSV with N rows about X" in plain language; `.callout-tech` with the delimiter, encoding, quote character, and whether it has a header row.
- **Overview table** (§3): row count, column count, column names with inferred types, null-count per column. Prepend a `.simple` saying which columns matter most; add a `.callout-tech` explaining how types were inferred (regex/heuristic per column).
- **Sample** (§4): `.simple` saying "the first 5 rows look like this," `.callout-tech` noting the slice (rows 1–5, line range, any rows skipped), then `.filebox` + the `<table>`. Use `.num` on numeric columns, `.mono` on timestamp/ID columns. Wrap in `<div style="overflow-x:auto">` if >5 columns.
- **Optional aggregate row**: if numeric columns exist, append a `<tr class="agg-row">` with sum/mean, and follow the table with a `.callout-ok` **"Check."** block walking the arithmetic.

### JSON
- **What this file is** (§2): `.simple` describing the shape ("an array of N objects, each looking like a user record"); `.callout-tech` with the actual root type, encoding, and whether it's pretty-printed or minified.
- **Overview table** (§3): top-level type, key count or array length, max nesting depth, total size. Prepend a `.simple` describing the structure; add a `.callout-tech` if the schema has unusual features (mixed types in arrays, deep nesting, etc).
- **Sample** (§4): `.simple` saying what the sample shows; `.callout-tech` with the slice rule ("first 50 lines of the pretty-printed form"); then `.filebox` with path + the pretty-printed JSON in `<pre><code>`. If the root is an array of objects, follow with a small schema table (key, inferred type, sample value) using `<span class="badge badge-info">` for each type.

### Log files (.log, .txt with timestamps)
- **What this file is** (§2): `.simple` ("a log file from service X covering Y"); `.callout-tech` with the log format (timestamp pattern, level field, structured vs unstructured).
- **Overview** (§3): total lines, time range, counts of ERROR / WARN / INFO each shown with the matching badge. Prepend a `.simple`; add a `.callout-tech` for the parsing approach (regex used, log-format guess).
- **Sample** (§4): `.simple` ("the bookends of the log"); `.callout-tech` noting that the middle is elided; then `.filebox` + a `<pre>` with first 10 lines, a `...` separator, and last 10 lines.
- **Top errors**: if errors are present, a small table of top 3 error messages with counts, preceded by a `.simple`.

### Source code (Python / JS / TS / Go / Rust / Java / C / C++)
- **What this file is** (§2): `.simple` ("a Python module that defines a class for X and three helper functions"); `.callout-tech` with the language version (from shebang / pragmas), imports/dependencies summary, framework hints.
- **Overview** (§3): total lines, code vs comment vs blank, function count, class count, language. Prepend a `.simple`; add a `.callout-tech` explaining how comment vs blank vs code lines were counted.
- **Function/class list**: `<table>` with columns "Kind" (badge: `badge-purple` for class, `badge-info` for function), "Name" (`.mono`), "Line" (`.num`).
- **Sample** (§4): `.simple` ("the first 30 lines, where imports and the main class live"); `.callout-tech` noting the slice; then `.filebox` + `<pre><code>` with the source.
- **TODO/FIXME callout**: if any are found, render them in a `.callout-warn` with line numbers.

### Markdown / plain text
- **What this file is** (§2): `.simple` ("a Markdown doc with 12 headings about X"); `.callout-tech` with flavor (CommonMark/GFM hints), front-matter presence, special blocks detected (code fences, tables, etc).
- **Overview** (§3): word count, line count, estimated reading time (200 wpm), heading count by level. Prepend a `.simple`.
- **Outline**: nested `<ol>` of h1–h3 headings as anchor links.
- **Sample** (§4): `.simple` ("the first 200 words"); `.callout-tech` noting any front-matter stripped; then `.filebox` + first 200 words of body.

### Unknown / binary
- **What this file is** (§2): `.simple` ("a binary file we couldn't identify — N bytes long"); `.callout-tech` with magic-byte signature, MIME guess from `file` command, and what was tried.
- **Sample** (§4): `.simple` ("a small hex preview so you can eyeball the format"); `.callout-tech` noting the byte range shown; then `.filebox` + first 256 bytes as a hex dump in `<pre>`.
- **Note**: include a `.callout-warn` saying the type wasn't recognized and only a generic preview is shown.

## Component usage guide

Match each piece of report content to the right component:

- **`.callout`** (blue, info) — neutral observations about the file
- **`.callout-ok`** (green) — sanity checks that passed, "no issues found"
- **`.callout-warn`** (amber) — truncation, redactions, parse errors, missing data
- **`.callout-tech`** (purple) — technical caveats: encoding fallback, type guesses, version notes
- **`.simple`** (gray, "Plain English:" prefix) — the one-sentence description of what the file is
- **`.filebox`** (dark monospace bar) — always sits flush above a `<pre>` or sample `<table>`, showing the source path
- **`.badge-info`** (blue) — file types, neutral tags
- **`.badge-ok`** (green) — passed checks, healthy counts
- **`.badge-warn`** (amber) — warnings, ERROR / WARN log levels
- **`.badge-purple`** (purple) — inferred properties, derived types
- **`.badge-err`** (red) — errors, failed parses
- **`.agg-row`** (highlighted) — sum / mean / total row at the bottom of a numeric sample table
- **`td.num`** — right-aligned monospace for numeric columns
- **`td.mono`** — left-aligned monospace for IDs, timestamps, paths

## Safety rules

- **Redact likely secrets** in samples before embedding. Match patterns including: `AKIA[0-9A-Z]{16}`, `sk-[A-Za-z0-9]{20,}`, `xox[bp]-`, `Bearer\s+[A-Za-z0-9]+`, and any line where a key name contains `password`, `secret`, `token`, `api_key`, `apikey`, or `private_key`. Replace the value with `[REDACTED]` and add a `.callout-warn` in Notes mentioning the redaction.
- **Never embed raw bytes** from binary files beyond the 256-byte hex preview.
- **HTML-escape all content** from the source file before embedding — no raw `<`, `>`, `&`, or quotes leaking through.

## Edge cases

- **File >10 MB**: stat-only read; for samples, read just the first and last few KB. Add a `.callout-warn` about the truncation.
- **File doesn't exist**: tell the user, list nearby paths in the same directory, ask for clarification.
- **Encoding errors**: try UTF-8 first, fall back to latin-1; if neither parses cleanly, treat as binary and use the hex dump path. Mention the fallback in a `.callout-tech`.
- **Empty file**: produce a minimal report stating the file is empty — still write the HTML with cover header and a single `.callout-warn`.
- **Multiple files in one request**: generate one HTML per file, then offer to build an index page that links to all of them using the same dark theme.
