LIMIT Order Report — SL/TP Callback Exit vs Direct LIMIT (with Order Emulator)

Two NautilusTrader order-handling scenarios contrasted end-to-end, with a Knowledge Graph of the kernel data-flow.

Generated 2026-05-28 · NautilusTrader 1.224.0 · Sourced from the 28 concept PDFs under .claude/agents/ntm3_docs/ via the ntm3 subagent.

This report walks through two distinct ways a strategy can exit (or enter) a position in NautilusTrader, both phrased the way the user described them. Scenario 1 keeps SL/TP as Python variables and fires a MARKET order from inside a callback handler when the price crosses. Scenario 2 sends a LIMIT order directly, and depending on the value of emulation_trigger, the order either rests on the venue or is held locally by the OrderEmulator until a trigger condition fires.

Every concept is presented twice — a Plain English block first, then a Technical (Nautilus) block with PDF citations. A unified inline-SVG Knowledge Graph in Section 5 ties both scenarios to the same kernel components so they can be compared at a glance.

1  ·  At-a-glance comparison

Two side-by-side ways of getting out of (or into) a position. The left column is the m-cube production exit pattern — the strategy itself watches the price and slams a market order when the line is crossed. The right column is the broker-resident way — you tell the venue your exact price and either let it sit, or hold it locally and watch a separate trigger stream until conditions are right.
Technically: A MARKET order cannot be emulated by the local OrderEmulator — the emulation matrix marks it as "Can emulate: n/a. Released type: n/a" (Orders.txt lines 669–717). A LIMIT with emulation_trigger=TriggerType.NO_TRIGGER bypasses the emulator entirely and is sent natively to the venue; with any other TriggerType value, the OrderEmulator holds it in EMULATED state until the trigger condition fires, then releases it (transformed into a MARKET order) into the ExecutionEngine via the RELEASED state (Orders.txt lines 582–593, 644–668, 678–717).

2  ·  Glossary of kernel components

The same handful of kernel components appear in both scenarios — only the path through them differs. The glossary below pairs each component with a plain-English description and a technical one citing the concept PDFs.

Strategy

The Python class you write. It receives price updates, decides what to do, and submits orders. The user's "strategy callback handlers" are the methods named on_bar, on_quote_tick, on_trade_tick, etc., which the framework calls automatically.
Technically: Subclass of nautilus_trader.trading.strategy.Strategy. Inherits the Actor handler surface — full list (Rust.txt lines 276–375): on_start, on_stop, on_quote, on_trade, on_bar, on_book_deltas, on_book, on_instrument, on_mark_price, on_index_price, on_funding_rate, on_option_greeks. Adds the trading handlers on_order_* and on_position_* (Events.txt lines 42–88). Handler dispatch is priority-ordered: specific (on_order_filled) → category (on_order_event) → catch-all (on_event) — first matching level runs (Events.txt 20–34).

OrderFactory

A helper attached to every Strategy as self.order_factory. It builds correctly-shaped order objects so you don't have to fill in trader-IDs, init-IDs, timestamps, etc., yourself.
Technically: From Orders.txt 220–222: "OrderFactory takes care of lower level details — such as ensuring the correct trader ID and strategy ID are assigned, generation of a necessary initialization ID and timestamp." Surface methods: .market(...), .limit(...), .stop_market(...), .stop_limit(...), .market_to_limit(...), .market_if_touched(...), .limit_if_touched(...), .trailing_stop_market(...), .trailing_stop_limit(...), .bracket(...). Every factory accepts emulation_trigger (default TriggerType.NO_TRIGGER).

MessageBus

An internal post-office. Strategies don't call the risk engine directly — they publish a message ("please submit this order") and the bus routes it to whatever component should handle it next.
Technically: Three messaging patterns (MessageBus.txt 8–13): point-to-point command/request/response, pub-sub on topics, and event broadcast. Strategy holds it as self.msgbus. The trading command path (SubmitOrder, ModifyOrder, CancelOrder, …) is dispatched through it from Strategy to whichever engine is the registered handler (see Execution flow below).

Cache

An in-memory store of "current truth" — every quote/trade/bar that arrived, every open order, every live position. Strategies read from it instead of querying the venue.
Technically: Examples in Cache.txt 25–53 and 212–219. DataEngine writes to the Cache as each tick/bar arrives, then Strategy handler methods read it (self.cache.orders_open(...), self.cache.position(position_id), self.cache.is_order_emulated(client_order_id)). The emulated-order helpers are critical for Scenario 2-B since the Python order reference is invalidated when the emulator releases the order.

RiskEngine

A pre-trade safety gate. Before any order reaches the venue, it checks for things like "is the price precision right?", "do you have enough cash?", "are you over the submit-rate limit?", "is trading currently halted?". Failures raise an OrderDenied event.
Technically: Validations enumerated in Execution.txt 154–174:
  • Price/trigger-price precision matches the instrument.
  • Positive prices (unless instrument class allows negatives).
  • Quantity precision and base-quantity min/max bounds.
  • GTD orders not already expired.
  • reduce_only orders don't increase the referenced position.
  • Engine-level max_notional_per_order and instrument max_notional.
  • Cash-account balance impact for non-margin accounts.
  • Submit and modify rate limits (max_order_submit_rate).
  • TradingState (ACTIVE / HALTED / REDUCING) — lines 170–173.
Failure at submit emits OrderDenied; failure at modify emits OrderModifyRejected.

OrderEmulator

A local "fake venue" for order types the real venue doesn't support — or that you want to evaluate against a specific price feed (last trade, mark price, mid-price, …). It holds the order, watches the trigger stream you chose, and releases the order to the real venue when the condition is met.
Technically: Activated when an order's emulation_trigger is anything other than TriggerType.NO_TRIGGER (Orders.txt 571, 582–593). Emulatable order types (Orders.txt 678–717): STOP_MARKET, STOP_LIMIT, MARKET_IF_TOUCHED, LIMIT_IF_TOUCHED, TRAILING_STOP_MARKET, TRAILING_STOP_LIMIT, and LIMIT (when its emulation_trigger is not NO_TRIGGER). On release the order is transformed and the emulation trigger is set to NONE; an OrderReleased event is emitted (Orders.txt 644–668). Crucially, an emulated LIMIT releases as a MARKET order (Orders.txt 586, 700) — not as a native LIMIT.

ExecutionEngine & ExecutionClient

The plumbing that actually talks to the venue (or, in a backtest, to the SimulatedExchange). The engine is generic; the client is the venue-specific adapter that translates the framework's command into the venue's protocol.
Technically: Routing rule from Execution.txt 38–52: "submit_order(...) routes to OrderEmulator for emulated orders, to an ExecAlgorithm when exec_algorithm_id is set, and to the RiskEngine otherwise. From there: → ExecAlgorithm → RiskEngine → ExecutionEngine → ExecutionClient." The ExecutionEngine also detects overfills (Order.is_duplicate_fill() and allow_overfills config flag — Execution.txt 409–443), applies fills to the Cache, and republishes OrderFilled/PositionOpened/PositionChanged/PositionClosed via the MessageBus.

Venue / SimulatedExchange + MatchingEngine + FillModel

In live trading, the real exchange. In a backtest, an internal simulator that maintains an order book, matches incoming orders against it, and uses a fill model to decide whether (and at what price) each order gets filled.
Technically: The backtest per-timestamp loop has three phases (Backtesting.txt 294–352):
  1. Exchange processes data — SimulatedExchange updates its book and iterates the MatchingEngine to fill existing resting orders.
  2. Strategy receives data — DataEngine dispatches to on_bar / on_quote_tick / on_trade_tick.
  3. Settle venues — engine drains queued venue commands and re-iterates the matching engine, so orders submitted inside on_bar settle in the same timestamp.
FillModel options include BestPriceFillModel, OneTickSlippageFillModel, TwoTierFillModel, ThreeTierFillModel, ProbabilisticFillModel, SizeAwareFillModel, LimitOrderPartialFillModel, MarketHoursFillModel, VolumeSensitiveFillModel, CompetitionAwareFillModel (Backtesting.txt 987–1047).

3  ·  Scenario 1 — Manual SL/TP via callback (MARKET exit)

SCENARIO 1 Strategy holds SL and TP as plain Python variables on self. Each new bar/tick calls back into on_bar; the strategy compares the live price against those variables and, when either threshold is crossed, builds a MarketOrder via self.order_factory.market(...) and calls self.submit_order(order) to flatten the position.

3.1 Plain English definition

The trader writes a strategy that watches every new bar/tick itself. On each price update, it compares the live price against a stop-loss and a take-profit it is keeping in its own head (plain Python variables). When either is crossed, it immediately sends a "sell at market" order. The venue (or the simulator in a backtest) fills that market order at the next available price. There is no special "exit order" sitting at the broker — the strategy does the watching, and the broker only ever sees the final market order that flattens the position.

3.2 Technical (Nautilus) definition

Technically: A vanilla MarketOrder with emulation_trigger=TriggerType.NO_TRIGGER (implicit; MARKET cannot be emulated — Orders.txt 692). Default TimeInForce is GTC (Orders.txt 230); honest practice is to set TimeInForce.IOC on an exit/flatten. Built by self.order_factory.market(instrument_id, OrderSide.BUY|SELL, Quantity, time_in_force, reduce_only, tags) (Orders.txt 220–242). Submission flows Strategy → MessageBus → RiskEngine → ExecutionEngine → ExecutionClient → Venue/SimulatedExchange (Execution.txt 38–52). The fill comes back as OrderFilled on the MessageBus and is dispatched to on_order_filled (Events.txt 20–34).

3.3 Step-by-step flow

  1. DataEngine dispatches on_bar(bar) — Phase 2 of the per-timestamp loop.
  2. Strategy compares bar.high ≥ self.tp or bar.low ≤ self.sl.
  3. If triggered, build the exit order: order = self.order_factory.market(instrument_id, OrderSide.SELL, qty, time_in_force=TimeInForce.IOC, reduce_only=True).
  4. self.submit_order(order) publishes a SubmitOrder command on the MessageBus.
  5. The bus routes it to RiskEngine (no emulation, no ExecAlgorithm).
  6. RiskEngine validates → forwards to ExecutionEngine.
  7. ExecutionEngine picks the registered ExecutionClient for the venue and forwards.
  8. SimulatedExchange + MatchingEngine fill in Phase 3 of the same timestamp (no latency model) or in Phase 1 of the next timestamp (with LatencyModel ≥ bar interval).
  9. Fill events propagate back as OrderFilled → on_order_filled and PositionClosed → on_position_closed.

3.4 Minimal code

strategies/sl_tp_callback_exit.py  ·  illustrative
from nautilus_trader.model.enums import OrderSide, TimeInForce
from nautilus_trader.model.objects import Quantity
from nautilus_trader.trading.strategy import Strategy


class CallbackSLTP(Strategy):
    def on_start(self):
        self.subscribe_bars(self.config.bar_type)
        self.sl = None
        self.tp = None

    def on_bar(self, bar):
        # ENTRY (omitted) sets self.sl and self.tp at fill time

        pos = self.cache.position_for_order(self.client_order_id)
        if pos is None or pos.is_closed:
            return

        # Manual SL/TP comparison in the callback
        triggered = (
            (pos.side.value == "LONG"  and (bar.low  <= self.sl or bar.high >= self.tp)) or
            (pos.side.value == "SHORT" and (bar.high >= self.sl or bar.low  <= self.tp))
        )
        if not triggered:
            return

        exit_side = OrderSide.SELL if pos.side.value == "LONG" else OrderSide.BUY
        order = self.order_factory.market(
            instrument_id=pos.instrument_id,
            order_side=exit_side,
            quantity=Quantity.from_int(int(pos.quantity)),
            time_in_force=TimeInForce.IOC,   # default would be GTC
            reduce_only=True,
            tags=["EXIT_SLTP"],
        )
        self.submit_order(order)             # MessageBus → RiskEngine → ExecEngine → Venue

3.5 Why MARKET cannot be emulated

Technically: The emulation matrix in Orders.txt 669–717 marks MARKET as "Can emulate: n/a. Released type: n/a". The OrderEmulator only exists to mimic conditional/passive types (STOP_MARKET, STOP_LIMIT, MARKET_IF_TOUCHED, LIMIT_IF_TOUCHED, TRAILING_STOP_*, and LIMIT with a non-NO_TRIGGER trigger) on venues that don't natively support them. A MARKET order has nothing to wait for — it takes liquidity immediately, so there is no "trigger" to evaluate locally.

3.6 Backtest fill mechanics

Per Backtesting.txt 294–352, the engine runs a three-phase loop each timestamp: Exchange processes data → Strategy receives data → Settle venues. A MARKET submitted from on_bar(N) settles inside the same cycle and matches against the top of book — for L1 / quote / trade / bar data, MARKET BUY fills at the best ask and MARKET SELL at the best bid (Backtesting.txt 386–440). With L2/L3 book it can walk levels (partial taker). Adverse slippage is governed by FillModel.prob_slippage (Backtesting.txt 535–565, 1051–1107); at prob_slippage=0.5 a MARKET BUY has a 50/50 chance of paying ask + 1 tick.
Crucial bar-data timing detail (Backtesting.txt line 933): "Bar N's OHLC sequence processes before on_bar(N) fires. Without a LatencyModel, an order submitted from on_bar settles immediately and matches against the current book, whose top reflects bar N's close." So the on_bar-submitted MARKET fills at the close of bar N (no latency model) or the close of bar N+1 (with LatencyModel(base_latency_nanos ≥ bar_interval)).

3.7 Gotchas

on_stop fills are silent. Backtesting.txt 359–366 — OrderFilled / PositionClosed from close_all_positions() in on_stop never re-enter on_order_filled / on_position_closed.
Between-bar wick risk → sl_wait_bars. The strategy inspects the closed bar, so the exit price is ≈ bar N close, not the SL price itself. A native STOP_MARKET resting at the SL would have filled at the SL during the Phase-1 H/L sweep. Single-bar wicks that pierce SL and recover will exit a callback-based strategy at the close — locking in slippage with no upside. m-cube's core/managed_strategy.py sl_wait_bars confirmation pattern trades first-bar latency for fewer whipsaws.
position_id under NETTING. Execution.txt 133–152 — under NETTING, position_id is deterministic ({instrument_id}-{strategy_id}). Passing a custom position_id to submit_order yields OrderDenied. Strategy.close_position() is safe (it forwards position.id). For arbitrary IDs configure oms_type=HEDGING.
Submitting MARKET while a prior exit MARKET is in-flight. Guard with self.cache.orders_open(...) or a local self._exit_pending flag, otherwise duplicate exits land.
TIF default = GTC (Orders.txt 230). TimeInForce.IOC is the more honest choice for a flatten command.

4  ·  Scenario 2 — Direct LIMIT (NO_TRIGGER vs emulated)

SCENARIO 2 Strategy submits a LIMIT order directly. The crucial parameter is emulation_trigger. With TriggerType.NO_TRIGGER, the order is sent straight to the venue and rests on the order book. With any other TriggerType value (e.g. BID_ASK, LAST_PRICE, MARK_PRICE) the local OrderEmulator holds the order in EMULATED state, subscribes to the relevant data feed, and releases the order to the ExecutionEngine only when the trigger condition fires.

4.1 Plain English definition

The trader knows the exact price they want, so they place a resting price-tagged order at that level. Two flavours: (a) the order is sent straight to the venue and sits on the venue's order book until the market touches it; or (b) Nautilus keeps the order locally — it watches a chosen "trigger price" stream (best bid/ask, last trade, mark price, etc.) and only releases the order to the venue when the trigger condition is met. The choice between (a) and (b) is one parameter, emulation_trigger: NO_TRIGGER means "send to venue now"; anything else means "hold locally and watch this price stream."

4.2 Technical (Nautilus) definition

Technically: A LimitOrder built via self.order_factory.limit(instrument_id, OrderSide.SELL|BUY, quantity, price, time_in_force, expire_time, post_only, reduce_only, display_qty, emulation_trigger, tags) (Orders.txt 244–252). Quote: "NO_TRIGGER: disables local emulation completely and order is fully submitted to the venue. DEFAULT: which is the same as BID_ASK. BID_ASK: emulated using quotes to trigger. LAST_PRICE: emulated using trades to trigger. … For LIMIT orders being emulated, the limit price will be compared against the specified trigger type to determine when to release the order as a MARKET order." (Orders.txt 582–586). The release-type table (Orders.txt 700) confirms: an emulated LIMIT releases as a MARKET order, not as a native LIMIT.

4.3 Branch A — emulation_trigger = NO_TRIGGER (native LIMIT)

  1. Strategy builds: order = self.order_factory.limit(..., emulation_trigger=TriggerType.NO_TRIGGER).
  2. self.submit_order(order) → MessageBus.
  3. Bus routes to RiskEngine (default; no emulation).
  4. RiskEngine validates → ExecutionEngine.
  5. ExecutionEngine → ExecutionClient → Venue.
  6. Venue rests the LIMIT on its book; OrderAccepted comes back; later OrderFilled or OrderCanceled (e.g. post_only crossed).

4.4 Branch B — emulation_trigger != NO_TRIGGER (held by local emulator)

  1. Strategy builds: order = self.order_factory.limit(..., emulation_trigger=TriggerType.LAST_PRICE) (or BID_ASK, MARK_PRICE, …).
  2. self.submit_order(order) → MessageBus.
  3. RiskEngine pre-trade check runs (Orders.txt 650 step 2).
  4. OrderEmulator receives the order → state becomes EMULATED; emits OrderEmulated.
  5. Emulator subscribes to the needed market data (Quote / Trade / Mark / Index, depending on trigger) and feeds its internal MatchingCore (Orders.txt 666).
  6. When the trigger condition fires:
    • Order is transformed to a MARKET order (per release-type table, Orders.txt 700).
    • emulation_trigger is set to NONE.
    • State transitions to RELEASED; OrderReleased event is emitted.
  7. RiskEngine re-validates the released order (Orders.txt 650 step 5) — this can still fail (e.g. balance now insufficient) and emit OrderDenied.
  8. ExecutionEngine → ExecutionClient → Venue.
  9. Venue fills the MARKET — OrderFilled propagates back to on_order_filled.

4.7 Backtest fill mechanics for LIMIT

Per Backtesting.txt 386–440: L2/L3 book → "Order's limit price when matched (maker)"; L1 / quote / trade / bar → "Limit price" (single-level book) — fills as soon as the synthesized top-of-book crosses; with bar data the OHLC sweep processes during Phase 1, so a resting LIMIT can fill before on_bar fires. The prob_fill_on_limit knob (default 1.0) governs the probabilistic queue position: at 0.0 the LIMIT only fills when the price level is crossed (back of queue); at 1.0 it fills the moment the level is touched (Backtesting.txt 1088–1093). With liquidity_consumption=True on L1 data, only fills against displayed/observed liquidity per crossed quote — partial fills as fresh quotes arrive (Backtesting.txt 567–622).

4.8 Gotchas

The emulator needs the right data feed. Orders.txt 666: "The OrderEmulator will subscribe to any needed market data … to update the matching core." If emulation_trigger=LAST_PRICE but you only feed bars in the backtest (no TradeTick data), the emulator never releases. Same trap for MARK_PRICE / INDEX_PRICE on venues that don't publish those streams.
Don't hold a Python reference to an emulated order. Orders.txt 739: "The order object transforms when the emulated order is released. Use the Cache instead" — self.cache.orders_emulated(...), self.cache.is_order_emulated(...), order.is_emulated.
Risk checks run twice. Orders.txt 650 step 5 and 746 item 3: pre-trade and on-release. An emulated order can still be denied at release time. Listen for OrderDenied even post-emulation.
LIMIT release type is MARKET. When emulating a LIMIT (Orders.txt 586, 700), release is a MARKET — no price guarantee on the actual fill. Use STOP_LIMIT or LIMIT_IF_TOUCHED if you want post-trigger price protection.
emulation_trigger=NO_TRIGGER ≠ "no emulator anywhere". It bypasses the local emulator for this order only. If the venue doesn't natively support your STOP type, you must set a real trigger.
GTD without expire_time → OrderDenied (Orders.txt 176–177).
post_only crossed marketable LIMIT is auto-cancelled by most venues — handle OrderCanceled defensively.

6  ·  Performance: slippage analysis

6.1 What slippage is

Slippage is the gap between the price you intended to trade at and the price you actually got. Every tick of slippage is a real cost — it comes straight out of your PnL on every single trade. Lower slippage = more profit kept. There are three sources you can lose money to: (a) crossing the bid-ask spread whenever you take liquidity, (b) the venue's tick-level adverse drift (modeled in Nautilus by prob_slippage), and (c) intra-bar latency — the gap between when your signal fires and when the order actually fills.

6.2 How Nautilus models slippage

Technically: FillModel.prob_slippage (default 0.0; documented in Backtesting.txt 535–565 and 1051–1107) is the per-fill probability of one tick of adverse slippage on every taker fill at L1 / bar / quote / trade granularity. At prob_slippage=0.5, a MARKET BUY has a 50/50 chance of paying ask + 1 tick. Bar-data fills add a latency component (Backtesting.txt line 933): "Without a LatencyModel, an order submitted from on_bar settles immediately and matches against the current book, whose top reflects bar N's close." That intra-bar drift between threshold-cross and bar-close is real, unmodeled slippage that hits only the callback path. Fill-price tables (Backtesting.txt 386–440): L1/quote/trade/bar → MARKET BUY at best ask, MARKET SELL at best bid; LIMIT → its own limit price. For passive LIMITs, prob_fill_on_limit (default 1.0; Backtesting.txt 1088–1093) governs queue position — at 0.0 the LIMIT only fills when the price level is crossed.

6.4 Quantitative ranking — least to most slippage

Ranking (LEAST adverse slippage → MOST adverse slippage):
  1. Scenario 2A with post_only=True — native maker LIMIT. Zero slippage; you get the exact limit price or you don't fill at all. Some venues even pay you a maker rebate.
  2. Scenario 2A with post_only=False — native marketable LIMIT. Fills at limit price or better on the taker side; no prob_slippage exposure because LIMIT matches at its own price.
  3. Scenario 2B (emulated LIMIT → released MARKET) — ~1 tick of prob_slippage plus half-spread on release. No intra-bar latency penalty — the emulator releases on the exact triggering tick, not on the next bar.
  4. Scenario 1 (callback MARKET) — worst on slippage: full intra-bar latency (entire range from threshold to bar close) plus prob_slippage plus the half-spread. On volatile bars this can drift many ticks past the threshold.

6.5 Recommendation — the answer to "which scenario has less slippage?"

If your goal is the minimum slippage path, use Scenario 2A — a native LIMIT order with emulation_trigger=TriggerType.NO_TRIGGER and post_only=True. This is the only scenario where you are guaranteed to fill at your chosen price (or not at all). The next-best option is Scenario 2B (emulated LIMIT that releases as MARKET) — you give up zero-slippage but you gain a guaranteed fill once the trigger fires, with at most one tick of adverse drift. Scenario 1 (callback MARKET) is the worst on slippage by a wide margin — it pays the half-spread, the prob_slippage tick, and the entire intra-bar drift from threshold to bar close.

6.6 The tradeoff — why m-cube still uses Scenario 1

The lowest-slippage path is also the highest non-fill-risk path. A native LIMIT (Scenario 2A) protects price but may never fill — leaving you exposed if the market moves away. m-cube's exit engine in [core/managed_strategy.py](core/managed_strategy.py) uses Scenario 1 precisely because the exit must happen when SL is hit, regardless of slippage cost. The slippage-vs-fill-certainty tradeoff is fundamental:
  • Scenario 2A — choose when non-fill is tolerable (e.g. limit-entry strategies where missing the entry is acceptable).
  • Scenario 2B — choose when you need a guaranteed exit/entry with minimal slippage and have the trigger data feed available in your backtest.
  • Scenario 1 — choose only when callback-driven exit logic is genuinely required (multi-bar confirmation via sl_wait_bars, trailing stops indexed off custom indicator state, RBO logic, etc.).

6.7 Worked numerical example

Setup: long EURUSD position. Adverse bar with O=1.0850, H=1.0852, L=1.0805, C=1.0810 — bar drops hard and closes near its low. Stop-loss set at SL = 1.0825. Tick size 0.0001. Backtest knobs: prob_slippage=0.5, half-spread = 0.5 tick. The bar's low (1.0805) pierces the SL (1.0825), so all three scenarios trigger an exit on this bar.
Scenario Exit fill price Adverse slippage from SL
Scenario 1 — callback MARKET fires in on_bar(N), fills at bar close 1.0810 (bar close) ± 1 tick from prob_slippage ± 0.5 tick spread ~15 ticks adverse + spread + prob_slippage = ≈ 16 ticks total
Scenario 2A — native resting LIMIT (or STOP_MARKET) at 1.0825, fills in Phase-1 OHLC sweep when L pierces it 1.0825 (limit price, taker side of the sweep) 0 ticks

Check.
  • Scenario 1: intended exit at SL = 1.0825, actual exit at C = 1.0810. Distance = 1.0825 − 1.0810 = 0.0015 = 15 ticks adverse. Plus 0.5 tick from the half-spread + 0.5 tick from the 50% prob_slippage expected value = ~16 ticks total.
  • Scenario 2A: limit/stop price = 1.0825, fill price = 1.0825. Distance = 0. 0 ticks slippage (this is what LIMIT guarantees by definition).
  • Scenario 2B: trigger fires at last-trade = 1.0825, MARKET released, fills at ~1.0824 (one tick adverse — the next available bid). ≈ 1 tick adverse.
  • Bottom line: Scenario 1 costs ~16× more in slippage than Scenario 2B and is uncountably worse than Scenario 2A. These numbers are conservative — on news bars or thinly-traded sessions Scenario 1 can drift 5–10× worse, while Scenario 2A still costs zero.

8  ·  Where this lives in m-cube

Scenario 1 is exactly how the m-cube exit engine works in production today. Scenario 2 is supported infrastructure for user strategies, but the m-cube exit path does not use the LIMIT-with-emulation pattern.
Scenario 1 is implemented by core/managed_strategy.py — the ManagedExitStrategy wraps every signal function from core/signals.py:SIGNAL_REGISTRY with the manual SL/TP/trailing/squareoff/RBO state machine. The sl_wait_bars confirmation pattern documented in [CLAUDE.md](CLAUDE.md) and the leg → slot → portfolio square-off precedence are all evaluated inside on_bar; the exit itself is a MARKET order submitted via self.submit_order(self.order_factory.market(...)).
Scenario 2 is available to user strategies via self.order_factory.limit(...) (with or without an emulation_trigger) but is not used in the m-cube exit path. The L1 entry strategies under strategies/ generally use MARKET entries; LIMIT/emulated patterns are open for new user-supplied strategies under custom_strategies/<user_id>/ registered via core/custom_strategy_loader.py.
