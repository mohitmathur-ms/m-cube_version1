How the live portfolio monitor works

Engine: core/portfolio_monitor.py (PortfolioMonitorStrategy) · the in-process buses in core/managed_strategy.py · wired in core/backtest_runner/unified/__init__.py. This is the mechanism behind every "Live" verdict in the Portfolio / Level-2 tables.

The setup. All of a portfolio's legs plus a single position-less PortfolioMonitorStrategy run in ONE engine, ONE pass, in the same process. The monitor never trades — it only observes. Because it lives in the same engine as the legs, it can read the combined P&L live on every bar and enforce portfolio-level SL / Target / Move-SL during the run — no post-run clip, no second pass.
① Monitor
Sees the combined P&L live each bar (sum over the engine's own Portfolio)
② Breach
Publishes an action-aware event to an in-process bus, keyed by portfolio_id
③ Each leg
Reads the bus → closes / re-arms its own position live, the same bar

How it sees the combined P&L

Every bar, _combined_pnl() sums Nautilus's Portfolio.total_pnl(instrument) — realized + unrealized, already converted to the account base currency (so it is multi-currency-correct) — across the monitored legs (portfolio_monitor.py:155-176):

combined_pnl = Σ over monitored instruments  Portfolio.total_pnl(iid)        # realized + unrealized
             + Σ legs' conservative-fill delta    # so the live decision matches the final §4.2/§8.1 fill

It reads this straight from the engine's live Portfolio / Cache — there is no separate accumulator to keep in sync (which is exactly why the old module-global users.py/tags.py aggregators are obsolete here). Perf: a flat instrument's P&L is constant between trades, so the monitor only re-values instruments that currently hold an open position, plus a one-shot recompute on each open→flat transition to catch the realized jump (:178-194) — identical number, far cheaper on large catalogs.

Why same-bar works (no 1-bar lag). When enforcing, the monitor is added to the engine before the legs, so within a single bar the engine calls the monitor's on_bar first (it publishes the breach) and then each leg's on_bar (it consumes) — the fire lands the same bar it was detected. Everything is one in-process engine, so the buses (keyed by portfolio_id) are physically shared between the monitor, the legs, and the ConservativeFillModel.
Why this underpins the report. This position-less-monitor + shared-bus pattern is identical on the Unified engine and the BacktestNode approaches (both attach the same monitor to the same engine) — that is why the Unified and Node columns match on every Level-2 row. It also generalizes directly to multi-portfolio: a tier of the same monitor (portfolio → tag → user), each summing combined P&L over its own scope of legs and firing the same kind of in-process bus. As of 2026-06-15 the session engine realizes this for the portfolio tier across co-run portfolios (one monitor per portfolio in a shared engine + a live cross-pf bus → cross-portfolio actions fire same-bar). The tag and user tiers of that pattern are now built too — a tag-scoped monitor and a synthetic USER::<id> monitor each sum combined PnL across their scope's portfolios and force-square the whole group same-bar on a Max-Loss/Profit/trailing breach (flat caps and trailing/profit-lock all live), and the post-run double-clip is suppressed via live_session_caps.
