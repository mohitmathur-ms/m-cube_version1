instrument_factory.py

d:\m-cube_version1\core\instrument_factory.py · Layer L0 — Data ingest
This module is the instrument builder of m-cube. Given a crypto or FX pair (or a Nautilus bar-type string), it produces a fully-specified NautilusTrader CurrencyPair — with the correct price and size precision, lot size, fees and limits — so the backtest engine knows exactly how to price, size and trade that symbol. Its single most important job: never lose price ticks to under-specified precision.

Functions — non-tech & technical definitions

_get_currency

Internal helper
def _get_currency(code: str) -> Currency

Non-technical

Turns a currency code like "USD" or "BTC" into a proper money object the system can do maths with. For real-world money (dollars, euros, pounds, yen) it deliberately keeps extra decimal places so tiny profits — fractions of a cent — don't get rounded away to zero. Anything it doesn't recognise is treated as a crypto coin with 8 decimals.

Technical (Nautilus)

Returns a Currency. For the four fiat codes in CURRENCY_PRECISION (USD/EUR/GBP/JPY) it constructs one explicitly with a higher precision and currency_type=2 (FIAT) plus the ISO-4217 code from _ISO4217, overriding Nautilus's default precision of 2 (cents).

  • Otherwise tries Currency.from_str(code) (built-in registry).
  • On failure, builds a currency_type=1 (CRYPTO) currency at precision=8.
Why the override matters: Nautilus defaults USD to 2 decimals (cents). At small trade sizes, sub-cent PnL truncates to 0.00 and silently vanishes from the account — so fiat precision is bumped to match PRICE_PRECISION.

create_instrument

Public API
def create_instrument(base: str, quote: str, venue: str="BINANCE", price_precision: int|None=None, size_precision: int|None=None) -> CurrencyPair

Non-technical

The factory's core builder. Hand it two currencies — a "base" (what you're buying, e.g. BTC) and a "quote" (what you pay in, e.g. USD) — and it returns a complete tradeable product definition: how many decimals the price has, the smallest order size, the minimum/maximum order, lot size, and the trading fees. It picks sensible decimal settings automatically if you don't specify them.

Technical (Nautilus)

Builds and returns a CurrencyPair with InstrumentId(Symbol(base+quote), Venue).

  • Price precision: explicit arg → BASE_PRICE_PRECISION[base] → PRICE_PRECISION[quote] → default 2.
  • Size precision: arg or default 0; derives size_step = Quantity(10**-size_prec) for size_increment/min_quantity.
  • Per-symbol config: load_instrument_config() supplies lot_size and a trade_size cap → max_quantity (else 9_999_999_999).
  • Sets price_increment, min/max_price, min_notional=Money(1, quote), margin_init/maint, and maker/taker_fee = 0.001.
Precision is silent and catastrophic if too low: FX minute bars stored at precision 2 collapse 1.0823 → 1.08, making open == close on every bar (all dojis). Always pick precision that preserves the smallest real tick.
size_precision ≠ max value: precision only controls decimal places. Nautilus stores quantities as fixed-point (FIXED_PRECISION=9), so the cap stays QUANTITY_MAX (~18.4B) regardless. Raising precision is safe; crypto uses non-zero so fractional lots (0.001 BTC) are tradeable.

_data_format_instrument_cfg

Internal helper
def _data_format_instrument_cfg(bar_type_str: str) -> dict

Non-technical

Looks up the "rule sheet" for a given asset class. From a bar-type string it figures out which kind of asset this is (crypto, FX, commodity, index…) and reads that asset class's settings file to find how its instruments should be built — decimals, quote currency, and so on. If anything along the way is missing, it just returns an empty answer so the builder can fall back to its built-in defaults.

Technical (Nautilus)

Resolves the venue's adapter config via load_adapter_config_for_bar_type(), reads its asset_class, then loads adapter_admin/data_formats/<asset_class>.json and returns its instrument sub-dict (price_precision, size_precision, quote_currency, base_currency_length, …).

  • Returns {} on any miss — no asset class, missing file, bad JSON, or non-dict instrument block.
  • Callers then fall back to the built-in precision tables in create_instrument.

_catalog_instrument

Internal helper
def _catalog_instrument(bar_type_str: str) # -> Instrument | None

Non-technical

Asks the question: "what instrument would the backtest engine actually use for this symbol?" Instead of guessing, it opens the real stored data and returns the exact instrument definition that was saved when the data was loaded. If that symbol hasn't been loaded yet, it returns nothing.

Technical (Nautilus)

Opens the ParquetDataCatalog at ./catalog, parses BarType.from_str(bar_type_str).instrument_id, and scans catalog.instruments() for the matching inst.id — returning that instrument or None.

  • This is the authoritative source: backtest_runner.py resolves the instrument the exact same way and calls make_qty() on it.
  • Sidesteps venue-name mismatches between bar types and adapter configs (e.g. COINBASE vs COINBASE_MS).
Why read the catalog at all? Reading the real ingested instrument means precision validation can never disagree with what the backtest actually does at runtime.

instrument_for_bar_type

Public API @lru_cache(256)
@lru_cache(maxsize=256) def instrument_for_bar_type(bar_type_str: str) # -> Instrument | None

Non-technical

The main "give me the right instrument for this data" function the rest of the app calls. It first asks for the real loaded instrument; if the data isn't there yet, it builds a stand-in from the asset class's rule sheet. It also splits a glued-together symbol like ADAUSD into base (ADA) and quote (USD). Results are remembered (cached) so repeated lookups are instant.

Technical (Nautilus)

Public, @lru_cached resolver used to validate a leg's lots/SL/TGT precision.

  • Prefers _catalog_instrument() (authoritative); returns it immediately if found.
  • Else parses symbol_from_bar_type / venue_from_bar_type; splits base/quote using base_currency_length (FX) or by stripping the quote suffix (variable-length crypto).
  • Calls create_instrument() with precision from _data_format_instrument_cfg(); returns None if nothing resolves.
Re-ingest caveat: because the catalog instrument wins, editing data_formats price/size precision only takes effect after the data is re-ingested (which rewrites the stored catalog instrument). The @lru_cache also holds results for the process lifetime.

How precision is resolved

Catalog wins. instrument_for_bar_type() returns the real ingested instrument from _catalog_instrument() whenever the symbol exists in ./catalog.
Else build from data_formats. _data_format_instrument_cfg() supplies price_precision / size_precision / quote_currency for the asset class.
create_instrument price ladder: explicit price_precision arg → BASE_PRICE_PRECISION[base] → PRICE_PRECISION[quote] → default 2.
Size ladder: explicit size_precision arg → default 0 (whole units); crypto sets non-zero so fractional lots trade.
Fiat money precision is separately bumped by _get_currency() via CURRENCY_PRECISION so PnL keeps sub-cent resolution.
