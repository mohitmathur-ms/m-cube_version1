§3What the OrderEmulator is & the problem it solves

Emulation lets you use order types even when your trading venue does not natively support them. Nautilus locally mimics the behaviour of these order types (such as STOP_LIMIT or TRAILING_STOP) while using only MARKET and LIMIT orders for actual execution on the venue. Orders.txt

When you create an emulated order, Nautilus continuously tracks a specific type of market price (chosen by the emulation_trigger parameter) and — based on the order type and conditions — automatically submits the appropriate fundamental order (MARKET/LIMIT) when the triggering condition is met. Worked example from the docs: an emulated STOP_LIMIT — Nautilus monitors the market price until the stop price is reached, then automatically submits a LIMIT order to the venue.

Why it exists — portability
Order emulation lets you use advanced order types even on venues that don't natively support them, making trading strategies more portable across different venues. The logic and code paths are exactly the same for all environment contexts and use a common OrderEmulator component, and there is no limit on the number of emulated orders per running instance. §4Enabling emulation: emulation_trigger & TriggerType

The only requirement to emulate an order is to pass a TriggerType to the emulation_trigger parameter of an Order constructor, or an OrderFactory creation method. Orders.txt

Don't confuse the two "trigger" parameters
emulation_trigger (takes a TriggerType) is what turns emulation on. It is distinct from the trigger_type field that order types like StopMarket/StopLimit carry to define the venue-side trigger-price reference. The knowledge base uses both but does not disambiguate them beyond this usage.

The choice of trigger type determines how emulation behaves: Orders.txt

  • For STOP orders, the trigger price is compared against the specified trigger type.
  • For TRAILING_STOP orders, the trailing offset is updated based on the specified trigger type.
  • For emulated LIMIT orders, the limit price is compared against the specified trigger type to decide when to release the order as a MARKET order.

§5Lifecycle of an emulated order

  1. Submitted by a Strategy via submit_order.
  2. Sent to the RiskEngine for pre-trade risk checks (may be Denied here).
  3. Sent to the OrderEmulator, where it is held / emulated.
  4. Once triggered, the emulated order is transformed into a MARKET or LIMIT order and released (submitted toward the venue).
  5. The released order undergoes final risk checks before venue submission.

Emulated orders are regular orders: they can be modified and canceled while emulated, are subject to the same risk controls, and retain their original client order ID throughout their entire lifecycle — so Cache queries by client_order_id work end to end. Orders.txt

Held emulated orders

  • The original SubmitOrder command is cached.
  • The order is processed inside a local MatchingCore component.
  • The emulator subscribes to any needed market data (if not already) to update the matching core.
  • The order can be modified (by the trader) and updated (by the market) until released or canceled.

Orders.txt — "Held emulated orders"

Released emulated orders

  • Transformed to a MARKET or LIMIT order via an additional OrderInitialized event.
  • The order's emulation_trigger is set to NONE — no component treats it as emulated anymore.
  • The original SubmitOrder command is sent back to the RiskEngine for re-checks (since it may have been modified/updated).
  • If not denied, it continues to the ExecutionEngine and on to the venue via an ExecutionClient, as normal.

§7MatchingCore & local trigger evaluation

The emulated order is processed inside a local MatchingCore component; the emulator subscribes to needed market data to update it. Release happens once data arrival triggers / matches the emulated order locally, at which point the order is transformed and released to the venue. The TriggerType (§4) determines which price the matching core compares against — quotes (BID_ASK), trades (LAST_PRICE), mid, mark, index, or the single/double-confirmation variants. Orders.txt

Boundary of documentation
The knowledge base does not describe the MatchingCore's internal matching algorithm, its data structures, or its tick-by-tick evaluation logic beyond “compares the trigger/limit price against the configured price source and releases on match.” Those internals are intentionally not asserted in this report.

§8Architecture & wiring (prose companion to Diagram A)

The execution layer comprises Strategy, ExecAlgorithm, OrderEmulator, RiskEngine, ExecutionEngine/LiveExecutionEngine, and ExecutionClient/LiveExecutionClient. Routing rules: Execution.txt — "Execution flow"

  • submit_order(...) routes to the OrderEmulator for emulated orders, to an ExecAlgorithm when exec_algorithm_id is set, otherwise to the RiskEngine.
  • submit_order_list(...) follows the same emulation / exec_algorithm_id branching.
  • modify_order(...) routes to the OrderEmulator for emulated orders, otherwise to the RiskEngine.
  • Cancel and query commands can route directly to the OrderEmulator, ExecAlgorithm, or ExecutionEngine, depending on the command and order state.

The RiskEngine sits on the submit and modify path and also receives order events such as OrderReleased from the OrderEmulator — this is the documented re-check on release. Execution.txt — "Risk engine"

Cache & MessageBus roles: commands/events travel point-to-point over the message bus; the emulator caches the original SubmitOrder and uses the Cache for emulated-order state. Order events are applied by the ExecutionEngine, which updates the Cache and publishes on the MessageBus (described for the ExecutionEngine generally, not the emulator specifically). §11Caveats & best practices

Never hold a local reference to an emulated order
The order object transforms when the emulated order is released (e.g. STOP_MARKET → MARKET). Use the Cache instead. This is the single most emphasized gotcha in the docs.
  • Dual risk checks: emulated orders are risk-checked both at submission and at release; they can be denied at either point.
  • Type transformation on release: the order changes type via a second OrderInitialized; downstream components stop treating it as emulated because emulation_trigger resets to NONE.
  • Stable client order ID: retained through the entire lifecycle, so Cache queries by client_order_id work end to end.
  • Crash recovery: if a running system crashes or shuts down with active emulated orders, they are reloaded inside the OrderEmulator from any configured cache database, preserving state across restarts.

§12Backtest vs live

The logic and code paths for order emulation are exactly the same for all environment contexts and use a common OrderEmulator component — i.e. no documented behavioural difference between backtest and live for the emulator itself. Orders.txt

Adjacent — but NOT the emulator
The one nearby backtest/live difference in the docs is for OTO contingencies: the default backtest venue uses a partial-trigger model, and you opt into full-trigger via oto_trigger_mode="FULL" on BacktestVenueConfig. This is a venue / matching-engine behaviour, not an OrderEmulator behaviour — the knowledge base never states that brackets (OTO/OCO/OUO) are processed by the emulator. §13What the knowledge base does NOT cover

Documented gaps — stated, not guessed
To keep this report honest about its source boundaries, the following are not present in the ntm3 knowledge base and are therefore not asserted above:
  • No OrderEmulatorConfig or engine/node-level enable flag — emulation is enabled per-order via emulation_trigger (NO_TRIGGER opts a single order out). Configuration.txt, Backtesting.txt, and Live Trading.txt contain zero emulation references.
  • MatchingCore internals — matching algorithm, data structures, tick-by-tick evaluation logic.
  • Exact data-subscription calls the emulator makes (which subscribe_* methods) — only the trigger-type → price-source mapping is documented.
  • Contingencies (OTO/OCO/OUO/brackets) are not documented as being handled by the OrderEmulator.
  • No backtest-vs-live behavioural divergence is documented for the emulator (code paths stated identical).
  • Position-ID / contingency handling specifically on emulated-order release is not documented.
