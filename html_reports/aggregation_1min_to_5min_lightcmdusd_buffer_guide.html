1. Plain English: how aggregation happens

A strategy says “trade me on 5-minute LIGHTCMDUSD bars.” But the engine was only fed 1-minute bars. So something has to collect five 1-minute bars and hand the strategy a single 5-minute bar. That collector keeps a small buffer: it drops each arriving 1-minute bar into the buffer, and the moment a bar arrives that belongs to the next 5-minute window, it seals the buffer into one finished 5-minute bar — open of the first bar, the highest high, the lowest low, the close of the last bar, and the volumes added up — then starts a fresh buffer.
Technically: each bar is a NautilusTrader Bar object carrying a BarType, OHLCV Price/Quantity values, and nanosecond ts_event/ts_init timestamps. The aggregated bar is built with the instrument's own factories (instrument.make_price(...), instrument.make_qty(...)) so its prices honour LIGHTCMDUSD's 3-decimal precision and its volume is clipped to QUANTITY_MAX. The output carries the target BarType (…-5-MINUTE-BID-EXTERNAL) and is stamped at the window close.

2. Two ways to aggregate: Nautilus native vs our buffer

NautilusTrader can build higher-timeframe bars for you with a built-in component called the TimeBarAggregator. We used to rely on it, but it caused phantom bars whenever we filtered the input stream, so we now do the aggregation ourselves inside the strategy with a tiny buffer. Both produce the same OHLCV; they differ in who buffers the bars and which source bars land in each window.
Technically — the native path. Nautilus' TimeBarAggregator is wired by subscribing to a composite bar type of the form LIGHTCMDUSD.COMMODITIES_MS-5-MINUTE-BID-INTERNAL@1-MINUTE-EXTERNAL. The INTERNAL half names the bar Nautilus assembles; the @1-MINUTE-EXTERNAL half names the feed it listens to. It labels each emitted bar with its close timestamp using a (left, right] bracket (the convention documented in the sibling aggregation_1min_to_15min_guide.html for FX).
Why we replaced it. The portfolio runner filters the 1-minute stream (e.g. run_on_days, intraday entry_start_time/end_time windows). When bars are dropped from the feed, Nautilus' internal aggregator sees gaps and can emit synthetic stale-close bars across them, which fire phantom signals. The fix (see the docstring of core/aggregating_strategy.py) is to aggregate inside the strategy, on exactly the stream the strategy sees — no gaps, no synthetic bars, and no composite INTERNAL@ bar types at runtime.

3. The bracket: [T−N, T) floor-bucketing

Our buffer decides which window a 1-minute bar belongs to by flooring its timestamp down to the nearest 5-minute mark. A bar at 00:00, 00:01, 00:02, 00:03 or 00:04 all floor to 00:00, so they share one window; the bar at 00:05 floors to 00:05 and opens the next one. That window is then labelled with its close time, 00:05. So the left edge is included and the right edge is excluded — the opposite end-points to the native Nautilus aggregator, even though both stamp the result at the close.
Technically: _floor_to_interval(ts, interval) computes n = (ts − epoch) // interval and returns epoch + n·interval — an epoch-aligned floor valid for any fixed-width interval (5-MIN, 1-HOUR, 1-DAY, 1-WEEK; not 1-MONTH, which has no fixed width). A bar joins the window whose floor key it shares. When a bar with a different floor key arrives, the previous window is sealed and stamped at window_start + interval (the close / right-edge label). In set notation the window labelled T is {x : T−5 min ≤ x < T}.

Contrast with the FX 15-min guide. That guide documents Nautilus' native (left, right] bracket, where the bar labelled 00:15 covers {00:01 … 00:15} and the very first window is a lone partial bar. Our buffer uses [left, right) floor-bucketing instead: the bar labelled 00:05 covers {00:00 … 00:04}, the aligned 00:00 bar is not isolated, and the only partial window is the trailing one. Same OHLCV reduction, opposite end-points.

4. The buffer system internals

The whole mechanism is one small class, BarAggregator (core/aggregator.py:355–421). It holds two pieces of state: _window_start (the floor key of the window currently filling) and _buffer (the 1-min bars collected so far).

core/aggregator.py — BarAggregator.on_bar (the boundary check)
def on_bar(self, base_bar: Bar) -> Bar | None:
    ts  = pd.Timestamp(base_bar.ts_event, unit="ns", tz="UTC")
    key = _floor_to_interval(ts, self._interval)   # which 5-min window?
    emitted: Bar | None = None
    if self._window_start is None:
        self._window_start = key                   # first bar ever
    elif key != self._window_start:
        emitted = self._build_window()             # boundary crossed -> seal prior window
        self._window_start = key
    self._buffer.append(base_bar)                  # append AFTER emit:
    return emitted                                 #   the boundary bar opens the next window
Technically — the append-after-emit invariant. The arriving bar is appended to _buffer after the boundary check. So when the 00:05 bar arrives, the 00:00 window is sealed from the bars already buffered (00:00–00:04) and the 00:05 bar becomes the first member of the next buffer. This is exactly why the right edge is exclusive.
core/aggregator.py — BarAggregator._build_window (the OHLCV reduction)
def _build_window(self) -> Bar:
    bars = self._buffer
    o   = float(bars[0].open)                       # open  = FIRST bar's open
    h   = max(float(b.high) for b in bars)          # high  = MAX high
    l   = min(float(b.low)  for b in bars)          # low   = MIN low
    c   = float(bars[-1].close)                     # close = LAST bar's close
    vol = min(sum(float(b.volume) for b in bars), float(QUANTITY_MAX))   # volume = SUM (clipped)
    # Stamp at the window CLOSE (right-edge label): 00:00..00:04 -> labelled & delivered at 00:05.
    close_ts = int((self._window_start + self._interval).value)
    agg = Bar(bar_type=self._target_bar_type,
              open=self._instrument.make_price(o),  high=self._instrument.make_price(h),
              low=self._instrument.make_price(l),   close=self._instrument.make_price(c),
              volume=self._instrument.make_qty(vol),
              ts_event=close_ts, ts_init=close_ts)
    self._buffer = []                               # reset for the next window
    return agg

Technically: the strategy never touches BarAggregator directly. The AggregatingStrategyMixin wraps it: _setup_aggregation(...) builds the aggregator in on_start; _route_bar(bar) in on_bar returns None while a window is filling and the finished 5-min Bar when it closes (also feeding the strategy's indicators via ind.handle_bar(agg)); _flush_aggregator() drains the tail in on_stop. If no target is configured the mixin is a transparent pass-through and single-timeframe behaviour is byte-identical.

8. Worked window — first 5-min bar (T = 00:05)

Take the 5-min bar labelled T = 2020-04-01 00:05:00. By the floor-bucket [00:00, 00:05) rule it consumes exactly the five 1-min bars {00:00, 00:01, 00:02, 00:03, 00:04} — the 00:05 bar is excluded because it opens the next window. The aggregate's OHLCV must equal: first open, max high, min low, last close, sum volume.

Check. open = first row's open = 20.335 ✓  ·  close = last row's close (00:04) = 20.515 ✓  ·  high = max of column = 20.516 (at 00:04) ✓  ·  low = min of column = 20.305 (at 00:00 & 00:01) ✓  ·  volume = 144+88+121+97+63 = 513 ✓  ·  stamped at the close 00:05 ✓
The 00:05 bar is not in this window. Under our floor-bucket rule the close of the window is exclusive: the 00:05 source bar opens the next window (labelled 00:10) and becomes the first member of the fresh buffer. This is the single behavioural difference from Nautilus' native (left, right] aggregator, which would instead pull 00:05 in and drop 00:00.

9. Edge cases — partial window & the aligned open

9.1 No lone first bar

Because the aligned opening bar (00:00) floors to the same key as 00:01–00:04, it is grouped with them into the first full window. There is no partial single-bar window at the start — the problem the FX 15-min guide warns about does not arise here.

Verified by tests/test_bar_aggregator.py::test_no_lone_first_bar_at_aligned_open (lines 102–109): five bars 00:00..00:04 emit nothing; the 00:05 bar triggers the first emission.

9.2 The trailing partial window

Where the partial window lands. If the data ends mid-window (say the last bars are 00:05..00:07), no later bar ever arrives to seal it via on_bar. At strategy stop, AggregatingStrategyMixin._flush_aggregator() calls BarAggregator.flush(), which builds the aggregate from whatever remains in the buffer and clears it. The mixin discards this final bar (no order action) so no spurious signal fires on a truncated window.

Verified by tests/test_bar_aggregator.py::test_flush_drains_trailing_window (lines 120–128): three buffered bars emit nothing until flush() seals them; a second flush() returns None.

And the offline/batch pandas path used by scripts\aggregate_catalog.py to pre-aggregate the catalog (same OHLCV math, closed='right', label='right' resample):

Bottom line. m-cube aggregates LIGHTCMDUSD 1-MINUTE-{BID,ASK}-EXTERNAL → 5-MINUTE-{BID,ASK}-EXTERNAL with an in-strategy BarAggregator buffer that replaces Nautilus' native TimeBarAggregator: five source bars in, one aggregate out (open=first, high=max, low=min, close=last, volume=sum), under a floor-bucket [T−5, T) bracket labelled at the close. It sees the exact stream the strategy sees, so stream filters never produce phantom synthetic bars.
