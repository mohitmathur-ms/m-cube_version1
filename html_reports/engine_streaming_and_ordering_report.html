1. The earliest design — post-run clip

The earliest approach ran each enabled slot in its own BacktestEngine in its own worker process (a ProcessPoolExecutor). A single run, pure per-leg — no leg could see the combined portfolio P&L during the run (separate processes, no shared state).

So portfolio SL/Target was applied purely as post-processing: after the per-slot runs, merge the per-slot equity curves into a combined P&L curve, find the breach point, and CLIP — drop the trades opened after the breach (e.g. after the square-off time).

The limitation (confirmed in the code) The clip dropped post-breach trades but did NOT close the positions already open at the breach — a position opened before the breach but closed after it was kept whole and ran to its natural exit. So the "square-off" truncated the trade list without actually squaring off open positions. Documented in _truncate_open_positions_at_clip's docstring:
“the splice head keeps positions by ts_opened < clip_ns, so a position opened before the breach but closed after it is kept whole — running past the breach to its natural exit.”
That helper (which rewrites the open-at-breach position to close at the breach, mark-to-market) was a later refinement; it explicitly “degrades to the prior ‘natural exit’ behaviour” when data is missing — i.e. natural-exit was the original behaviour.

No ReExecute in this phase — pure post-processing on a finished run can't re-enter the market.

2. The two-pass approach

To support ReExecute (and aggregate Move-SL discovery) — which the single post-run pass couldn't do — a second pass / replay was added:

Portfolio featureHow it was done (multi-pass)
ReExecuteReplay: pass 1 discovers the breach + each leg's entry price; pass 2 re-runs the slots starting flat from the clip, with resting-limit re-entries.
Aggregate Move-SL / Hit-On-LegDiscovery pass (find the trigger timestamp) + an apply pass (move SL).
Open-at-breach positionsRefined to close at the breach (mark-to-market) via _truncate_open_positions_at_clip, instead of running to natural exit.
Limitations of two-pass Portfolio decisions were still reconstructed after the run, not enforced during it; cross-leg coordination was impossible in one pass (separate processes); it needed 2–3 passes (slower); and the reconstruction was approximate at the edges.

3. Migration to the unified single-pass live engine

The fix was to put all legs plus a position-less PortfolioMonitorStrategy in ONE engine, running ONE pass, in the same process. Now the monitor can see the combined P&L live, every bar, and enforce portfolio logic during the run:

Monitorsees combined P&L live each bar
Breachpublishes to an in-process bus (keyed by portfolio)
Each legreads the bus → closes / re-arms its own position live

How the monitor tracks combined P&L

The enabler: the monitor is a position-less Strategy living in the same engine as the legs, so it can read the shared Portfolio directly — impossible in the per-slot design where legs were in separate processes. Every bar it computes the live combined P&L:

combined_pnl = Σ portfolio.total_pnl(instrument_id)   # over EVERY leg's instrument
             + cons_bus[0]                            # live conservative-fill delta
   # total_pnl = realized + UNREALIZED (mark-to-market), so the curve reflects
   # open positions on every bar — not just realized P&L at closes.
  • Combined & live: portfolio.total_pnl(iid) gives realized + unrealized P&L per instrument; summed across all legs it's the portfolio's mark-to-market P&L at that bar (multi-currency safe via the venue's base currency).
  • Performance (skip-when-flat): total_pnl dominates runtime, so the monitor only re-values instruments that currently hold an open position (a flat instrument's P&L is its constant realized total between trades), with a one-shot recompute on each open→flat transition to catch the realized jump. When no position is open at all it reuses the last value — no new breach is possible while fully flat.
  • Conservative consistency: legs publish their live §4.2 conservative-vs-engine fill delta on a shared bus (cons_bus); the monitor adds it, so its SqOff/Target/ReExecute decisions use the same conservative P&L the final report shows.
  • References & baselines: a day baseline (resets each calendar day → day-scoped SqOff), a trailing-reset baseline (→ ReExecute, capped at the configured count), and the §5.3 confirmation-delay window (a breach must hold N seconds before it fires; clears if it recovers first).
  • Underlying SL: for the underlying-price types it tracks the primary slot's bar close live and evaluates the cross / loss+band condition each bar — same primary series the post-run path used, now read in-engine.

On a breach it calls _fire(...), appending an action-aware entry {ts, action, market, reason} to the in-process fire bus (keyed by portfolio_id); each leg reads it on the same bar and closes / re-arms its own position. The reason string becomes the orderbook exit tag. Implementation: core/portfolio_monitor.py — _combined_pnl(), on_bar(), _eval_side(), _fire().

This was rolled out in phases (all legs in one engine → live SqOff → live ReExecute → live aggregate/Hit-On-Leg → streaming) and made the default. The old behaviour remains reachable via the escape hatch _USE_POST_RUN_PF=1.

Other features moved to live one-pass in the same effort: §8.1 directional close + portfolio-SqOff VWAP enhancement, underlying-price SL (Underlying Movement / Loss & Underlying Range — which also fixed a latent misfire), the §5.3 confirmation Delay, and the §8.2 exit-sell-first log ordering.

4. The unified engine's eager data loading

The unified engine is a low-level BacktestEngine with eager data handling — every bar for the whole range is read into an in-memory list, sorted, then run in one shot:

all_bars = []                                  # load EVERY bar for the range
for slot: all_bars += catalog.bars(slot.bar_types, start, end)
all_bars.sort(key=lambda b: b.ts_init)
engine.add_data(all_bars); engine.run()        # one shot
Why this matters next Peak memory scales with the whole date range (the FX catalog is ~24M bars). Fine for one run — but the next goal made it the binding constraint.

5. The goal — multi-user, concurrent backtests

The driver: many users running many backtests simultaneously. Two clarifications shaped the rest:

RealizationConsequence
Concurrency comes from process isolation, not the engine API (Nautilus engines aren't thread-safe).Runs must be in separate processes regardless of engine.
The lever the engine choice affects is per-run memory.So: stream the data instead of loading it all.

6. Shifting toward BacktestNode

NautilusTrader's high-level BacktestNode takes a chunk_size and streams the catalog in row-batches via an internal DataBackendSession — peak memory ≈ one chunk, independent of the range. That's the memory profile we wanted.

BacktestRunConfigvenues + data + chunk_size
node.build()builds engine, loads instruments
get_engine()attach strategies imperatively
node.run()streams chunks → engine

8. The problem — same-timestamp ordering (ASK/BID/MID)

For an FX leg a single minute is three bars at the same timestamp: MID, BID, ASK (MID is synthesized from BID/ASK). Something must decide the order within that minute.

Unified BacktestEngineBacktestNode
Data deliveryone in-memory list, sorted by ts_initDataBackendSession merges files by ts, streamed in chunks
Same-ts ordercontrollable (we own the sort)internal / not controllable — MID may land first, middle, or last
The problem The unified order was incidental (load order + stable sort → MID,ASK,BID), and BacktestNode uses a different internal order. If results depend on that order, the engines can't agree — and the node's order can't be forced.

9. Proving the order matters

Change only the same-ts tiebreak on BXT_11 (FX, EMA-Cross, SL/TP):

Same-ts orderTotal P&LTrades
MID, ASK, BID (incidental default)−4650.63367
ASK, BID, MID (reordered)−5241.58422
BacktestNode (its internal order)−4647.12371
Result Reordering the same three bars swung the result by $591 / 55 trades. The output is materially sensitive to same-timestamp order — and the node (−4647) is close to but not identical to the unified (−4650), so it can't be byte-identical.

10. Root cause — a same-bar re-entry race

The first divergence is one minute, 04:35 — a long's stop fires and the EMA flips to sell on the same bar:

# UNIFIED (MID,ASK,BID) — fills at 04:35
04:35:00  EXIT  SELL  px=1.22452  tag=[Stop Loss: 1.22439 <= SL 1.22444]
          # ...that's it. Long closed. New short DEFERRED.

# REORDERED (ASK,BID,MID) — fills at 04:35
04:35:00  EXIT   SELL  px=1.22454  tag=[Stop Loss: 1.22439 <= SL 1.22444]
04:35:00  ENTRY  SELL  px=1.22454  tag=[EMA Cross SELL: fast(9) < slow(21)]
          # Long closed AND a new short OPENED on the same bar.
Root cause At 04:35 the stop closes the long and the EMA simultaneously signals a short. Whether the leg takes that short on the same minute depends on whether it's already flat (the close has settled) when the entry is evaluated — which depends on which of MID/BID/ASK is processed last. The same-ts order flips a "re-enter on the exit bar?" decision, and that one trade cascades (367 vs 422 trades).

The new short is the strategy's own EMA-cross signal (tag EMA Cross SELL) — not a re-execute or reverse (BXT_11: on_sl_action="close", max_re_executions=0).

11. Confirming the fills are correct

We checked the scarier possibility — that the order corrupts fill prices — and it's false:

PositionExit fillMatches
LONG exit (sell to close)1.22453BID close ✓
SHORT exit (buy to close)1.23021ASK close ✓
Conclusion LONG exits fill at the BID, SHORT exits at the ASK — exact to the 5th decimal, 10/10 positions. So this is a determinism / re-entry-policy issue, not a fill bug. Both engines price every fill correctly; they only sequence a few same-bar re-entries differently.

12. The fixes

11.1 MID-primary normalization

The signal should run on the unbiased midpoint (ASK-only/BID-only skews indicators by half the spread). So whatever the UI selects, the signal primary is forced to MID for FX; fills stay BUY→ASK, SELL→BID. Verified: ASK-primary and BID-primary portfolios now produce the identical result to MID-primary.

11.2 Explicit same-ts order — ASK, BID, MID (quotes-before-MID)

The incidental order became an explicit, deterministic contract (spec §4.1/§4.2: an exit's conservative fill should see the current minute's bid/ask before the MID trigger), applied project-wide, no flag:

def _same_ts_sort_key(bar):
    rank = {ASK:0, BID:1, MID:2}.get(price_type(bar), 3)
    return (bar.ts_init, rank)
BonusMaking the order explicit brought the unified and per-slot paths into agreement (both −5241.58 / 422 on BXT_11).

11.3 "Stream it yourself" — controlled order and bounded memory

node.run() can't control the same-ts order, so we stream the data ourselves: read the catalog in date windows, sort each window with our key, feed it, advance, drop it.

for window in date_windows(start, end, days=7):
    chunk = catalog.bars(all_bar_types, window.start, window.end)
    chunk.sort(key=_same_ts_sort_key)            # OUR order: ASK,BID,MID
    engine.add_data(chunk, sort=True); engine.run(streaming=True); engine.clear_data()
Why this is the answerControlled order (we sort each chunk) and bounded memory (≈ one window). Date-aligned windows never split a timestamp, so per-window sort + ascending windows reconstruct the same global order as an eager sort → byte-identical. The only thing dropped is node.run() — exactly the part whose order we couldn't control.

This record documents the full evolution: from the earliest post-run clip (single run + truncate, open positions not closed), to the two-pass replay (adding ReExecute), to the unified single-pass live engine, to the streaming & ordering work — where same-timestamp (MID/BID/ASK) ordering was found to materially affect results via a same-bar close→re-enter race (not a fill bug), and resolved with an explicit ASK,BID,MID order everywhere, self-managed windowed chunking in the BacktestNode path, an eager no-chunk unified reference, and verified byte-identical results between the two.
