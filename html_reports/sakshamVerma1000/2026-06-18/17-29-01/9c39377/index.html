Plain English

What this change does, for a non-technical reader.

This push adds a new "Visual Verification" page to the backtesting platform. After running a backtest, a user can upload the trade order-book export (a CSV file) to this new tool and it will automatically check whether every stop-loss, take-profit, trailing stop, and other exit was computed and triggered correctly — giving a per-trade verdict rather than leaving the developer to verify by hand.

Alongside the tool, 18 pre-built "verification portfolio" files were added (VP-01 through VP-12 and OT-01 through OT-06). Each portfolio isolates one feature — for example, VP-01 tests a percentage stop-loss in isolation, VP-05 tests a trailing stop, VP-10 tests portfolio-level combined loss limits against leg-level stops. These serve as a permanent, reproducible test bed for the exit-management engine.

Batch scripts were also added to run all 18 portfolios in one go and produce a consolidated HTML report, along with a detailed written guide (manual_verification_v2.html) that explains exactly what to check, how to re-derive expected prices by hand, and what engine behaviors (like filling at a bar's close rather than the exact stop level) are expected quirks versus bugs.

The developer documentation (CLAUDE.md) was substantially expanded: the runtime-flag table now covers all active execution paths (unified engine, per-slot, Path B, session), the architecture section was updated to reflect that several backend files have been reorganized into sub-packages, and new sections document notable core modules.

Technical / Engineering

Implementation detail and impact, for engineers.

**core/visual_verification.py (new, ~337 lines):** The verification backend. Given an order-book CSV path and a loaded `PortfolioConfig`, it iterates every trade row and runs three verification axes per trade: (A) TIME — finds the first bar where the trigger condition holds (`low ≤ sl_level` for a long SL) and compares to the logged exit timestamp; (B) LOGIC — checks that the logged reason matches the condition, that actions (re-execute count, reverse side) are consistent, and that SL/TP never both fire on the same trade; (C) PRICE — recomputes `expected_sl = round(entry × (1 − pct/100), tick 0.01)` and diffs against `current_sl` in the CSV, then computes the fill-vs-level gap (the close-fill realism metric). It also reports six execution-realism diagnostics (D–I): entry correctness, realistic fills (close ≠ level), zero-slippage note, gap-through detection, intrabar SL-before-TP ordering, and a fill-at-level counterfactual P&L to quantify close-fill inflation.

**server.py (+129 lines):** New endpoint `POST /api/visual-verification/analyze` accepts a multipart CSV upload (`file`) plus `X-User-Id` header. It resolves the portfolio name from the filename convention, loads the config via `portfolio_from_dict`, invokes `core.visual_verification.analyze_order_book`, and returns the full analysis JSON (keys: `summary`, `trades`, `realism`, `config_loaded`, `feed_in_catalog`). A separate `GET /api/visual-verification/portfolios` lists eligible portfolios for the dropdown.

**static/js/visual_verification.js (~425 lines):** New SPA page wired into `app.js`. Renders the analysis JSON into a per-trade table (columns: kind, entry/exit price, expected level, Δ fill−level, timing verdict, logic verdict, price verdict, gap flag) plus a summary bar and realism panel. Added as a route in `App` alongside existing pages.

**portfolios/testing2/ (new directory):** 18 JSON portfolio configs generated programmatically by `_generate_portfolios.py` from a shared NIFTY/EMA-cross template (1-sec feed, 5-min composite, 2026-03-02 to 2026-03-20, product=MIS, squareoff 15:29 IST). Each file varies exactly one exit-config dimension. `_run_all_backtests.py` POSTs each config to the live Flask server and collects order-book CSVs; `_build_full_report.py` (~812 lines) calls `visual_verification` for each and renders a consolidated HTML report. `_verify_lib.py` (~121 lines) is shared assertion helpers.

**config/users.json:** Added `testing2` user so the test portfolio namespace resolves under `portfolios/testing2/`.

**CLAUDE.md:** Branch note on package modularization added; runtime flags table expanded from 3 rows (grouping/path-B/profiling) to 14 rows covering unified engine, per-slot force, PF enforce, live fill model, VWAP/directional fill, lazy stream, multi-portfolio; architecture diagram updated to reflect `core/backtest_runner/` as a package tree; new sections for notable core/ modules, strategy `_shared/` package, session/unified paths, package layout of `core/models/`, Strategy Tags tier, and CI/report pipeline.

Worked Example

A concrete illustration of the most significant change.

VP-01 (long SL 0.5%) end-to-end through the new tool:

User runs the VP-01 portfolio, exports `order_book_portfolio_VP-01_long_sl_pct_....csv`, uploads it to /visual-verification.

In `core/visual_verification.py`, for a trade with entry_price = 24722.00: expected_sl = round(24722.00 × (1 − 0.005), 0.01) = 24598.39 logged current_sl from CSV → 24598.39 ✓ (PRICE PASS) first bar where low ≤ 24598.39 → 2026-03-02T08:47:00Z logged exit_time from CSV → 2026-03-02T08:47:00Z ✓ (TIME PASS) logged reason → 'SL' ✓ (LOGIC PASS) exit_fill (trigger-bar close) → 24591.20 ≠ 24598.39 Δ fill−level = −7.19 (adverse, close-fill realism gap, expected engine behavior)

Risks & Follow-ups

  • visual_verification.py reads bar data from the order-book CSV only — it does not open the parquet catalog to re-derive the trigger bar's OHLC independently, so TIME-axis mismatches caused by data discrepancies may be missed.
  • The tool resolves the portfolio config by inferring the portfolio name from the uploaded CSV filename; a rename or non-standard export will silently load the wrong config.
  • OT-01 through OT-06 are documented as 'live-market' order types that are either blocked at save or not wired in the engine — they exist as rejection/documentation probes, not runnable verification cases; this distinction may be unclear to new contributors.
  • The _run_all_backtests.py script requires a live Flask server on localhost:5000; it is not integrated into pytest or CI, so test results are not automatically tracked.
  • VP-10 (portfolio combined-loss + leg SL) depends on portfolio-level enforcement (_USE_PF_ENFORCE=on); if the flag or two-pass machinery behavior changes, VP-10 results will silently diverge.
  • No automated assertions are wired — _build_full_report.py renders HTML but does not exit non-zero on failures; adding CI gate would close this gap.
