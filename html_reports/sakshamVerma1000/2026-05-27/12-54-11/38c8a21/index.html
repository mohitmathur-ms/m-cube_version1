Plain English

What this change does, for a non-technical reader.

This push adds a detailed internal research document answering a key architectural question: when a stop-loss or take-profit price is hit during live trading, is it the exchange itself that reacts, or is it our own software watching the price and sending a close order?

The short answer documented here is: it depends on one setting. In the standard NautilusTrader setup, stop-loss and take-profit orders sit directly on the exchange's order book. The exchange monitors them in real time and fills them automatically — your software doesn't need to be running at all. This is the safest and fastest model.

However, m-cube currently works differently. Instead of placing resting orders at the exchange, it keeps the stop-loss and take-profit levels as internal numbers and checks them on every price bar, then sends a market close order when a level is breached. This is necessary because m-cube supports advanced features like trailing stops, target-lock, and re-execution logic that a simple resting order cannot express.

The report maps out all three modes (venue-managed, Python-emulated, and m-cube's hand-rolled state machine), compares them across latency, resilience to crashes, and order type used, and frames the path forward if m-cube ever adds a live-trading layer. No production behaviour was changed — the code diff is a single blank line.

Technical / Engineering

Implementation detail and impact, for engineers.

The substantive change is the addition of `html_reports/Live_Env_Monitoring_sl_tp.html`, a self-contained research report (Mermaid diagram + comparison tables) that investigates NautilusTrader's order-routing architecture as it relates to `ManagedExitStrategy`.

The core finding documented: at submit time, `trading/strategy.pyx:891-897` branches on `order.emulation_trigger`. If `NO_TRIGGER` (the default from `order_factory.bracket()`), the command is forwarded via `send_risk_command()` → `RiskEngine` → `ExecEngine` → `ExecutionClient` → real venue. If any other `TriggerType`, it routes to `send_emulator_command()` → `OrderEmulator` (local Python `MatchingCore`), which watches the data feed and releases a plain `MARKET` order on trigger.

m-cube's `ManagedExitStrategy` (L2, `core/managed_strategy.py`) uses neither path for exit management: `current_sl` and `current_tp` are plain floats, and `_run_exit_phase` inside `on_bar` checks them bar-by-bar. This makes m-cube's model functionally equivalent to the emulated path but hand-rolled at the strategy layer — NautilusTrader's own classification marks this as the least-preferred fallback. The report justifies its existence: trailing SL, target-lock, `sl_wait_bars`, RBO, and `re_execute`/`reverse` actions all require dynamic per-bar logic that a static resting bracket (`STOP_MARKET` + `LIMIT`) cannot express.

The report also notes that the existing `_USE_NATIVE_BRACKET` experiment routes through `order_factory.bracket()` (backtest-only), which means the `SimulatedExchange` matching engine handles fills intra-bar — more realistic than bar-close exits — but falls back to the Python path when any dynamic exit feature is configured.

The one-line change to `core/managed_strategy.py` is cosmetic: an extra blank line inserted before the `self.order_factory.bracket(...)` call at line 2054, with no behavioural effect.

Worked Example

A concrete illustration of the most significant change.

The report's central routing decision, taken verbatim from NautilusTrader source (trading/strategy.pyx:891-897):

# order submitted via order_factory.bracket() with default emulation_trigger=NO_TRIGGER if order.emulation_trigger != TriggerType.NO_TRIGGER: self._manager.send_emulator_command(command) # → OrderEmulator watches price in Python else: self._manager.send_risk_command(command) # → RiskEngine → ExecEngine → VENUE

m-cube's ManagedExitStrategy never reaches this branch for exits: it never submits a resting SL/TP order. Instead, on each bar, _run_exit_phase checks `if bar.close <= self.current_sl: submit MARKET close`. The report documents this as equivalent to the emulator path, but hand-rolled — necessary because trailing SL updates and re-execute logic require per-bar mutation of those float targets.

Risks & Follow-ups

  • No production code was changed; this is research/documentation only — no runtime risk
  • The report references a `_USE_NATIVE_BRACKET=1` flag that does not appear in CLAUDE.md's runtime-flags table or in the diff — worth confirming whether this flag is implemented or only aspirational
  • The report asserts m-cube has no L4 live-execution layer, which matches CLAUDE.md — but if that layer is ever added, the Python-monitor SL/TP model documented here becomes a live-trading risk (unprotected positions on process crash)
  • The HTML file uses an external CDN for Mermaid (cdn.jsdelivr.net) — diagram won't render in an air-gapped environment
  • Consider moving research reports to a docs/ subdirectory rather than html_reports/ to keep that folder consistent with generated tearsheet outputs
