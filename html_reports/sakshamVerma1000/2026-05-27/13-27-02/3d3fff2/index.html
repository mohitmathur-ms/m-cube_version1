Plain English

What this change does, for a non-technical reader.

Every time code is pushed to this repository, a GitHub Action automatically generates a change-report webpage summarising what was modified. Previously that report contained a technical file-dependency diagram useful mainly to engineers.

This update adds a visual "knowledge graph" to every report — a diagram showing the key concepts, classes, and functions a change touches and how they relate to each other. The goal is to give any reader an immediate picture of what a push is really about, not just which files moved.

When the AI backend is available it authors the graph itself, drawing on real symbol names from the diff and expressing meaningful relationships. When the AI is unavailable the system automatically falls back to a graph built from the project's file-import structure, so a diagram is always present in every report.

The diagrams are drawn by the Mermaid.js library loaded from a public CDN and rendered inside the browser when the report page is opened. No extra build step is needed in the GitHub Actions workflow.

Technical / Engineering

Implementation detail and impact, for engineers.

A new module `.github/scripts/mermaid_graph.py` provides two public rendering functions. `from_concept(nodes, edges)` accepts the AI-authored semantic graph (list of `{id, kind}` nodes and `{source, relation, target}` edges) and emits Mermaid `graph LR` DSL. `from_depgraph(graph)` consumes the existing `depgraph.py` output as a deterministic fallback. Both functions remap real identifiers to safe tokens (`n0`, `n1`, …) because symbol names and file paths contain characters (`/`, `.`, `[`, `|`) that break Mermaid's parser; human-readable text lives in quoted node labels. Per-kind `classDef` blocks apply GitHub-dark palette colours matching `_style.py`.

In `generate_report.py` the change touches four layers. (1) `SYSTEM_STATIC` gains a fourth instruction asking the model to produce a `concept_graph` field (4–10 nodes, 3–12 edges drawn from real diff symbols). (2) `REPORT_TOOL`'s JSON schema gains a matching `concept_graph` object with fully-typed `nodes[]` and `edges[]` arrays. (3) `_normalize_report()` coerces any malformed or missing `concept_graph` to a well-formed `{"nodes": [], "edges": []}` dict so downstream rendering never raises. (4) `_graph_section(graph)` is refactored to `_graph_section(report, graph)` which calls the new `_mermaid_section(report, graph)`: that helper tries `mermaid_graph.from_concept()` first, falls back to `mermaid_graph.from_depgraph()`, and returns a graceful note only when both yield empty strings. The pre-existing SVG detail view is preserved below the Mermaid block under an `<h3>Dependency detail</h3>` heading.

The HTML template gains a CDN `<script>` tag for Mermaid 10, an `mermaid.initialize({startOnLoad:true, theme:"dark", securityLevel:"loose"})` call, CSS for `.mermaid` container (dark surface, rounded border) and `.graph-legend` colour-key spans per node kind. `push-report.yml` receives only a documentation comment block — no workflow steps change because Mermaid is browser-rendered.

Worked Example

A concrete illustration of the most significant change.

Before this push `_graph_section(graph)` returned only the deterministic SVG or a "could not be computed" note.

After, given a report where the AI returned: ``` concept_graph = { "nodes": [{"id": "from_concept", "kind": "function"}, {"id": "mermaid_graph", "kind": "file"}], "edges": [{"source": "generate_report", "relation": "imports", "target": "mermaid_graph"}] } ``` `mermaid_graph.from_concept(nodes, edges)` emits: ``` graph LR n0["from_concept"] n1["mermaid_graph"] n2["generate_report"] n2 -->|"imports"| n1 class n0 kfunc; class n1 kfile; classDef kfunc fill:#10243f,stroke:#58a6ff,... ``` That string is wrapped in `<div class='mermaid'>…</div>` and the CDN script renders it to SVG in the browser.

Risks & Follow-ups

  • Mermaid loaded from cdn.jsdelivr.net at view time — reports won't render graphs if CDN is unreachable or blocked
  • securityLevel:"loose" permits HTML inside Mermaid node labels; _mlabel strips most dangerous chars but does not fully sanitise — mild XSS risk if attacker-controlled symbol names reach the diagram
  • _MAX_NODES=16 / _MAX_EDGES=22 in mermaid_graph.py exceed the 4-10 / 3-12 caps advertised to the model in the prompt — model may legitimately emit up to 10 nodes and they render fine, but the cap mismatch could allow slightly larger graphs than intended
  • No unit tests for mermaid_graph.py; correctness relies solely on the __main__ self-check at the bottom of the file
  • mermaid_graph.py is missing a trailing newline (minor lint issue)
