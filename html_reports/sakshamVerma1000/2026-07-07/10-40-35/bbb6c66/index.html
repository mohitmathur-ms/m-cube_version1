Plain English

What this change does, for a non-technical reader.

The team added a dedicated AI assistant called `dckr` that specialises in Docker and containerisation questions for this platform. When someone asks how to run the app in a container — how to persist data, expose ports, set memory limits for backtest workers — the `dckr` assistant looks up the answer in a curated library of Docker documentation rather than guessing from general knowledge. This keeps containerisation expertise separate from the main AI session and makes answers more accurate and citable.

Two large test portfolio files were added to cover every possible combination of stop-loss and take-profit configuration — all 24 variants. These act as manual verification fixtures, letting the team confirm that every exit-management scenario the system claims to support actually behaves correctly.

A scalability analysis document was added explaining the platform's concurrency model, its current bottlenecks (including how multiple simultaneous backtest runs interact at the process level), and recommendations for future scaling.

Several supporting pieces were updated alongside: the visual-verification tooling gained new tests, the Dockerfile was revised, and a terminology reference for stop-loss and take-profit concepts was added to the codebase documentation.

Technical / Engineering

Implementation detail and impact, for engineers.

The core deliverable is a new Claude Code sub-agent defined in `.claude/agents/dckr.md`. The agent frontmatter declares `tools: Read, Grep, Glob` (read-only), `memory: project`, and a description that triggers automatic delegation whenever container-related questions arise. Its knowledge base — ~400 curated Markdown pages from the official `docker/docs` repository — lives under `.claude/agents/dckr_docs/` in 16 subdirectories (get-started, guides/python, compose, build, engine/containers, engine/storage, engine/network, engine/logging, engine/daemon, engine/security, desktop, reference/compose-file, reference/cli, includes, and others). `.claude/agents/dckr_docs/INDEX.md` is the agent's first-read table of contents mapping each topic to its files.

Two agent-memory namespaces were seeded. Under `.claude/agent-memory/dckr/`, `catalog-persistence.md` records the load-bearing finding that m-cube's `CATALOG_PATH` is derived from `server.py`'s own `__file__` location (always `/app/catalog` in-container), there is no env-var override, and the Dockerfile already declares that path as a `VOLUME`. Under `.claude/agent-memory/ntm3/`, four new memory files document verified findings from inspecting the installed `nautilus_trader==1.224.0` package: `BacktestEngine.run()` holds the Python GIL for the entire bar loop (confirmed by absence of `with nogil:` blocks in the Cython source), each `BacktestEngine` owns its own `NautilusKernel` so two concurrent engines are fully isolated, the Rust logging subsystem is the only genuine process-global singleton, and the default unified path runs `engine.run()` in the Flask request thread with no `ProcessPoolExecutor`.

`portfolios/testing2/SL_Test_Scenarios.json` and `portfolios/testing2/TP_Test_Scenarios.json` are each 1447-line portfolio configuration files. Each contains a slot matrix systematically exercising all 24 combinations of SL/TP type and value against real instruments, intended as manual regression fixtures for `ManagedExitStrategy` exit logic.

`SCALABILITY.MD` documents the concurrency architecture conclusions drawn from the ntm3 memory research: the GIL serializes concurrent unified-path backtests within a single Flask process, per-slot `ProcessPoolExecutor` is the current source of real parallelism, and the recommended path to scaling concurrent users is a bounded process-global pool rather than more Flask threads.

`core/models/SL_TP_terms.md` is a 263-line terminology reference. `core/visual_verification.py` was substantially extended, a companion `tests/test_visual_verification.py` (206 lines) was added, and `static/js/visual_verification.js` received minor updates. `server.py` received a small change (+7 lines, content not visible in the truncated diff). The Dockerfile was modified but the full before/after is not visible in the truncated diff.

Worked Example

A concrete illustration of the most significant change.

The dckr subagent in action: a developer asks "How do I persist the catalog across container restarts?"

Without dckr, Claude would answer from general Docker memory and might suggest a `CATALOG_PATH` env var (which does not exist in m-cube).

With dckr, the agent reads `INDEX.md`, opens `engine/storage/volumes.md` and `engine/storage/bind-mounts.md`, then cross-references `.claude/agent-memory/dckr/catalog-persistence.md` to surface the project-specific fact: the catalog is always at `/app/catalog` (hardcoded via `server.py`'s `__file__`), no env var override exists, and the correct answer is:

``` docker run -v ./catalog:/app/catalog mcube ```

and it cites "per engine/storage/bind-mounts.md, *Bind mounts* section; path confirmed from catalog-persistence.md memory".
