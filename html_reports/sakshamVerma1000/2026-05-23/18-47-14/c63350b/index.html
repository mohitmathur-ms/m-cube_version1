Plain English

What this change does, for a non-technical reader.

The 'View Data' screen was showing the wrong label for Coinbase crypto data — it was displaying 'COINBASE_MS' instead of 'COINBASE', so the venue name didn't match what the engine actually uses. This push fixes that by correcting the venue label in the Coinbase adapter configuration and updating the frontend to render it properly.

A new tool has been added that lets the assistant generate rich, self-contained HTML overview reports for any file in the project. When asked to summarize or preview a file, it can now produce a polished dark-themed document with structured sections, metadata, a sample of the file's contents, and clear plain-English plus technical explanations side by side. A companion reference guide was also generated documenting every hardcoded value baked into the five trading strategies — things like 'all orders are market orders' and 'Range Breakout supports at most 10 legs' — so users know exactly what they cannot change from the UI.

A small but important correctness gap was closed in the portfolio backtest engine: the Path B execution path (which uses NautilusTrader's higher-level BacktestNode API) was missing a check that Path A already had, which determines whether all slots in a group need exit-management bars to keep flowing after the entry window closes. Without this, open positions in a Path B grouped run could have been left unmonitored for stop-loss or take-profit hits.

Finally, a test portfolio ('Portfolio test 1') was saved to the shared default user folder, and some internal import hygiene fixes were applied to prevent circular-dependency errors in the model layer.

Technical / Engineering

Implementation detail and impact, for engineers.

**COINBASE venue fix (`adapter_admin/adapters_config/coinbase_ms.json`, `static/js/view_data.js`):** The `venue` field in `coinbase_ms.json` was corrected from `"COINBASE_MS"` to `"COINBASE"`. The `id` and `exchange_type` fields remain `coinbase_ms`/`COINBASE_MS` (used for adapter lookup), but `venue` is the string mapped to the NautilusTrader `Venue(...)` object at backtest time and is also what `view_data.js` resolves when rendering bar-type labels. Because instrument IDs are formed as `BTCUSD.COINBASE`, any venue lookup using `COINBASE_MS` would fail to match, producing a blank or incorrect label. The `view_data.js` change (~11 lines) likely adds or corrects a normalisation/lookup step on the frontend side.

**Path B group-management flag (`core/backtest_runner.py:_run_slot_group_node`):** Adds `_group_all_managed` — a boolean computed via `all(slot.exit_config.has_exit_management() or slot.exit_config.squareoff_time or slot.squareoff_time or default_squareoff_time or default_rbo_settings is not None for slot, _cap in group)` — mirroring the identical flag already present in Path A's `_run_slot_group`. In Path A, this flag gates whether post-entry-window bars are passed through to strategies (required for exit monitoring of open positions). Its absence in `_run_slot_group_node` was a parity gap: grouped Path B runs with exit management or squareoff could silently drop bars after the entry window, leaving positions unmonitored. A separate, smaller change adds `user_id: str | None = None` to `_extract_portfolio_results` (line 4969), a preparatory parameter likely for per-user result provenance tagging.

**Circular-import guards (`core/models/slot_sizing/__init__.py`, `core/models/squareoff/__init__.py`):** Both submodules now wrap their model imports (`StrategySlotConfig`, `PortfolioConfig`) in `if TYPE_CHECKING:` blocks. This is the standard Python pattern for annotation-only imports that would otherwise create a runtime cycle between the `core/models` subpackages.

**New Claude skill (`.claude/skills/html_report_generator/SKILLS.MD`):** Defines the `html-report-generator` slash-command. Specifies a 6-step workflow (identify → read → detect type → build → write → confirm), a mandatory 'paired-description pattern' (plain-English block + `.callout-tech` block + example, in that order, for every section that introduces a concept), per-type recipes for CSV/TSV, JSON, logs, source code, Markdown, and binary files, a full dark-theme inline CSS component library (`.callout`, `.callout-tech`, `.callout-warn`, `.callout-ok`, `.simple`, `.filebox`, `.badge-*`, `.agg-row`), secret-redaction safety rules (AWS key pattern, `sk-`, Bearer tokens, fields named `password`/`secret`/`token`/`api_key`), and edge-case handling (>10 MB files, encoding fallbacks, empty files).

**Reference HTML guide (`html_reports/strategy_hardcoded_values_guide.html`):** 775-line light-themed document (note: uses a light theme, not the dark theme the skill mandates) covering seven hardcoded values across `strategies/`: `TimeInForce.GTC` on every order, `order_factory.market()` for all entries and exits, `MAX_LEGS = 10` in `range_breakout.py`, the `max(trigger, bar_open)` modeling entry-fill clamp, `float('inf')`/`float('-inf')` degenerate-range sentinels under `target_stop_basis=1`, the `/ 100.0` percent-to-fraction divisor, and `1e9` nanosecond and HHMM integer-arithmetic constants.

Worked Example

A concrete illustration of the most significant change.

**COINBASE venue name fix — before/after**

Before (coinbase_ms.json): { "id": "coinbase_ms", "name": "COINBASE_MS", "venue": "COINBASE_MS", ... }

After: { "id": "coinbase_ms", "name": "COINBASE_MS", "venue": "COINBASE", ... }

A bar type string like `BTCUSD.COINBASE-1-MINUTE-BID-EXTERNAL` carries venue `COINBASE`. When view_data.js looked up the adapter config to resolve the display label, it found `venue: "COINBASE_MS"` — a mismatch — so the venue rendered incorrectly. After the fix, `venue: "COINBASE"` matches the instrument ID component, and the View Data panel correctly resolves and displays the venue name.
