SL Execution Logic — Three-Format Engine

Execution rules for the SL side of the SL/Target engine. Specified in parallel for Bid/Ask, OHLCV, and LTP data shapes.

Three formats supported: Format A — Bid/Ask   Format B — OHLCV   Format C — LTP
Adapter feeds one format; engine picks matching code path. Asset-class-to-format mapping is an adapter concern.

1. Hierarchy Structure

The engine evaluates SL across four nested levels every bar. Higher-level fires first and force-squares everything below.

Level 1 — Leg

Level 2 — Portfolio

Level 3 — User

Evaluation order: User → Portfolio → Leg per bar.

3. Adapter Contract

Format A — Bid/Ask

FieldMeaning
bid_o, bid_h, bid_l, bid_cBid side OHLC
ask_o, ask_h, ask_l, ask_cAsk side OHLC
bid_v, ask_vVolume per side (broker-dependent — see caveat)
bid_vwapRunning volume-weighted on bid side
ask_vwapRunning volume-weighted on ask side
mid_vwap(bid_vwap + ask_vwap) / 2 — bid-ask average reference
mark_price (crypto only)Exchange-published fair-value reference

Format B — OHLCV

FieldMeaning
open, high, low, closeSingle OHLC
volumeTraded volume in the bar
vwapRunning volume-weighted — see VWAP definition below
ltpLast Traded Price = close (in OHLCV bars, close IS the last traded price of that bar)
mark_price (crypto only, optional)Exchange-published fair-value reference

Format C — LTP (Last Traded Price)

FieldMeaning
ltpLast traded price for the bar / tick
timestampTime of the LTP observation
mark_price (crypto only, optional)Exchange-published fair-value reference

One price per bar — no high/low, no bid/ask, no volume, no VWAP. Trigger and fill collapse to single-value comparisons.

VWAP definition (Formats A & B)

VWAP = (H + L + C) / 3 × candle_weight
candle_weight = volume of that candle / total aggregate volume for that day till that point in time

Format A computes bid_vwap and ask_vwap independently using bid_v and ask_v respectively.

Mark Price (crypto only)

mark_price is published by crypto exchanges (CME, Binance, Bybit) alongside the last trade price. Computed by the exchange as a weighted average of multiple spot indices plus funding-rate adjustments. Useful as an alternative reference for triggers/fills — filters out manipulation via single-venue wicks. When the adapter exposes mark_price, user may configure trigger/fill to reference it instead of bid/ask/LTP (per-portfolio config).

Volume caveat (default — currency & commodity): Volume for currency and commodity is broker-dependent. In Dukascopy-style bid/ask data, volume is bid/ask quote size at that broker. For exchange-direct feeds (index futures, stocks, crypto futures), volume is true traded volume. The VWAP formula runs correctly either way, but on currency/commodity the resulting VWAP weights quote depth rather than executed flow.

4.2 Fill-Price Formula

Rule: SELL exits use MAX(vwap, hit) — conservative (pay more). BUY exits use MIN(vwap, hit) — conservative (receive less).

Format A

SL — SELL:  exit = ask_vwap if ask_vwap > bid_high  else bid_high
SL — BUY:   exit = bid_vwap if bid_vwap < ask_low   else ask_low

Format B

SL — SELL:  exit = vwap if vwap > high  else high
SL — BUY:   exit = vwap if vwap < low   else low

Format C

SL — SELL:  exit = ltp
SL — BUY:   exit = ltp

No spread / no VWAP / no high-low — fill equals the LTP that triggered.

4.3 SL Wait / Delay

Same in all three formats

On trigger bar:
    delay_pending    = True
    delay_start_time = current_dt

Each subsequent bar:
    if condition reverses:
        delay_pending = False              # DELAY_CLEARED
    elif elapsed < SL_Wait:
        skip (hold)
    else:
        execute exit

4.4 SL Value Parsing

Same in all three formats. Accepts absolute or % input.

Conversion at leg entry (Stoploss Type = Premium):

SELL leg:
    Premium with %:    sl = entry × (1 + pct/100)    # SL above entry
    Premium absolute:  sl = entry + value

BUY leg:
    Premium with %:    sl = entry × (1 - pct/100)    # SL below entry
    Premium absolute:  sl = entry - value

Type variants: None, Premium (alias: PremiumBased), AbsolutePremium, Underlying (not implemented at leg level — use portfolio level).

4.5 Move SL to Cost (leg-level)

Same in all three formats — uses entry_price and current price (per-format reference)

VariantRule
Move Only for Profitable Legsif leg_pnl > 0 → sl = entry_price
Move SL for All Legssl = entry_price for all ACTIVE legs
Move SL to LTP + Buffer for Loss Making LegsProfitable → sl = entry_price; Loss SELL → sl = ltp × 1.0005; Loss BUY → sl = ltp × 0.9995

After move, leg["sl_moved_to_cost"] = True is stamped and never cleared within a trading day.

4.6 Trail After Move SL

Same in all three formats. PnL-based step tightening, activated after Move SL to Cost fires.

# Set once when Move SL fires:
leg["move_sl_trail_anchor"] = curr_leg_pnl

# Each bar thereafter:
leg_gain = curr_leg_pnl - leg["move_sl_trail_anchor"]
if leg_gain >= sl_trail["every"]:
    steps  = int(leg_gain / sl_trail["every"])
    new_sl = sl_pending_val ± (steps × sl_trail["by"])    # SELL: subtract, BUY: add
    leg["move_sl_trail_anchor"] += steps × sl_trail["every"]
    # log: LEG_TRAIL_SL_UPDATED

Direction adjustment for new_sl:

  • SELL leg: subtract — tighter SL is lower
  • BUY leg: add — tighter SL is higher

sl_trail["every"] and sl_trail["by"] accept absolute or % input.

4.7 Leg-Level Actions (5 types)

SqOff · Re-Execute · Execute (other leg) · ReEntry · KeepLegRunning. Format-agnostic dispatch.

4.8 Leg Action Combination Rules

Max 3 actions. Invalid combos: KeepLegRunning+ReEntry, KeepLegRunning+SqOff, Re-Execute+ReEntry, >3 actions, Execute without valid leg_id.

4.9 Leg-Level Trailing SL — Profit Lock (NEW) Added this revision

Same in all three formats — PnL-based profit-lock ratchet, mirror of Target §4.7

Once the leg's PnL crosses an activation threshold, a profit floor is locked and ratchets upward as PnL grows. If PnL falls back to the floor, the leg exits with the locked profit protected.

Distinct from §4.5 / §4.6: Move SL to Cost + Trail After Move SL move the SL price level, and Trail only activates after Move-to-Cost fires. This profit lock is a standalone PnL floor with its own activation threshold — it does not require Move-to-Cost first, and can run alongside the loss-limiting SL.

# Activation:
if leg_pnl >= when_profit_reach:
    active       = True
    current_stop = lock_min_profit
    anchor_pnl   = when_profit_reach
    # log: LEG_TRAIL_SL_LOCK_ACTIVATED

# Active phase (each bar):
if leg_pnl <= current_stop:
    exit leg (SL_PROFIT_LOCK)                 # exit fill per §4.2, format-specific
else:
    gain = leg_pnl - anchor_pnl
    if gain >= trail_every:
        steps         = int(gain / trail_every)
        current_stop += steps × trail_by      # floor ratchets up — never down
        anchor_pnl   += steps × trail_every
        # log: LEG_TRAIL_SL_LOCK_UPDATED

Fields: enabled, when_profit_reach, lock_min_profit, trail_every, trail_by. All accept absolute or % input.

Three-format dependence. The ratchet logic is format-agnostic (operates on leg_pnl). Only two pieces are format-specific:

StepFormat A — Bid/AskFormat B — OHLCVFormat C — LTP
Mark price feeding leg_pnlSELL → ask side; BUY → bid side (cost to close); mark_price if configured (crypto)close (or vwap)ltp
Exit fill when floor breachedper §4.2 — SELL ask_vwap/bid_high, BUY bid_vwap/ask_lowper §4.2 — vwap/high/lowper §4.2 — ltp

5.3 Portfolio Delay

Same structure as leg-level SL Wait.

5.4 Trailing SL (Portfolio)

Same in all three formats. PnL-based step tightening at portfolio level.

# Anchor set on first profitable evaluation
trail_anchor_pnl = max(0, curr_pnl)

# Each bar:
gain = curr_pnl - trail_anchor_pnl
if gain >= trailing_sl["every"]:
    steps        = int(gain / trailing_sl["every"])
    portfolio_sl = portfolio_sl - (steps × trailing_sl["by"])    # loss threshold tightens
    trail_anchor_pnl += steps × trailing_sl["every"]
    # log: PORTFOLIO_TRAIL_SL_UPDATED

Trailing SL only tightens — it never loosens. every / by accept absolute or % input.

5.5 Move SL to Cost (portfolio-driven)

Same as leg-level §4.5, triggered by aggregate portfolio profit.

combined_pnl = Σ state["pnl"]["combined"] for state owned by uid

6.1 User-Level Trailing SL

user_trail_anchor = max(0, combined_pnl)
if (combined_pnl - user_trail_anchor) >= user_trailing_sl["every"]:
    steps = int((combined_pnl - user_trail_anchor) / user_trailing_sl["every"])
    user_sl -= steps × user_trailing_sl["by"]
    user_trail_anchor += steps × user_trailing_sl["every"]
    # log: USER_TRAIL_SL_UPDATED

max_loss accepts absolute input only (% removed at user level — see sl_features.html Level 3). every, by accept absolute or % input.

7. ReExecute Gating Flags

Same in all three formats

Four boolean flags that modify how re-execution behaves after an SL hit. Configured at portfolio level under the ReExecute tab.

FlagDefaultBlocks
no_reexec_sl_costOFFRe-Execute action when leg["sl_moved_to_cost"] == True. Avoids re-opening risk after a flat-out at cost.
no_wait_trade_reexecOFFPer-leg Wait & Trade delay on re-executions only (detected via exec_count >= 1). Original entry still waits.
no_reentry_after_endOFFBoth Re-Execute and ReEntry past Portfolio End Time. Cross-portfolio triggered Manual portfolios bypass this.
no_reentry_sl_costONReEntry action when leg["sl_moved_to_cost"] == True. Default ON — most strategies that move SL to cost intend a clean exit.

Dispatch checks

Action queue (in process_active_legs):

# Before queuing Re-Execute:
if reexec_cfg["no_reexec_sl_cost"] and leg["sl_moved_to_cost"]:
    # log REEXEC_BLOCKED_SL_COST, skip queue

# Before queuing ReEntry:
if reexec_cfg["no_reentry_sl_cost"] and leg["sl_moved_to_cost"]:
    # log REENTRY_BLOCKED_SL_COST, skip queue

# After End Time (in both action dispatch and IDLE entry):
if end_blocked and not _triggered_manual and reexec_cfg["no_reentry_after_end"]:
    # block all new re-execution and re-entry queueing

Entry-side check (in process_idle_leg_entries):

_is_reexec = leg.get("exec_count", 0) >= 1
if wt_delay > 0 and _is_reexec and reexec_cfg["no_wait_trade_reexec"]:
    wt_delay = 0   # log WAIT_TRADE_SKIPPED_REEXEC

Flag interactions

sl_moved_to_cost persistence. Flag is set once by MoveSLManager.apply() and never cleared within a trading day. Carries over into re-execution cycles if the gating flag was off — meaning if no_reexec_sl_cost is toggled ON mid-session (live mode), it correctly blocks the next re-execution attempt on legs that previously had SL moved to cost.

no_reexec_sl_cost vs no_reentry_sl_cost. Both react to the same flag but block different actions. Can be active simultaneously for full protection.

BUY  exit:  fill = ltp

Same conservative direction-aware rule as §4.2. Time-based exits use a simpler close-only fill since they aren't driven by intra-bar trigger events.

8.2 Exit Sell Legs First

Same in all three formats

Default ON. Controls leg ordering in batch exit events.

OFFOriginal dict-insertion order

In the current engine all legs in the same bar are processed within the same data row — no intra-bar leg-exit delay — so ordering affects PnL attribution sequence and orderbook log order, not fill prices. Becomes price-impactful when intra-bar delay is added.

9. Timing Gates

Same in all three formats

Three time fields control when SL-related entries and exits are permitted.

FieldEffect
Start TimeEarliest bar for any leg entry. Per-leg Start Time override allowed via leg config.
End TimeCutoff for new entries (including SL-triggered re-executions if no_reentry_after_end is ON). Open positions continue under SL/Target monitoring until SqOff Time.
SqOff TimeForced exit of all remaining ACTIVE legs at last known price. Distinct from per-leg SL and Portfolio SL.

End Time gate

if end_blocked and not _triggered_manual:
    skip — block IDLE leg entries (no new entries past End Time)

Manual portfolios that were started via a cross-portfolio "Start Other Portfolio" action bypass end_blocked for that trigger cycle.

SqOff Time forced exit

At or after SqOff Time, _close_active_legs() runs once and closes every remaining ACTIVE leg at last known price (no VWAP enhancement — see §8.1). Distinct code path from Portfolio SL.

Common configurations

  • Intraday strategy: End Time == SqOff Time (most common)
  • Allow late SL/Target management: End Time < SqOff Time. New entries blocked at End Time; existing positions continue exiting on SL/Target until SqOff Time

Validation rule

Portfolio Start ≤ Leg Start ≤ Portfolio End ≤ SqOff Time (enforced on save).

11. Portfolio Tags — Feature Request (To Be Added)

Hierarchy clarification

Different legs make up a strategy → strategies combine into a portfolio → portfolios belong to a user (algo).

SL is currently defined at three levels:

  • Leg level (§4)
  • Portfolio level (§5)
  • User level (§6)

Request

Add Portfolio Tags (also called Strategy Tags) as a way to group portfolios so that SL/Target can be assigned to a subset of strategies — between Portfolio and User in the evaluation hierarchy.

A portfolio tag groups multiple portfolios sharing a common characteristic (e.g., strategy type, market regime, time-of-day window). Each tag has its own SL/Target. When a tag's SL fires, all portfolios in that tag are force-sqoff'd; portfolios in other tags continue unaffected. User-level SL remains the ultimate ceiling.

Example

User runs 100 strategies (= 1 algo)
User-level SL  = ₹1,00,000

Divide the 100 strategies into 5 strategy tags of 20 each:
    Tag 1: 20 strategies — SL = ₹30,000
    Tag 2: 20 strategies — SL = ₹30,000
    Tag 3: 20 strategies — SL = ₹30,000
    Tag 4: 20 strategies — SL = ₹30,000
    Tag 5: 20 strategies — SL = ₹30,000

Concrete grouping example:
    Of the 100 strategies, 10 are of type "non-trending".
    To limit/fix loss on that type specifically, define a
    "non-trending" strategy tag and assign it its own SL
    (e.g., ₹30,000). When the tag SL fires, only those 10
    strategies are squared off — the other 90 keep running.

Validation rule (required when implemented)

When SL/Target is defined at the leg level, the engine must verify it does not breach the SL assigned at higher levels:

  • Sum of leg-level SLs within a portfolio ≤ portfolio SL
  • Sum of portfolio SLs within a tag ≤ tag SL
  • Sum of tag SLs ≤ user SL

If a leg-level SL/Target would violate the parent strategy / portfolio / tag / user limit, the engine should flag this on config save and prevent the run (or warn and clip the leg-level limit to fit). Same check applies for Target on the upper side.
