m-cube — Multi-Portfolio Architecture

One session engine · a live monitor tier (leg → portfolio → tag → user) · same-bar cross-portfolio actions. Turns every parked SL/Target setting CORRECT and Live, without regressing the single-portfolio engine.

Design spec · builds on the live PortfolioMonitorStrategy + ConservativeFillModel + unified/BacktestNode engine · cites file:line into the current code

One-sentence summary. Put every portfolio's legs plus a tier of position-less monitors (portfolio → tag → user) into one session engine, one pass, one process; each monitor sums the combined P&L over its own scope of legs live every bar and publishes to an in-process bus; legs (and other portfolios) read the buses and act the same bar — which makes cross-portfolio actions, user/tag limits, %-of-allocation and hierarchy validation all work live, exactly as the spec requires.

2. Design principles

PrincipleMeaning
Live per specThe spec evaluates the hierarchy every bar (User → Tag → Portfolio → Leg) and a higher level force-squares everything below in the same bar. Every decision and every cross-pf effect happens in-engine on the triggering bar — never a post-run pass.
No regressionEach portfolio's monitor + legs + buses stay byte-identical to a standalone run (they are already portfolio_id-keyed). Multi-portfolio is a strict superset: new monitors/buses are added on top; nothing existing is rewired. A parity gate proves it per build.
Reuse the monitor patternThe tag and user monitors ARE the existing position-less PortfolioMonitorStrategy, just scoped to a different set of legs. ~90% reuse.
Both approaches freeEverything is wired in the shared post-branch attach code, so the Unified engine and the BacktestNode path both get multi-portfolio automatically.

3. The session model (schema)

A request now carries a user's whole tree (NEW SessionConfig), not a single PortfolioConfig:

SessionConfig
  user_id
  allocation_base : float          # engine constant, fixed at session start (for "% of allocation")
  reporting_ccy   : str            # currency to aggregate cross-currency PnL into
  user            : { max_loss, max_profit, trailing_sl{every,by}, trailing_tgt{reach,lock,every,by} }
  tags     : [ { tag_id, portfolio_ids[], sl{...}, tgt{...}, trailing_sl{...}, profit_lock{...} } ]
  portfolios : [ PortfolioConfig + {
                   portfolio_id,           # unique
                   tag_id | null,
                   manual : bool,          # NEW: idle until a cross-pf Start/Execute fires it
                   pf_sl_action / pf_tgt_action may include:
                       target_portfolio, verb(sqoff|execute|start), delay_sec, reexecute_count
                 } ]
  # each leg inherits (portfolio_id, tag_id, user_id) + a GLOBALLY-UNIQUE strategy tag  P{p}-U{i}

The whole tree in one request is also what makes Σ-of-siblings validation possible (§11) — today the server only ever sees one portfolio, so it can't sum siblings.

4. One session engine

Generalize _run_portfolio_unified to accept a SessionConfig and add every leg of every portfolio to the one engine, plus the monitor tier. The node-vs-direct build branch is untouched; the new monitors are attached in the shared post-branch code (unified/__init__.py:489-562), so Unified + BacktestNode both inherit it.

ONE session engine · ONE pass · ONE process +----------------------------------------------------------------+ | UserMonitor scope = ALL the user's legs | <- ceiling | |- TagMonitor "A" scope = legs of P1 + P2 | | | |- PfMonitor P1 scope = P1's legs --> legs x N | | | +- PfMonitor P2 scope = P2's legs --> legs x N | | +- TagMonitor "B" scope = legs of P3 ... | | | | ConservativeFillModel (per venue, session-scoped, per-leg pin)| +----------------------------------------------------------------+ evaluation order each bar: User -> Tag -> Portfolio -> Leg a higher scope fires first and force-squares everything below, same bar

5. Scope & combined P&L

The one critical change to the monitor: aggregate P&L by the scope's set of leg strategy_ids, not by instrument. Today _combined_pnl sums Portfolio.total_pnl(instrument) (portfolio_monitor.py:155-176), which is engine-wide per instrument — correct only when an instrument belongs to one portfolio. If two portfolios share an instrument it cross-contaminates.

# scope = the set of leg strategy_ids in this monitor's tier
def scope_pnl(scope):
    total = 0.0
    for pos in cache.positions():
        if pos.strategy_id in scope.strategy_ids:
            pnl = pos.realized_pnl + pos.unrealized_pnl(last_price)
            total += fx_convert(pnl, pos.quote_ccy -> reporting_ccy)   # cross-currency aggregation
    return total + scope.cons_fill_delta            # conservative-fill consistency (existing cons bus)

This is a no-op for disjoint-instrument portfolios (same number as today) and required for shared ones. Higher tiers (tag, user) just use a larger strategy_ids set = the union of their children. Cross-currency conversion uses the existing FxRateResolver at each leg before summing at tag/user scope (ties into TBD-3; a no-op when everything is one currency).

6. The monitor tier & per-bar order

Use a single NEW HierarchyMonitorStrategy that owns all scopes and walks them top-down each bar (or keep per-scope monitors registered User→Tag→Portfolio). Top-down + a per-bar squared guard gives the spec's "higher force-squares lower, same bar":

on_bar(bar):
    squared = set()                                  # scopes closed this bar

    # 1) USER ceiling
    if user.enabled and breach(scope_pnl(user)) and held(user.delay):
        fire(user_bus); squared |= user.legs; return # everything below is moot this bar

    # 2) TAG tier
    for tag in tags:
        if tag.legs & squared: continue
        if breach(scope_pnl(tag)) and held(tag.delay):
            fire(tag_bus[tag]); squared |= tag.legs

    # 3) PORTFOLIO tier  (this is today's PortfolioMonitor, unchanged per portfolio)
    for pf in portfolios:
        if pf.legs & squared: continue
        evaluate_portfolio(pf)        # Combined Loss/Profit, trailing, underlying, agg Move-SL,
                                      # Hit-On-Leg, SqOff/ReExecute, AND cross-pf actions (sec.8)

    # 4) LEG level runs in each leg's own on_bar (after the monitor) — unchanged

Registration order guarantees same-bar delivery: the monitor(s) are added to the engine before the legs, so the engine calls monitor on_bar first (publish) then each leg on_bar (consume) — the exact pattern the single-portfolio engine already relies on.

8. Cross-portfolio actions — the detail

When portfolio A's monitor breaches with a cross-pf action targeting B, the effect must land on B the same bar. Because all portfolios live in one engine, this is just a same-bar bus drain:

# PfMonitor A, on breach (after §5.3 Delay hold, capped by ReExecute Count):
for action in A.sl_actions + A.tgt_actions:
    if action.is_local:           # "SqOff" / "ReExecute" on A itself
        fire(pf_bus[A], action)                    # A's own legs (today's behaviour)
    if action.target_portfolio:   # cross-pf
        cross_pf_bus[action.target].append(
            {verb: action.verb, ts: bar.ts, source: A, idem: (A, action.verb, bar.ts)})

# Legs of B, same bar (their on_bar runs after the monitors):
for evt in cross_pf_bus[B]:
    if evt.ts != this_bar or evt.idem in B.seen: continue   # idempotent, once per (source,verb,bar)
    if B.legs & squared_this_bar: continue                  # a higher tier already closed B -> skip
    B.seen.add(evt.idem)
    if   evt.verb == "sqoff":   leg._force_portfolio_sl_close()        # close B now
    elif evt.verb == "execute": leg._armed_for_entry = True           # B takes its entry signal now
    elif evt.verb == "start":   leg._started = True; leg._triggered_manual = True  # start manual B

Verb semantics (spec §5.2)

VerbLive effect on target BReuses
SqOff Other PortfolioForce-close all of B's legs at this bar (same as a portfolio SqOff)_force_portfolio_sl_close
Execute Other PortfolioArm B's legs so they take their entry signal now (re-enter)_armed_for_entry (:2127-2133)
Start Other PortfolioStart a manual B (idle until triggered); B begins running and bypasses End-Time for that trigger cycle_triggered_manual + blocked flags
ReExecute Same ContractOptions / multi-contract — out of scope (degenerates to "at Entry Price" for single-instrument)—

Delay, Count, manual lifecycle, ordering

  • Delay (sec) — the §5.3 confirmation hold before the cross-pf event is published (reuse _delay_ok): A's breach must persist delay_sec, cleared if it reverses.
  • ReExecute Count — caps how many times A's action re-fires (reuse the monitor's trailing-reset fire counter / reexec_cap).
  • Manual portfolio lifecycle — manual=True portfolios are added to the engine but their legs start entry-blocked (_started=False); only a start/execute event activates them, setting _triggered_manual so they bypass end_blocked for that cycle (verbatim spec).
  • Precedence — the per-bar squared set means a User/Tag fire that already closed B suppresses a redundant cross-pf SqOff of B; the User/Tag ceiling always outranks a cross-pf start.
  • Loop guard — cross-pf events carry source + an idem key, processed once per (source, verb, bar); a global per-bar hop cap stops an A→B→A cascade from looping within a bar.
Why this is live per spec: A breaches → (Delay hold) → publish → B closes/arms/starts in the same on_bar. Nothing is deferred to a post-run pass or a later request — the exact gap the compliance report flagged on today's "drained next-request" bus.

9. User & Tag limits

The UserMonitor and each TagMonitor are the same position-less monitor, scoped to their legs (§5). They reuse the existing SL/Target logic verbatim:

LimitMechanismReuses
Max Loss / Max ProfitCombined scope P&L ≤ −maxLoss / ≥ maxProfit → fire scope bus → all scope legs closemonitor Combined-Loss/Profit path
Trailing SLTighten-only ratchet on the scope loss-limit as scope profit growsthe portfolio Trailing-SL ratchet
Trailing Target / Profit-LockActivate at reach, lock lock, ratchet by by per everyadvance_trailing_target

Because P&L is read live from the engine cache, the obsolete module-global users.py/tags.py accumulators (the "never reset in production" bug) are deleted, not extended.

10. % of allocation

User/Tag thresholds entered as "% of allocation" resolve against SessionConfig.allocation_base — an engine constant fixed at session start, not affected by intraday PnL, fund add/withdraw, or exchange margin (spec Level-3 rule). Resolved once at session build:

user_max_loss_currency = allocation_base * (pct/100)   if pct-mode else absolute

Leg/portfolio raw-% stays as-is (still open per TBD-6); only the user/tag tiers get the fixed-base % per the resolved spec decision.

11. Hierarchy validation (Σ-of-siblings)

With the whole tree in one SessionConfig, the save/run validator can finally sum siblings (today it can't — it sees one portfolio):

assert Σ(leg SL within a portfolio)   ≤ portfolio SL        # per portfolio
assert Σ(portfolio SL within a tag)   ≤ tag SL              # per tag
assert Σ(tag SL)                      ≤ user SL             # session
# same chain mirrored for Target.  Block save (or warn+clip) on violation (spec §11).

(Leg SL is a price-distance trigger, not a currency budget — so the leg→portfolio rung stays a documented exception unless leg SLs are first converted to a worst-case currency loss; the portfolio→tag→user rungs are exact.)

12. Shared-resource fixes (mandatory, or single-portfolio regresses)

These are the two places where naive co-location of portfolios would silently break today's behaviour. Both must land in Phase 0.

12.1 ConservativeFillModel — re-key the pin per leg FIX

Today the model is one per venue, bound to a single portfolio_id, and the pin is keyed by instrument (conservative_fill_model.py:61-65; pins at managed_strategy.py:1506,1925). Breakages with multiple portfolios:

  • Two portfolios sharing a venue → the single model reads only one portfolio's bus → the other's conservative/directional fills are silently lost.
  • Two legs on the same instrument firing the same bar → pin collision (a latent issue even today).

Fix: a session-scoped fill bus, with the pin keyed by the leg's order_tag/strategy_id. The model already receives the order in get_orderbook_for_fill_simulation, so it resolves the leg identity from the order's tag/strategy. This also hardens single-portfolio.

12.2 Monitor P&L — scope by strategy_id FIX

Replace Σ Portfolio.total_pnl(instrument) with Σ over positions whose strategy_id ∈ scope (§5). No-op for disjoint instruments, required for shared.

12.3 Namespacing + per-monitor context FIX

  • order_id_tag must be globally unique across all portfolios (P{p}-U{i}), or NETTING position keys collide.
  • Each PfMonitor gets its own underlying_bar_type (its primary slot), day_tz, and scope — automatic if each portfolio keeps its own monitor instance.

13. Correctness & the parity gate

Invariant checklist (Phase 0 must hold all):

  1. Per-portfolio monitor scope = exactly that portfolio's legs.
  2. Buses stay portfolio_id-keyed (already true) → P2 can't touch P1.
  3. Fill pin keyed per-leg; fill bus session-scoped (§12.1).
  4. Monitor P&L scoped by strategy_id (§12.2).
  5. Globally-unique order_id_tag.
  6. Cross-pf events idempotent + loop-guarded; squared guard enforces top-down precedence.
The proof mechanism — a parity gate. For every build: run each portfolio standalone and again inside the multi-portfolio session (with no user/tag/cross-pf limits configured); assert the orderbook + per-portfolio P&L are byte-identical. This is how we guarantee leg- and portfolio-level SL/Target/Move-SL/trailing/actions are untouched. Model it on enforce_parity_test.py.

14. Unified engine + BacktestNode

All new pieces (tier monitors, tag_bus/user_bus, cross-pf drain, re-keyed fill pin) are attached in the shared post-branch code (unified/__init__.py:489-562) — the same place today's monitor + legs are attached. So the BacktestNode path inherits multi-portfolio with zero extra work, preserving the verified Unified≡Node equivalence. The session fill model still rides through ImportableFillModelConfig (now carrying a session id + per-leg keying).
