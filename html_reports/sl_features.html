Currency rule (current): INR ₹ for Indian Index Futures only. USD $ for everything else (US Index Futures, FX, Commodity, Crypto). See TBD-3 for the proposed flexible multi-currency model.
Per-asset-class customization: Most features now run uniformly across IF, FX, CF, XF. With the underlying-defaults-to-self model (see Underlying Definition below), even Underlying-based SL/Target apply universally. The applicability matrix in each section shows where each feature applies.
Data formats supported (all apply to both SL and Target):
  • Format A — Bid/Ask (bid OHLC + ask OHLC; bid_vwap, ask_vwap, mid_vwap; mark_price for crypto)
  • Format B — OHLCV (OHLC + volume; running volume-weighted vwap; ltp = close; mark_price for crypto)
  • Format C — LTP (Last Traded Price) (single last-trade price per bar; mark_price for crypto)
See execution_logic.html and execution_logic_target.html for per-format trigger/fill formulas.

Hierarchy structure

The engine evaluates SL/Target across four nested levels every bar. A higher-level limit that fires force-squares all lower-level entities under it in the same bar.

Level 1 — Leg

Level 2 — Portfolio

Level 3 — User

Evaluation order per bar: User → Portfolio → Leg. Higher level fires first; force-squares everything below.

Underlying Definition

Underlying-based SL/Target — one-line explanation: Portfolio-level safety guard that fires on the underlying instrument's price movement rather than aggregate PnL. Intended as a fail-safe for multi-leg strategies where sum of individual leg SLs may exceed the portfolio SL, OR individual leg targets may be tighter than the portfolio target. The underlying guard catches that by exiting on a price-level basis regardless of how the PnL is aggregating.

Default — self-referential

Underlying price = the instrument's own price. The futures contract is its own underlying; the spot symbol is its own underlying. Makes Underlying-based features universally available without requiring separate data feeds.

Optional — separate spot data (parked, see TBD-5)

When spot data is available for an instrument, the user may pin the underlying to a separate spot reference:

Open Decisions — TBD

TBD-1 · Safety Seconds semantics ✓ Resolved

Anchor: the time of the triggering decision event itself, NOT market open. Example: when Move SL to Cost fires at 11:43:00 and Safety Seconds = 60, the move actually applies at 11:44:00.

This generalizes Safety Seconds beyond the original NSE-09:15 model and applies uniformly to all asset classes — FX, Commodity, Crypto included, because events can happen anytime of day (24/7 markets, US/CME session boundaries).

Engine requirements:

  • Log timestamps of every decision/trigger event with sub-second precision (or matching the data resolution being used).
  • Safety Seconds is measured between event_time and now.

Data resolution requirement: Works correctly only with 1-second or finer resolution data. On 1-minute bars, Safety Seconds < 60 effectively rounds up to the next bar — sub-minute resolution is unenforceable. Adapter must surface a data_resolution field; engine refuses to enforce Safety Seconds < bar size and logs a warning.

TBD-2 · Tick-size enforcement for SL / Target trigger prices ✓ Resolved

Decision: option (a) — accept the calculated SL/Target value as-is. Do NOT snap to the instrument tick at monitoring time.

Rationale:

  • The engine fires MARKET orders for SL/Target exits (Exit Order Type = MARKET; Limit/SL_Limit not implemented).
  • For market orders, the broker handles tick alignment at fill time — engine-side tick enforcement is unnecessary.
  • For monitoring/trigger, an SL stored at 108.54 vs the nearest tick 108.55 practically fires together — price has to cross both anyway. Snapping adds no precision benefit.
  • Snapping WOULD matter if the engine fired Limit / SL_Limit orders. If those order types are added later, revisit.

Worked example:

entry_price = 100.5
Stoploss Type = Premium, Value = 8%
→ sl_pending_val = 100.5 × 1.08 = 108.54 (kept as-is)
→ trigger checks against 108.54 directly
→ exit fires market order; broker fills at next valid tick

Tick metadata remains in the per-instrument table for UI display, future limit-order support, and slippage modeling.

TBD-3 · Multi-currency support Parked

Current rule: binary INR (Indian Index Futures only) / USD (everything else).

Proposed: three-layer flexible currency model.

  • (i) Exchange-derived default — each instrument's settlement currency from per-instrument metadata. Examples: NSE → INR, CME → USD, EUREX → EUR, JPX → JPY, KRX → KRW, HKEX → HKD, SSE → CNY. Indian crypto exchanges → INR; offshore crypto → USD/USDT.
  • (ii) Per-portfolio override — user can pin a portfolio to a custom currency. Engine applies FX conversion at exit.
  • (iii) User-level reporting currency — required for aggregating cross-currency PnL into a single Max Loss / Max Profit.

Open sub-decisions:

  • FX conversion source — live rate / start-of-day / entry-time
  • UI symbol — becomes per-instrument (₹ / $ / € / ¥ / £ / ₩ / HK$ / CNY) once flexible currency is implemented.

Status: parked.

TBD-4 · Lot size update mechanism Parked

Indian index F&O lot sizes are revised periodically by NSE based on contract-value bands. NIFTY-FUT and BANKNIFTY-FUT are the most commonly affected. Static hardcoded lot sizes drift out of date and silently break PnL calculations.

Proposed approaches:

  • (i) Automated script — pulls lot sizes from NSE F&O master file (publicly available CSV / API) on a daily schedule. Updates per-instrument metadata automatically.
  • (ii) Manual override — admin UI to update lot sizes when notified by exchange. Audit-logged.
  • (iii) Hybrid (recommended) — script runs daily, detects changes, sends notification to admin who confirms before applying.

Additional consideration: Backtests over periods spanning a lot-size change need a lot-size history (effective dates), not just current values. Live trading needs current lot size only.

Status: parked.

TBD-5 · User-selectable underlying reference (self / spot) Parked

Default: underlying = the instrument itself (works for all asset classes without external data — see Underlying Definition).

Proposed extension: when spot data is available for an instrument, the user can configure the portfolio to track the spot reference instead (e.g., NIFTY spot for NIFTY-FUT, BTC spot for BTC futures).

Blocker: spot data not yet procured for all instruments under scope. Procurement is feasible (NIFTY spot is free; BTC spot via crypto exchange APIs; commodity spot via XAU/USD vendors) but deferred until data layer is in place.

Status: parked.

TBD-6 · Threshold input mode — absolute vs % Open

Applies symmetrically to SL and Target. All threshold fields on both sides are affected:

SideThreshold fields currently accepting absolute or %
SLSL Value (leg + portfolio), Trailing SL every / by (portfolio + user), Move SL to Cost trail every / by, Max Loss (user)
TargetTarget Value (leg + portfolio), Trailing Target when_profit_reach / lock_min_profit / trail_every / trail_by (leg + portfolio + user), Max Profit (user)

Concern: % is risky in a multi-asset, multi-broker setting because it's ambiguous what the percentage references — available margin, strategy allocation, current funding state, exchange-side margin/leverage changes, etc. If the engine resolves the reference wrong, a small misinterpretation can cause silent failures.

Worked failure mode — SL side: User enters SL = 1% intending "1% of strategy allocation". Engine parses it against the wrong base (e.g., 1% of $1 = $0.01). User-level SL is breached on the first bar → engine force-squares all portfolios for that user → all running trades exit immediately, including unrelated profitable ones. Silent until the cascade exits.

Worked failure mode — Target side: User enters Target = 5% intending "5% of allocation". Engine parses against a tiny base → target is hit on the first bar at near-zero profit → portfolio force-sqoffs, then ReExecutes (if configured) → re-enters and exits again the next bar → loop burns the ReExecute count and racks up slippage/commission while the user thinks the strategy is "scalping". Silent — no obvious error, just degraded PnL.

Proposed resolution (preferred): Lock all SL and Target threshold fields (and Trailing SL, Trailing Target, MaxLoss, MaxProfit) to absolute values only. Drop % support entirely on both sides.

Alternative (if % is retained): Define % strictly as % of allocation, where "allocation" is an engine-defined constant set at strategy start and NOT affected by:

  • User actions (fund add / withdraw mid-day)
  • Exchange-side margin or leverage changes
  • Realized PnL accumulating during the session
  • Broker-specific available-margin reporting

Same base for SL and Target so the two sides remain comparable. Any change to the allocation base requires explicit reconfiguration, not silent rebasing.

Status: Open — decision required before launch. Default direction: absolute-only for both SL and Target.
