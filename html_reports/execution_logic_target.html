3. Adapter Contract

Identical to SL doc §3 — same Format A / B / C adapters. See execution_logic.html §3 for full field tables and VWAP definition.

Key fields summary

Format A — Bid/Ask

Exposes: bid OHLC, ask OHLC, bid_v, ask_v, bid_vwap, ask_vwap, mid_vwap, mark_price (crypto only).

Format B — OHLCV

Exposes: open/high/low/close, volume, vwap, ltp = close, mark_price (crypto only).

Format C — LTP

Exposes: ltp (Last Traded Price), timestamp, mark_price (crypto only).

VWAP (Formats A & B)

VWAP = (H + L + C) / 3 × candle_weight
candle_weight = volume of that candle / total aggregate volume for that day till that point in time

Mark Price (crypto only)

Exchange-published fair-value reference. Filters out manipulation via single-venue wicks. When adapter exposes mark_price, user may configure trigger/fill to reference it instead of bid/ask/LTP.

Volume caveat (default — currency & commodity): Volume is broker-dependent. VWAP still computes, but weights quote depth rather than executed flow for these asset classes.

4.2 Target Fill-Price Formula

Rule: SELL exits MAX(vwap, hit) — conservative; BUY exits MIN(vwap, hit) — conservative.

Format A

TGT — SELL:  exit = ask_vwap if ask_vwap > bid_low   else bid_low
TGT — BUY:   exit = bid_vwap if bid_vwap < ask_high  else ask_high

Format B

TGT — SELL:  exit = vwap if vwap > low   else low
TGT — BUY:   exit = vwap if vwap < high  else high

Format C

TGT — SELL:  exit = ltp
TGT — BUY:   exit = ltp

4.3 Target Wait / Delay

Same as SL doc §4.3. Shares delay_pending state with SL Wait.

4.4 Target Value Parsing

Same in all three formats

SELL leg:
    Premium with %:    tgt = entry × (1 - pct/100)
    Premium absolute:  tgt = entry - value

BUY leg:
    Premium with %:    tgt = entry × (1 + pct/100)
    Premium absolute:  tgt = entry + value

Type variants: None, Premium (alias: PremiumBased), AbsolutePremium, Underlying (not implemented at leg level — use portfolio level).

4.6 Leg Action Combination Rules

4.7 Leg-Level Trailing Target (NEW)

Same in all three formats — PnL-based profit-lock ratchet at leg level

# Activation:
if leg_pnl >= when_profit_reach:
    active = True
    current_stop = lock_min_profit
    anchor_pnl = when_profit_reach
    # log: LEG_TRAIL_TARGET_ACTIVATED

# Active phase (each bar):
if leg_pnl <= current_stop:
    exit leg (TARGET_TRAIL)
else:
    gain = leg_pnl - anchor_pnl
    if gain >= trail_every:
        steps = int(gain / trail_every)
        current_stop += steps × trail_by
        anchor_pnl += steps × trail_every
        # log: LEG_TRAIL_TARGET_UPDATED

Fields: enabled, when_profit_reach, lock_min_profit, trail_every, trail_by. All accept absolute or % input.

Parallel to Trail After Move SL on the SL side — see SL doc §4.6.

6. User-Level Target Execution

combined_pnl = Σ state["pnl"]["combined"] for state owned by uid

# Max Profit
if max_profit != 0 and combined_pnl >= max_profit:
    force_sqoff all user portfolios
    gst["hit"] = True       # GLOBAL_MAX_PROFIT_HIT

Order: Max Loss checked first (SL doc §6), then Max Profit. gst["hit"] sticky for the rest of the day.

7. ReExecute Gating Flags

Same four flags as SL doc §7

The flags apply to Target re-executions identically — they don't distinguish whether the underlying hit was SL or Target.

FlagDefaultBlocks
no_reexec_sl_costOFFRe-Execute action when leg["sl_moved_to_cost"] == True
no_wait_trade_reexecOFFPer-leg Wait & Trade delay on re-executions (detected via exec_count >= 1)
no_reentry_after_endOFFBoth Re-Execute and ReEntry past Portfolio End Time
no_reentry_sl_costONReEntry action when leg["sl_moved_to_cost"] == True

Even though the flag names reference "SL cost" (the sl_moved_to_cost flag set by Move SL to Cost), the gating applies to any re-execution attempt on that leg regardless of which event fires it (SL hit or Target hit). See SL doc §7 for full dispatch logic and flag interactions.

Same in all three formats

Three time fields control when Target-related entries and exits are permitted.

Start TimeEarliest bar for any leg entry
End TimeCutoff for new entries (including Target-triggered re-executions if no_reentry_after_end is ON). Open positions continue under SL/Target monitoring until SqOff Time.

if end_blocked and not _triggered_manual:
    skip — block IDLE leg entries

Winter Time Adjustment

Applies for US-listed instruments where the data source and strategy configuration may straddle DST boundaries.

AssetWinter adjustment applies
NIFTY-FUT (NSE), BANKNIFTY-FUT, NSE stocks❌ No — India doesn't observe DST
US Index Spot (SPY), US stocks✅ Yes
Commodity futures, FX futures, Crypto futures (US-listed)✅ Yes
Crypto spot (24/7)⚠️ Depends on user's configured-time timezone

When is_winter = True, the engine shifts raw configured times by +1 hour via add_one_hour() before applying:

_raw_ls = parse_time_str(leg["conf"].get("Start Time"))
if _raw_ls and timing.get("is_winter"):
    _raw_ls = add_one_hour(_raw_ls)
leg_start = _raw_ls or timing["start"]

For Indian-market instruments the flag should be a no-op (set is_winter = False in adapter init).

Validation rule

Portfolio Start ≤ Leg Start ≤ Portfolio End ≤ SqOff Time (enforced on save).

11. Portfolio Tags — Feature Request (To Be Added)

Hierarchy clarification

Different legs make up a strategy → strategies combine into a portfolio → portfolios belong to a user (algo).

Target is currently defined at three levels:

  • Leg level (§4)
  • Portfolio level (§5)
  • User level (§6)

Request

Add Portfolio Tags (also called Strategy Tags) as a way to group portfolios so that SL/Target can be assigned to a subset of strategies — between Portfolio and User in the evaluation hierarchy.

A portfolio tag groups multiple portfolios sharing a common characteristic (e.g., strategy type, market regime, time-of-day window). Each tag has its own SL/Target. When a tag's Target fires, all portfolios in that tag are force-sqoff'd; portfolios in other tags continue unaffected. User-level Target remains the ultimate ceiling.

Example

User runs 100 strategies (= 1 algo)
User-level SL  = ₹1,00,000

Divide the 100 strategies into 5 strategy tags of 20 each:
    Tag 1: 20 strategies — SL = ₹30,000
    Tag 2: 20 strategies — SL = ₹30,000
    Tag 3: 20 strategies — SL = ₹30,000
    Tag 4: 20 strategies — SL = ₹30,000
    Tag 5: 20 strategies — SL = ₹30,000

Concrete grouping example:
    Of the 100 strategies, 10 are of type "non-trending".
    To limit/fix loss on that type specifically, define a
    "non-trending" strategy tag and assign it its own SL
    (e.g., ₹30,000). When the tag SL fires, only those 10
    strategies are squared off — the other 90 keep running.

The same grouping mechanism applies for Target — each tag has its own target, fires when reached, closes only its own portfolios.

Validation rule (required when implemented)

When SL/Target is defined at the leg level, the engine must verify it does not breach the SL/Target assigned at higher levels:

  • Sum of leg-level SLs within a portfolio ≤ portfolio SL
  • Sum of portfolio SLs within a tag ≤ tag SL
  • Sum of tag SLs ≤ user SL

If a leg-level SL/Target would violate the parent strategy / portfolio / tag / user limit, the engine should flag this on config save and prevent the run (or warn and clip the leg-level limit to fit). Same check applies for Target on the upper side.
