Sync squareoff time across UI tabs; align two default portfolios to US market hours

Report generated 2026-05-23 06:19 UTC

Plain English

What this change does, for a non-technical reader.

The team ran a backtest and found that two saved portfolio configurations had inconsistent and mismatched end-of-day close settings. Both portfolios were reconfigured to use 4:15 PM UTC as the daily squareoff (forced close) time, replacing a mix of 9:00 PM and 3:15 PM India-time values that had been left over from earlier setup. The trading entry window was also tightened to 9:30 AM – 4:15 PM UTC, more closely matching standard US equity market hours.

Separately, a usability bug in the portfolio settings editor was fixed. The squareoff time appeared in two places in the editor — on the "Execution Parameters" tab and on the "Timing" tab — but changing one did not update the other, making it easy to accidentally run a backtest with mismatched values. Now both fields are kept automatically in sync: editing either one immediately updates the other.

A small explanatory note was also added to the editor to let users know these two fields are linked, and tooltip text on both fields was updated to describe the relationship.

Technical / Engineering

Implementation detail and impact, for engineers.

The main new logic is `_bindSqoffMirror()` in `static/js/portfolio.js` (~60 lines), called once per modal open at the end of `_openEditModal`. It wires a two-way live sync between `#pf-m-mis-sqoff` / `#pf-m-mis-sqofftz` (Execution Parameters tab) and `#pf-m-sqoff` / `#pf-m-sqofftz` (Timing tab).

On open, the method reconciles the two pairs to a single coherent (time, tz) source rather than mixing them. The Timing-tab value wins when set — matching backend precedence in `core/models.py` where `squareoff_time` overrides `mis_squareoff_time`. If the Timing tab is empty, it falls back to the MIS value. A `setVal` helper handles the asymmetry that `mis_squareoff_tz` is a free-text `<input>` while `squareoff_tz` is a `<select>`: it dynamically inserts an `<option>` if the IANA zone string typed in the free-text field isn't already in the dropdown, so arbitrary zones survive the round-trip. Event listeners use `"change"` for `<select>` and `"input"` for time/text inputs. `_toggleMisRow()` was extended to also show/hide the new `#pf-mis-sqoff-note` paragraph.

The two portfolio JSON files were re-saved after running a backtest through the UI. Substantive changes: `squareoff_time` set to `"16:15"` + `squareoff_tz: "UTC"` on both (EDGE_14 had `"21:00"` with no tz; EDGE_01 had nulls); `entry_start_time` / `entry_end_time` switched from `"06:00"/"20:00"` and nulls to `"09:30:00"/"16:15:00"` (note the format also changed from `HH:MM` to `HH:MM:SS`); and RBO monitoring window fields were populated from null to `09:30:00–10:30:00` / `10:30:00–16:15:00` even though `rbo_enabled` remains false. The widespread `0.0 → 0` changes are cosmetic: Python's `json.dump` serialises integer-valued floats as integers after a round-trip through the save path.

Risks & Follow-ups

  • RBO window times were populated (09:30–16:15) in both portfolios even though rbo_enabled is false — these will silently activate if RBO is later toggled on; verify this is intentional.
  • entry_start_time / entry_end_time format changed from 'HH:MM' to 'HH:MM:SS' — confirm the backend time-filter parser in backtest_runner.py handles both formats without regression.
  • On modal open, _bindSqoffMirror reconciles by silently overwriting the MIS fields with the Timing-tab value whenever the Timing tab is non-empty — users who previously edited only the MIS side will see their value replaced on next open with no warning.
  • EDGE_14 previously had mis_squareoff_tz: null; the mirror logic defaults this to 'UTC' on reconcile — verify UTC is the intended timezone for that portfolio's squareoff.
  • No automated test covers the new JS mirror logic; a regression to either field being updated without syncing the other would be silent.
