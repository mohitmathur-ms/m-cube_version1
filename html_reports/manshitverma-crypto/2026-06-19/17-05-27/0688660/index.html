Plain English

What this change does, for a non-technical reader.

Previously, when the system's combined-profit guardrail fired during a backtest, it always used a one-and-done rule: once the portfolio hit its profit target for the entire run, it stopped trading for good. This push gives that rule a new option — it can instead reset each day, just like the combined-loss guardrail already does, letting the portfolio resume trading the next morning after a profitable day.

Five sample portfolio configurations used for internal testing were also updated. They now specify a trading window (entries only allowed between 4:00 AM and roughly 10:45 AM), which better reflects realistic intraday trading hours. One portfolio was also switched from Ethereum on Coinbase to Bitcoin on Binance, and another had its date range and product type corrected to match more useful historical data.

The session window for the Nifty Futures market data adapter was extended from ending at 1:44 PM to 7:14 PM, which means the system now recognizes a longer tradeable session for that market.

Technical / Engineering

Implementation detail and impact, for engineers.

The core change is in `core/portfolio_monitor.py`: `PortfolioMonitorConfig` gains a new frozen field `tgt_day_scoped: bool = True`. The `_eval_side` call on the profit-target branch now reads `day_scoped=bool(self.config.tgt_day_scoped)` instead of the previously hardcoded `day_scoped=False`. This means the default behavior flips: the combined-profit target is now day-scoped (resets daily, fires once per day, blocks re-entry until next session) unless the caller explicitly sets `tgt_day_scoped=False`.

To preserve the original absolute semantic for tag/user-tier caps, `core/backtest_runner/unified/__init__.py` passes `tgt_day_scoped=False` explicitly when constructing the `PortfolioMonitorConfig` for that tier. This is the only callsite changed, so all other callers (which don't set the field) now get day-scoped behavior by default — a behavioral change for any portfolio that relies on a combined-profit cap.

Five portfolio JSON fixtures under `portfolios/_default/` were updated: all gained `entry_start_time`/`entry_end_time`/`entry_window_overnight` fields (trading window 04:00–10:45 UTC or 04:00–09:45); `PFCP_REEXEC` swapped its second slot from ETHUSD.COINBASE_MS to BTCUSD.BINANCE_MS (including the aggregated bar type string); `PFCP_SQOFF` changed backtest dates (2026-01 → 2025-01/2025-06), added a 18:29 UTC squareoff, changed product from NRML to MIS, and reduced `pf_tgt_value` from 100 to 10. `PFCL_REEXEC` also adjusted EMA periods from (50/100) to (10/20) on its second slot.

The `nifty_futures_ms.json` adapter config's `session_end_time` was extended from `13:44:00` to `19:14:00`, affecting what bars the system considers within the tradeable session for that venue.

Worked Example

A concrete illustration of the most significant change.

Before this push, the profit-target path in PortfolioMonitorStrategy was always absolute:

# Old code (hardcoded) self._eval_side(ts, pnl, is_loss=False, side="tgt", day_scoped=False, ...)

After the push it reads the new config field:

# New code self._eval_side(ts, pnl, is_loss=False, side="tgt", day_scoped=bool(self.config.tgt_day_scoped), ...)

For a portfolio with `pf_tgt_value=100` and the default `tgt_day_scoped=True`: if combined P&L hits $100 on Monday, the portfolio squares off for the rest of Monday but resumes on Tuesday — matching the day-scoped SL semantics. For the tag/user tier, the unified runner passes `tgt_day_scoped=False` explicitly, preserving the old one-shot absolute behaviour.

Risks & Follow-ups

  • Default flip risk: tgt_day_scoped now defaults to True, which changes runtime behavior for any existing portfolio that previously relied on the absolute (rest-of-run) profit-target semantic without explicitly setting the field — the portfolio will now resume trading the next day after hitting its target.
  • The only callsite that sets tgt_day_scoped=False is the unified runner's tag/user-tier path; callers using PortfolioMonitorConfig directly (e.g. tests, portfolio_monitor skeleton) silently inherit the new day-scoped default.
  • PFCP_SQOFF.json's pf_tgt_value was reduced from 100 to 10 — may cause this verification portfolio to trigger its combined-profit cap much more aggressively, potentially masking test failures that were previously only visible above $100.
  • PFCP_REEXEC slot B instrument change (ETHUSD→BTCUSD/BINANCE_MS) means the catalog must have BTCUSD.BINANCE_MS data for this fixture to run without a data-not-found error.
  • nifty_futures_ms.json session end extension to 19:14 should be verified against actual exchange hours; an overly wide session window can admit stale or illiquid bars in the backtest.
