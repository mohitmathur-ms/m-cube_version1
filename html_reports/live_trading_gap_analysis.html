0Bottom line up front

Good news — your most valuable code already runs in live, unchanged.
NautilusTrader is designed so the same Strategy class runs in both backtest and live. That means your entry strategies (strategies/, L1) and your entire exit engine — SL/TP/trailing/square-off/RBO in core/managed_strategy.py (L2) — port to live without rewriting the trading logic.
The work — a new execution subsystem (L4), not a tweak.
Backtesting runs many short-lived BacktestEngine processes via a ProcessPoolExecutor. Live trading is a single, long-lived async process (TradingNode) holding open websocket + broker connections. None of core/backtest_runner.py's per-slot / grouping / Path-B orchestration applies to live. This is a new module, not an edit to an existing one.
REUSABLE

Signals, exit state machine, RBO, portfolio SL/TP logic, models, venue/instrument config, the Admin panel's credential storage & masking.

REFACTOR

One coupling point: ManagedExitStrategy._submit_order() calls Nautilus order APIs directly — fine, but the surrounding orchestration must change.

BUILD NEW

The L4 live runner (TradingNode launcher), real-time process lifecycle, reconciliation/persistence, and live monitoring UI + endpoints.

Recommended first milestone: SANDBOX (paper) trading.
Nautilus ships a SANDBOX execution client that takes real live market data but fills orders on its own simulated matching engine — the same fill model your backtests already use. This de-risks the entire effort: you prove the live data feed, the node lifecycle, and the strategy wiring before a single real order or real API secret touches an exchange.

2The Nautilus promise: what transfers for free

Nautilus's headline guarantee is backtest/live parity: a Strategy subclass that submits orders via self.order_factory.market(...) / self.submit_order(...) behaves identically whether an engine is feeding it historical bars or a live client is feeding it real ticks. Your exit engine already uses exactly these native APIs:

# core/managed_strategy.py — _submit_order() (already live-compatible)
order = self.order_factory.market(
    instrument_id=self.config.instrument_id,
    order_side=side,
    quantity=self.instrument.make_qty(self.config.trade_size),
    time_in_force=TimeInForce.GTC,
)
self.submit_order(order)   # identical call path in backtest AND live
What this means concretely
Your SL/TP/trailing logic, the RBO range-breakout machine, target-lock, and per-leg/slot/portfolio square-off precedence all evaluate on on_bar the same way live. You do not reimplement trading logic for live — you give it a live data feed and a live execution client, and host it inside a TradingNode instead of a BacktestEngine.

Caveat worth stating to stakeholders: parity is on logic, not outcomes. Backtest fills are deterministic from OHLCV; live fills bring real slippage, partial fills, rejections, latency and queue position. The code is the same; the market is not.

3Backtest engine vs. live TradingNode

Today — Backtest

  • Many short processes. One BacktestEngine per slot in a ProcessPoolExecutor.
  • Synchronous. Bars replayed start→end, then the process exits.
  • Test clock. Time is driven by the data.
  • Data = catalog. Parquet bars loaded up front.
  • No credentials. No network, no auth, no fills from a real venue.
  • State is disposable. Results extracted, process torn down.

Target — Live / Sandbox

  • One long-lived process. A single TradingNode running an asyncio event loop.
  • Asynchronous. Reacts to streamed ticks/bars + broker events indefinitely.
  • Real-time clock. Time is wall-clock.
  • Data = live client. Websocket subscriptions (e.g. Binance, IB).
  • Credentials required. API key/secret or IB Gateway connection per venue.
  • State must persist & reconcile. Cache (optionally Redis), order/position reconciliation on startup.

4The one real refactor: order submission

The exit state machine is logically pure, but it is physically coupled to Nautilus's in-strategy order APIs (self.order_factory, self.submit_order). For a live node that coupling is actually fine — those same APIs exist on a live strategy. So strictly, no rewrite is required to run the strategy live.

The decision point is whether you also want a thin submitter abstraction so the same state machine can be unit-tested and driven outside an engine. If yes, inject an interface:

# Optional hardening — not required for parity, but improves testability
class OrderSubmitter(Protocol):
    def submit(self, side, qty, *, tags): ...

# ManagedExitStrategy keeps using self.submit_order in live;
# the abstraction only matters if you want to drive the FSM in isolation.
Scope guard
Do not treat "decouple the strategy" as a prerequisite for live. It is a nice-to-have. The critical-path work is the L4 node launcher + lifecycle + reconciliation, not refactoring proven exit logic.

6Adapter Admin: ready vs. missing

The Admin panel (adapter_admin/admin_server.py, port 5001) is already most of the way to a live control plane. It discovers Nautilus adapters at runtime (adapter_discovery.py introspects LiveDataClientConfig / LiveExecClientConfig fields via msgspec), stores per-venue configs, masks secrets, and even runs a live credential test. 7UI fields that "wake up" in live

The portfolio editor (static/js/portfolio.js) already marks fields that are stored but inert in backtest. pf-live-only (gray) fields are precisely the controls that become meaningful once L4 exists. They are documented in LOGICS_BACKEND_STATUS.md. Highlights:

Field / tabMeaning in liveWhy inert in backtest
strategy_tagBroker-side order grouping / risk tierBacktest never routes to a broker
on_leg_failWhat to do when a broker rejects a leg (keep / cancel placed legs)Backtest orders never get rejected
Monitoring tab: leg/combined *_monitoringReal-time vs minute-close vs interval evaluation cadenceBacktest evaluates every bar deterministically
exit_order_type = LIMIT / SL_LIMITReal limit/stop-limit exit ordersOnly MARKET is wired today
product = MIS / NRML, mis_squareoff_*Intraday auto-square-off vs overnight at the brokerBacktest treats MIS as a default squareoff only
on_portfolio_complete / cross-portfolio targetsSquare-off / start another live portfolioOnly "None" wired; needs a live orchestrator
Many of these are options-trading semantics (strike rounding, based_on, combined-premium mode) inherited from the BTSoftware design target — for FX/crypto live they remain no-ops. Don't scope them into the first live release; the "wake-up" set that actually matters for FX/crypto is: order rejection handling, monitoring cadence, limit exit orders, and MIS/NRML square-off.

8Verified TradingNode skeleton

Class & method names below were confirmed against the installed nautilus_trader==1.224.0 package (nautilus_trader/live/node.py, live/config.py, adapters/sandbox/, adapters/binance/). Treat this as the shape of the new core/live_trader.py, not copy-paste-final.

from nautilus_trader.live.node import TradingNode
from nautilus_trader.live.config import TradingNodeConfig, LiveExecEngineConfig
from nautilus_trader.config import InstrumentProviderConfig, LoggingConfig, CacheConfig
from nautilus_trader.adapters.binance.factories import (
    BinanceLiveDataClientFactory, BinanceLiveExecClientFactory)
from nautilus_trader.adapters.binance.config import BinanceDataClientConfig, BinanceExecClientConfig
# Paper trading: real data in, simulated fills
from nautilus_trader.adapters.sandbox.config import SandboxExecutionClientConfig
from nautilus_trader.adapters.sandbox.factory import SandboxLiveExecClientFactory

config = TradingNodeConfig(
    trader_id="MCUBE-001",
    logging=LoggingConfig(log_level="INFO"),
    # Redis-backed cache for state persistence (optional but recommended live):
    cache=CacheConfig(#[ database=DatabaseConfig(...) ]),
    # Reconciliation: on startup, rebuild state from the venue. Node refuses
    # to start if reconciliation fails — this is a safety feature, keep it on.
    exec_engine=LiveExecEngineConfig(reconciliation=True),
    data_clients={
        "BINANCE": BinanceDataClientConfig(
            api_key=..., api_secret=..., testnet=True,
            instrument_provider=InstrumentProviderConfig(load_all=True),
        ),
    },
    exec_clients={
        # PHASE 1 (paper): SANDBOX fills on its own matching engine
        "BINANCE": SandboxExecutionClientConfig(
            venue="BINANCE", starting_balances=["10_000 USDT"],
            instrument_provider=InstrumentProviderConfig(load_all=True),
        ),
        # PHASE 3 (real): swap to BinanceExecClientConfig(api_key=..., ...)
    },
)

node = TradingNode(config=config)
node.add_data_client_factory("BINANCE", BinanceLiveDataClientFactory)
node.add_exec_client_factory("BINANCE", SandboxLiveExecClientFactory)   # or Binance factory for real
node.trader.add_strategy(my_managed_strategy)   # ← your existing L2 strategy, unchanged
node.build()
try:
    node.run()          # blocks: runs the asyncio event loop indefinitely
finally:
    node.dispose()      # graceful shutdown / connection teardown
The single most important line
node.trader.add_strategy(my_managed_strategy) — the strategy object is the same class you backtest with. Phase 1 → Phase 3 is one swap: SandboxLiveExecClientFactory → BinanceLiveExecClientFactory and the matching exec-client config. Everything above the exec client is identical.

9Operational concerns — the part that's actually hard

The strategy port is easy; running a live node safely is where the real engineering is. Budget for these:

Reconciliation

On startup the node queries the venue for open orders/positions and rebuilds internal state. If it can't reconcile, it won't start — by design. You must handle cold starts, externally-placed orders (EXTERNAL / external order claims), and mid-session restarts.

State persistence

Backtest state is disposable; live state is not. A crash mid-position must be recoverable. Plan a Redis-backed cache (CacheConfig + DatabaseConfig) and a MessageBusConfig so positions/orders survive a restart.

Async lifecycle & the Flask seam

node.run() blocks on an event loop. It cannot live inside a Flask request thread. The node runs as a separate supervised process/service; Flask sends start/stop/status commands to it (subprocess, queue, or a small control socket).

Disconnects & risk

Websocket drops, partial fills, rate limits, rejections are normal live. Configure LiveExecEngineConfig retries and a LiveRiskEngineConfig (max order rate, position limits) plus an explicit kill-switch.

Real-time clock

Square-off times, MIS auto-close, entry windows and RBO day boundaries now fire against wall-clock in a specific timezone. Verify TZ handling end-to-end — a backtest TZ bug is a wrong number; a live TZ bug is a missed square-off.

Secrets at rest

Configs currently store api_key/api_secret in plaintext JSON, masked only in transit. Before real money: move to env vars / a secrets store, add access control, and an audit trail. The Admin panel has no auth (X-User-Id is spoofable).

10Phased roadmap

● Phase 1 Paper/Sandbox ● Phase 2 Control plane & UI ● Phase 3 Real money (one venue) ● Phase 4 Harden & scale
Phase 1 · Sandbox / paper trading on live data prove the loop
Lowest risk. No real orders, no real secrets needed beyond read-only data keys.
  • New core/live_trader.py that builds a TradingNode with a live data client + SANDBOX exec client.
  • Feed one existing strategy slot live (e.g. Binance testnet data → EMA-cross + SL/TP).
  • Confirm bars stream, signals fire, sandbox fills occur, square-off triggers on wall-clock.
  • Run the node as a standalone script first — no Flask integration yet.
Phase 2 · Control plane & live monitoring make it operable
Wrap the node in start/stop/status; surface state in the Admin panel.
  • Run the node as a supervised subprocess/service; add POST /api/trading/start, /stop, GET /api/trading/status.
  • Live blotter page: open orders, positions, fills, balance, running PnL (poll the node's cache).
  • Map a saved portfolio → a set of live strategies on the node (reuse core/models).
  • Wire the genuinely-needed pf-live-only fields: on_leg_fail, monitoring cadence, MIS/NRML square-off.
Phase 3 · Real money, single venue go live, small
Swap SANDBOX → real exec client for ONE venue. Tiny size. Hands on the kill-switch.
  • Swap to BinanceLiveExecClientFactory (or IB) + real exec_config credentials.
  • Turn on reconciliation, Redis persistence, and LiveRiskEngineConfig limits.
  • Implement the kill-switch and disconnect/reconnect handling; alerting on rejects/errors.
  • Harden secrets at rest + Admin-panel auth before this phase ships.
Phase 4 · Harden & scale multi-venue, robust
Generalize beyond one venue; production reliability.
  • Add remaining adapters (IB FX/commodities, Bybit, custom) + connectivity tests for each.
  • Multi-venue / multi-portfolio nodes; per-user isolation.
  • Crash-recovery drills, reconciliation edge cases, partial-fill correctness, latency/slippage reporting.
  • Cross-portfolio actions & remaining monitoring semantics if business needs them.

One-paragraph summary for stakeholders
Backtesting is done. Live trading reuses ~80% of what exists — every strategy and the entire exit engine run unchanged on a NautilusTrader TradingNode, and the Admin panel already stores broker credentials and configs. The new work is a single live-execution module plus the operational scaffolding around it: real-time process lifecycle, state persistence/reconciliation, monitoring UI, and secrets hardening. The safe path is to ship paper trading on live data (SANDBOX) first, then flip a single exec-client factory to go real on one venue with tiny size and a kill-switch.
