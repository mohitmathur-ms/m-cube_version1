1. The reported symptom

Running portfolio portfolios/_default/FX_9_Slot_2024.json (9 enabled slots) produced an HTML report whose header read:

| 113 trades | 3 Portfolios | 2024-01-01 to 2024-12-31

The Portfolio Filter dropdown listed only three entries:

  • Bollinger_Bands_on_GBPUSD_SL_0.5_TP_1_
  • EMA_Cross_on_GBPUSD_SL_0.5_TP_1_
  • RSI_Mean_Reversion_on_GBPUSD_SL_0.5_TP_1_

And the CSVs in reports/_default/ (all dated 20-May-2026, 16:39) showed inconsistent counts across files. The question was: are 6 slots being silently dropped? and if not, why don’t I see them?

3. Two separate issues uncovered

Issue A — mis-labeled slot IDs in the portfolio JSON data issue

The JSON file at portfolios/_default/FX_9_Slot_2024.json has nine slots whose slot_id values suggest three instruments — fx_eur_*, fx_gbp_*, fx_jpy_* — but the bar_type_str field on every slot currently reads GBPUSD.FOREX_MS-1-MINUTE-BID-EXTERNAL. So the IDs lie about what the slot trades.

(This is purely a data discrepancy in the saved portfolio — out of scope for this fix; we left the JSON untouched.)

Issue B — report generation overwrites duplicate-config slots code bug

This is the real bug. Even if all 9 slots had been truly distinct (e.g. three real instruments × three real strategies), if any two of them produced the same display_name, the second slot’s data would silently overwrite the first’s in the order book CSV and HTML report. This is the bug we fixed.

4. Root cause — the overwriting bug

In server.py, after the portfolio engine runs, results are reshaped for the report generator:

# server.py, around line 1490 (before the fix)
for slot_id, sr in per_strat.items():
    strat_label = sanitize_filename(sr["display_name"])
    …
    all_results_for_reports[strat_label] = { … }

The key strat_label is built from display_name, which is defined in core/models.py:177:

# core/models.py
@property
def display_name(self) -> str:
    instrument = self.bar_type_str.split(".")[0] if self.bar_type_str else "N/A"
    sl_desc = f" | SL: {self.exit_config.stop_loss_value}%" if … else ""
    tp_desc = f" | TP: {self.exit_config.target_value}%"   if … else ""
    return f"{self.strategy_name} on {instrument}{sl_desc}{tp_desc}"

display_name deliberately omits slot_id. When three slots share strategy_name + instrument + SL + TP, all three produce the same key. The dict overwrites; only the last write survives. Downstream consequences:

  • core/report_generator.py at line 235 iterates for strategy_name, results in all_results.items() and writes strategy_name into the PORTFOLIO NAME and STRATEGY columns of the order book CSV.
  • docs/report_template.html at line 1436 dedups the filter dropdown by PORTFOLIO NAME, and at line 1590 dedups the strategy-breakdown table by STRATEGY.

The merged position_report and order_fill_report CSVs were untouched by this bug because they are written before the loop above — that’s why we saw 452 positions but only 113 order-book rows.

Why the disagreement matters — any time someone cross-checks the HTML against the merged CSVs (which is exactly what triggered this investigation), the numbers disagree. The bug was silent: no error raised, no warning logged, just trades disappearing into a dict key collision.

5. Sidebar: netting vs hedging at the leg level

This came up during the discussion and is worth recording. The runner uses different OMS modes per execution path:

Execution pathOMS modeSource
Single-strategy backtestNETTINGbacktest_runner.py:2102
Portfolio per-slot (default)NETTINGbacktest_runner.py:2624
Portfolio grouped _USE_GROUPING=1HEDGINGbacktest_runner.py:3394
Portfolio Path B grouped _USE_BACKTEST_NODE=1HEDGINGbacktest_runner.py:3046

The HEDGING rationale is commented inline:

HEDGING (not NETTING) so each strategy’s positions are tracked independently. NETTING would merge all strategies’ orders on the same (venue, instrument) into a single position record — breaks per-strategy round-trip accounting.

For the FX_9_Slot_2024 run we investigated: grouping was off, so each slot lived in its own engine with NETTING. Within a single slot, BUY then SELL cancels out. Between slots, no interaction at all — slots are isolated by trader-id, which is why the position report can carry all 452 positions tagged with unique trader-ids.

6. Fix design — questions asked, choices made

Two clarifying questions were asked before writing the patch:

Q1 — How should the two label columns work?

Chosen: Same unique label in both PORTFOLIO NAME and STRATEGY. Format: {sanitize_filename(display_name)}__{slot_id}.

This was preferred over splitting the columns (unique in PORTFOLIO NAME, collapsed in STRATEGY) for simplicity. Both the filter dropdown and the strategy-breakdown table now show one row per slot, matching how the user wants to inspect the data.

Q2 — Should SLOT_ID also appear as its own CSV column?

Chosen: Yes. Adds a SLOT_ID column to the order book CSV so users can filter / pivot in Excel or pandas without parsing the composite label string.

What stayed off the table

  • display_name in models.py was not changed. It is also consumed by static/js/portfolio.js and static/js/portfolio_tearsheet.js for UI display; changing it would cascade.
  • No changes to how Nautilus StrategyId / trader_id are assigned in backtest_runner.py — that disambiguation already works correctly at the engine level.
  • The merged position_report / order_fill_report CSVs were already correct — left untouched.

7. The patch — what changed in which file

Change 1 — server.py (around line 1490–1518)

Make the per-slot dict key unique so duplicate-config slots do not overwrite each other. Also embed slot_id in the result payload so the report generator can write the new column.

strat_label = sanitize_filename(sr["display_name"])
base_label  = sanitize_filename(sr["display_name"])
strat_label = f"{base_label}__{slot_id}"
…
all_results_for_reports[strat_label] = {
    "slot_id": slot_id,
    "positions_report": slot_pos, "fills_report": slot_fills,
    …
}

Change 2 — core/report_generator.py (line 240, in _build_orderbook)

Read slot_id off the per-strategy result dict.

for strategy_name, results in all_results.items():
    positions_report = results.get("positions_report")
    if positions_report is None or positions_report.empty:
        continue
    slot_id = results.get("slot_id", "")
    fills_lookup = _build_fills_lookup(results.get("fills_report"))

Change 3 — core/report_generator.py (line 386, trade dict)

Emit the new column in every trade row.

trade = {
    …
    "PORTFOLIO NAME": strategy_name,
    "STRATEGY": strategy_name,
    "SLOT_ID": slot_id,
    "EXIT TIME": exit_time,
    …
}

Change 4 — core/report_generator.py (line 425, column_order)

Pin SLOT_ID’s position in the CSV right after STRATEGY.

column_order = [
    "USERID", "SYMBOL", "EXCHANGE", "TRANSACTION", "QUANTITY", "LOTS",
    "MULTIPLIER", "OrderID", "ENTRY TIME", "ENTRY PRICE",
    "ENTRY REASON", "ENTRY DETAILED REASON",
    "OPTION TYPE", "STRIKE", "PORTFOLIO NAME", "STRATEGY", "SLOT_ID",
    "EXIT TIME", "AVG EXIT PRICE",
    …
]
Net effect — the same conceptual key (display_name) is now suffixed with slot_id at exactly the report-generation boundary. The Nautilus engine, the merged CSVs, and the SPA tearsheet UI all see the unchanged display_name; only the order book CSV and HTML report adopt the longer unique label. Surface area: two functions across two files. Backward-compatible for single-strategy runs (empty SLOT_ID column).

8. How to verify after re-running

Restart the server and rerun the portfolio:

# then in the browser: Portfolio page → FX_9_Slot_2024 → Run

Then inspect the newly written files in reports/_default/:

  1. Order book CSV: open order_book_portfolio_FX_9_Slot_2024_<date>.csv and confirm
    • 9 distinct values in PORTFOLIO NAME
    • 9 distinct values in STRATEGY
    • 9 distinct values in the new SLOT_ID column (e.g. fx_eur_ema, fx_gbp_ema, …)
    • Total row count matches the sum of per-slot round-trips (not the previously truncated 113).
  2. HTML report: open portfolio_FX_9_Slot_2024_<date>_report.html and confirm
    • Header reads | <N> trades | 9 Portfolios |
    • Portfolio Filter dropdown lists 9 entries
    • Strategy Breakdown table shows 9 rows
  3. Regression baseline: compare row count and unique trader_id count of position_report_*.csv and order_fill_report_*.csv against the 16:39 run — should be unchanged.
  4. Single-strategy sanity: run any single-strategy backtest. Its order_book_*.csv should still generate, with the SLOT_ID column present but empty — slot_id is a portfolio-only concept.

9. Out of scope

  • The mis-named slots in FX_9_Slot_2024.json — fx_eur_* / fx_jpy_* all currently point at GBPUSD. This is a data fix for the user to decide separately; the report fix is independent of it.
  • Changing display_name semantics — would cascade into the SPA tearsheet and portfolio tabs. Kept the surface narrow.
  • Engine-level StrategyId / trader_id generation — already correct; nothing to change there.
  • docs/report_template.html rendering logic — it adapts to whatever STRATEGY values appear, no template changes required.
