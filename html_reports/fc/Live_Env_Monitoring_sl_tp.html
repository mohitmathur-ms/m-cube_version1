Who Monitors SL/TP Prices in a Live Trading Environment?

m-cube · NautilusTrader 1.224.0 · generated 2026-05-27 · question: the venue or our Python code?

Short answer. In NautilusTrader the answer is decided by one field on the order — emulation_trigger. With a native order_factory.bracket() (default NO_TRIGGER), the SL (STOP_MARKET) and TP (LIMIT) orders rest on the real venue/exchange and the venue's matching engine triggers them — your Python code is not in the loop. Only when emulation is enabled (DEFAULT/BID_ASK/LAST_PRICE) does Nautilus's local OrderEmulator watch price in Python and release a market order on trigger. m-cube's current default does neither — it monitors SL/TP itself in on_bar and fires a market close, which is conceptually the same as the emulated path but hand-rolled, and the one Nautilus treats as the least-preferred fallback.

venue-managed (Nautilus default, live) ■ Python-monitored (emulator / m-cube) ■ engine / backtest simulator

  • Venue path (NO_TRIGGER): the SL/TP orders physically rest on the exchange. The venue observes price and triggers — survives a crash/disconnect of your client, lowest latency. This is what order_factory.bracket() does by default.
  • Emulated path: the order is held in Nautilus's local OrderEmulator (MatchingCore), invisible to the venue. Nautilus Python watches the data feed and, on trigger, transforms the STOP_MARKET into a plain MARKET order and releases it. Exists as a portability layer for venues lacking a given order type.
  • Backtest path: the SimulatedExchange matching engine inside BacktestEngine plays the venue — this is where m-cube actually runs today.
  • m-cube default: no resting order at all — SL/TP are floats checked every on_bar; on breach it submits a market close. Same model as the emulator, but hand-rolled at the strategy layer.

2 · The core concept — emulation_trigger routes everything

At submit time the strategy routes the order on a single field (trading/strategy.pyx:891-897):

if order.emulation_trigger != TriggerType.NO_TRIGGER:
    self._manager.send_emulator_command(command)   # → OrderEmulator (LOCAL Python)
else:
    self._manager.send_risk_command(command)        # → RiskEngine → ExecEngine → VENUE

The bracket() factory defaults to emulation_trigger=NO_TRIGGER, whose docstring states plainly: "Disables local emulation; orders are sent directly to the venue." (common/factories.pyx:1259-1263). So the SL/TP of a default native bracket live on the exchange, and the exchange monitors them.

5 · Bottom line

If m-cube always used order_factory.bracket():

  • In backtest (where m-cube lives today): the SimulatedExchange matching engine monitors and fires SL/TP — more realistic fills than the current "close at bar close" Python model. This is exactly why the native-bracket experiment exists.
  • In live trading (with a future L4 execution layer): under the default NO_TRIGGER, the real venue monitors SL/TP — orders rest on the exchange, trigger tick-by-tick, and survive a crash of the Python process. This is the Nautilus-recommended convention.
  • m-cube's current default Python state machine is the opposite model: your code observes the SL hit and reacts. Nautilus treats this as the fallback (what OrderEmulator automates), acceptable mainly because m-cube needs it for the dynamic exits a static resting bracket cannot express.
