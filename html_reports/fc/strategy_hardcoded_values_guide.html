Strategy Hardcoded Values Guide

Every truly hardcoded value in strategies/ — the literals baked into the trading logic that no UI field or portfolio JSON can override — and exactly how each one touches your backtest.

Scope: strategies/bollinger_bands.py · ema_cross.py · four_ma.py · rsi_mean_reversion.py · range_breakout.py · _shared/time_windows. Line numbers verified against the current source.

What this document shows. It answers one question: "When I run a backtest, is there a value baked into the strategy code that I can't see or change, and could it harm my results?"
  1. A precise definition of "truly hardcoded" vs. an overridable config default — so you know which values this report covers and which it deliberately ignores.
  2. A summary table of every true hardcoded value across all five strategies.
  3. One detailed section per value: the exact syntax, a plain-English description, a technical description, and a clear note on its impact on your backtest.

0. What counts as "truly hardcoded"?

Most numbers you see in a strategy file (RSI period 14, Bollinger 20/2.0, the Range-Breakout 09:30 start time) are just starting suggestions. The moment you run a backtest, the values from the screen are pasted over them, so they are not hardcoded — you control them. A truly hardcoded value is different: it's written straight into the trading logic, there is no box for it on the screen, and it is used on every single run no matter what you type.
Technically: the runner builds each strategy's config with config_class(**config_kwargs) in core/backtest_runner.py, unpacking the UI/portfolio params over the dataclass. A field only falls back to its declared default when the request omits that key — and the UI form never omits a key it renders. So any field that appears in a strategy's PARAMS dict (and trade_size, which the runner always computes from lots × lot_size) is overridable and out of scope here. A value is "truly hardcoded" only if it is a literal inside a method body or a module-level constant with no corresponding PARAMS entry. Those are what follows.
Explicitly out of scope (these are NOT hardcoded — you can change them). Indicator params (bb_period, bb_std, rsi_period, overbought, oversold, EMA/MA periods); all Range-Breakout config fields including the equity-style session defaults range_start_hhmm=930 / squareoff_hhmm=1515 and timezone_offset_min=0; and trade_size. They have UI fields (or are runner-computed) and are overridden on every real run. Caveat: the RBO session-time defaults are equity-oriented — harmless once you set them, but worth knowing if you ever drive the strategy programmatically and forget to pass them.

2. Order time-in-force = TimeInForce.GTC

strategies/bollinger_bands.py · ema_cross.py · four_ma.py · rsi_mean_reversion.py · range_breakout.py (order-submission helpers)
# bollinger_bands.py:88-98  (every strategy's _submit_order/_submit_market is identical in spirit)
def _submit_order(self, side: OrderSide, reason: str | None = None) -> None:
    kwargs = dict(
        instrument_id=self.config.instrument_id,
        order_side=side,
        quantity=self.instrument.make_qty(self.config.trade_size),
        time_in_force=TimeInForce.GTC,          # <-- hardcoded, no config field
    )
    ...
    order = self.order_factory.market(**kwargs)
    self.submit_order(order)
Every order the strategy sends is marked "keep this order working until it either fills or I cancel it." There is no setting anywhere to change this to, say, "cancel it instantly if it can't fill right now."
Technically: time_in_force=TimeInForce.GTC (Good-Till-Cancelled) is passed as a literal in every order builder — bollinger_bands.py:93, ema_cross.py:109, four_ma.py:101, rsi_mean_reversion.py:95, range_breakout.py:454. No PARAMS entry exposes it, so it is fixed for the lifetime of the codebase unless edited. The alternatives Nautilus offers (IOC, FOK, GTD, DAY) are never reachable from a config.

Impact on your backtest

Low. Because every order is also a market order (see §3), it is matched on the very next tick/bar regardless of time-in-force, so GTC vs. IOC produces the same fill in practice. The value matters only if the code were ever changed to emit limit orders — then GTC would let a resting limit order survive across bars instead of expiring. Worth knowing, not worth worrying about for the current market-order strategies.

3. Order type = order_factory.market(...)

strategies/*.py — every entry and every exit
# ema_cross.py:105-112
order = self.order_factory.market(            # <-- always a MARKET order
    instrument_id=self.config.instrument_id,
    order_side=side,
    quantity=self.instrument.make_qty(self.config.trade_size),
    time_in_force=TimeInForce.GTC,
    tags=[reason],
)
self.submit_order(order)

# range_breakout.py:484-485  (exits, including stop/target and squareoff)
opposite = OrderSide.SELL if side == OrderSide.BUY else OrderSide.BUY
self._submit_market(opposite, self._leg_qty[idx])
The strategy only ever knows how to do one thing when it wants in or out of a trade: "buy/sell right now at whatever the going price is." It never places a resting order to buy at a specific better price.
Technically: all submissions go through self.order_factory.market(...); there is no limit(), stop_market(), or bracket-order path anywhere in strategies/. Exits from the Range-Breakout target/stop logic are also market orders — the strategy decides intrabar that a target or stop level was touched, then fires a market order to flatten, rather than resting a protective stop/limit with the venue.

Impact on your backtest

Moderate and structural. Two consequences worth internalising:

  • Fills follow the engine's market-fill model. Your slippage/fill realism comes entirely from NautilusTrader's fill model + the venue config, not from the strategy. You cannot test "enter only if price pulls back to X" — there is no limit entry.
  • Range-Breakout target/stop are modeled, then market-filled. The strategy detects the touch using bar high/low and the modeled entry price (§5), then sends a market order. Realised P&L is the engine's actual market fill, which can differ from the exact target/stop price the strategy "saw." This is by design (the file's docstring calls it the "modeling entry"), but it means RBO P&L is not a clean fill at the printed target/stop level.

4. MAX_LEGS = 10

strategies/range_breakout.py:83 (constant) · :152-153 (clamp)
MAX_LEGS = 10                          # range_breakout.py:83 — module-level cap

# range_breakout.py:149-154 — num_legs is silently clamped into [1, MAX_LEGS]
n = int(config.num_legs)
if n < 1:
    n = 1
if n > MAX_LEGS:
    n = MAX_LEGS                       # <-- request for 11+ legs is silently reduced to 10
The Range-Breakout strategy supports at most 10 pyramid legs. If you ask for more, it quietly gives you 10 and doesn't warn you. Asking for zero or a negative number quietly becomes 1.
Technically: MAX_LEGS is a module constant used both to clamp num_legs in __init__ (range_breakout.py:152-153) and to bound the auto-generated legN_lots / legN_range_end_hhmm params in the PARAMS loop (range_breakout.py:545-554). The UI's num_legs field also advertises "max": MAX_LEGS, so a UI user is fenced in before the clamp ever fires — the clamp is a defensive backstop for programmatic callers.

Impact on your backtest

Low. The only way this surprises you is a non-UI call (script/API) requesting more than 10 legs: legs 11+ are dropped with no error, so the backtest runs a smaller pyramid than you intended. Within the UI you cannot exceed the cap, so results are never silently truncated there.

5. Range-Breakout modeling entry-fill clamp

strategies/range_breakout.py:403-412 (inside _process_side entry pass)
# Long side (range_breakout.py:403-407)
trig_src = bar_close if minute_close else bar_high
if trig_src < up_trig:
    continue
entry_fill = up_trig if bar_open < up_trig else bar_open   # <-- max(up_trig, bar_open)

# Short side (range_breakout.py:408-412)
trig_src = bar_close if minute_close else bar_low
if trig_src > dn_trig:
    continue
entry_fill = dn_trig if bar_open > dn_trig else bar_open   # <-- min(dn_trig, bar_open)
When a breakout triggers, the strategy assumes you got in at the breakout level — unless the bar already opened past that level (a gap), in which case it assumes you got in at the open. It never assumes a fill better than the breakout line. This assumed price is then used to compute where the target and stop sit.
Technically: the modeling entry is max(upper_trigger, bar.open) for longs and min(lower_trigger, bar.open) for shorts — a hardcoded clamp with no config knob. It feeds leg.entry_price (range_breakout.py:474), which is the basis for _target_price / _stop_price under target_stop_basis = 0 (percent of entry) and the reference for the range-size deltas under basis = 1. Note this is a modeling price for the strategy's own target/stop arithmetic; the engine still computes realised P&L from its independent market-order fill.

Impact on your backtest

Moderate, and easy to misread. The conservative clamp means the strategy never credits itself an optimistic sub-trigger entry, but on gap-through bars it books the (worse) open price as the entry — which shifts where the modeled target/stop levels land and therefore which subsequent bars count as target/stop hits. If your RBO tearsheet shows exits that don't line up with the "clean" trigger ± target%, this clamp (combined with §3's market exit) is why. It is intended behaviour, documented in the file's module docstring, but it is not adjustable.

6. Range-Breakout degenerate-range sentinels (±inf)

strategies/range_breakout.py:331-341 (inside _finalize_leg_triggers)
if self._basis == 1:
    rng = rh - rl
    if rng <= 0.0:
        # Degenerate range: block entries on this leg for the day.
        self._leg_upper_trigger[i] = float("inf")     # <-- range_breakout.py:335
        self._leg_lower_trigger[i] = float("-inf")    # <-- range_breakout.py:336
    else:
        self._leg_upper_trigger[i] = up_trig
        self._leg_lower_trigger[i] = dn_trig
    self._leg_tgt_delta[i]  = rng * (self._tgt_pct  / 100.0)
    self._leg_stop_delta[i] = rng * (self._stop_pct / 100.0)
When the strategy uses "range size" to size its target and stop, but the recorded range has zero width (the high and low of the range window were identical), it deliberately makes that leg impossible to trigger for the rest of the day — because a zero-width range would otherwise produce a zero-distance target and stop, and every trade would instantly round-trip.
Technically: under target_stop_basis = 1 (range size), a zero or negative range (range_high == range_low) sets the upper trigger to +inf and the lower to -inf. Since the entry pass requires bar_high ≥ up_trig (long) or bar_low ≤ dn_trig (short), no real price can ever satisfy ≥ +inf / ≤ -inf, so the leg never enters that day. This guard only applies on basis = 1; under basis = 0 (percent of entry price) a flat range does not disable the leg.

Impact on your backtest

Low but silent. On instruments/timeframes where a range window can be perfectly flat (illiquid sessions, tiny tick movement, or a too-short range window), affected legs simply produce no trades that day with no log message. If an RBO backtest shows fewer trades than expected on quiet days, this sentinel is a likely cause. It is correct behaviour (it prevents a degenerate zero-distance round-trip), just invisible.

7. Range-Breakout percent→fraction / 100.0

strategies/range_breakout.py:328, 340-341, 429, 442
buf = self._buf_pct / 100.0                       # :328  breakout buffer (percent mode)
up_trig = rh * (1.0 + buf); dn_trig = rl * (1.0 - buf)

self._leg_tgt_delta[i]  = rng * (self._tgt_pct  / 100.0)   # :340  target delta (basis=range)
self._leg_stop_delta[i] = rng * (self._stop_pct / 100.0)   # :341  stop delta   (basis=range)

# _target_price / _stop_price under basis=0 (percent of entry price)
delta = entry * (self._tgt_pct  / 100.0)         # :429
delta = entry * (self._stop_pct / 100.0)         # :442
The breakout-buffer, target, and stop boxes are read as percentages. Typing "10" into the target box means 10%, not 10×. The "divide by 100" that turns "10" into "0.10" is fixed in the code — you can change the number you type, but not the fact that it's treated as a percent.
Technically: the / 100.0 divisor is the hardcoded contract between the UI's percent-labelled fields (breakout_buffer_pct, target_pct, stop_pct) and the strategy's internal fractional math. The inputs are configurable; the unit interpretation is not. Note the buffer has a separate non-percent path — breakout_buffer_mode = 1 switches to absolute points (breakout_buffer_pts) and bypasses the / 100.0 entirely (range_breakout.py:324-330).

Impact on your backtest

None if you remember the fields are percentages; potentially large if you assume fractions. Entering 0.1 expecting "10%" actually yields 0.1% — a target/stop 100× tighter than intended, which would make trades round-trip almost immediately. This is a units gotcha rather than a bug: the divisor is correct, but it fixes the meaning of every value you type into those three boxes.

8. Time-helper constants (1e9, HHMM math)

strategies/_shared/time_windows/__init__.py:18-37
def hhmm_to_min(hhmm: int) -> int:
    return (hhmm // 100) * 60 + (hhmm % 100)          # :24  930 -> 570, 1515 -> 915

def bar_to_local(ts_event_ns: int, tz_offset_min: int) -> tuple[int, date]:
    local_dt = datetime.fromtimestamp(ts_event_ns / 1e9, tz=timezone.utc) + timedelta(
        minutes=tz_offset_min
    )                                                  # :34  ns -> seconds via 1e9
    return local_dt.hour * 60 + local_dt.minute, local_dt.date()
These are the plumbing constants the Range-Breakout clock uses: how to turn a time like "1515" into "minutes since midnight," and how to turn the bar's nanosecond timestamp into a normal time. They are unit conversions, not trading choices.
Technically: hhmm_to_min bakes in the integer-HHMM encoding (// 100 for hours, % 100 for minutes) used by all the RBO time fields; it does no validation and assumes the caller passes UI-bounded values in 0..2359. bar_to_local bakes in the ts_event_ns / 1e9 nanosecond→second divisor and uses UTC + a tz_offset_min shift (the offset itself is your configurable timezone_offset_min). These constants are physical-unit facts, not tunables.

Impact on your backtest

Negligible for normal use — the constants are simply correct. The only practical caveat: because hhmm_to_min assumes valid integer-HHMM input and skips validation, a malformed time fed through a non-UI path (e.g. 970, which isn't a real clock time) would be misinterpreted rather than rejected. Within the UI's 0..2359 bounds this never happens.

Bottom line. Your signal parameters are safe — every indicator setting and Range-Breakout session field is overridden from the UI on each run, so nothing about your chosen strategy logic is silently hardcoded. The genuinely fixed-in-code values are narrow and mostly benign: every order is a GTC market order (so fills follow the engine's market model, never a limit), Range-Breakout caps at 10 legs, models entries with a max(trigger, open) clamp, disables zero-width-range legs via ±inf sentinels, and reads buffer/target/stop as percent. None of these will corrupt a correctly-configured backtest — but the RBO entry-fill clamp (§5) and the percent units (§7) are the two that most often explain "why don't my exits land exactly on the target/stop price?"
