Internal Aggregation Migration Plan

Stop persisting higher-timeframe bars to the catalog. Have NautilusTrader's TimeBarAggregator build them on the fly from 1-MINUTE base bars at backtest time.

1. Why this change

Today the catalog stores one parquet directory per timeframe per side per instrument — e.g. EURUSD.FOREX_MS-5-MINUTE-BID-EXTERNAL, EURUSD.FOREX_MS-15-MINUTE-BID-EXTERNAL, and so on for 30-MINUTE, 1-HOUR, 2-HOUR, 1-DAY, 1-WEEK, 1-MONTH, on both ASK and BID sides (and MID when present). All produced by a manual offline batch.

This has three concrete problems:

  • Stale by default. Whenever new 1-minute data is ingested, every derived timeframe needs a manual re-aggregation pass or backtests run on out-of-date bars.
  • Disk + I/O cost. Eight extra timeframe directories per (instrument, side) tuple. Roughly 8× the parquet bytes per instrument, all derivable from the 1-MIN source.
  • Mismatch risk. Custom-aggregated math can drift from Nautilus's live TimeBarAggregator. The notebooks ipynb/aggregate_1min_to_5min.ipynb and ipynb/aggregator_strategy_demo.ipynb already prove parity at the math level, but every divergence between the offline pandas math and Nautilus's internal aggregator is a latent bug waiting to surface.
Outcome: the catalog stores only 1-MINUTE-{ASK,BID,MID}-EXTERNAL bars and instrument definitions. Every higher TF is computed on demand by Nautilus's own DataEngine via an INTERNAL@1-MINUTE-EXTERNAL composite subscription. Strategies do not change; portfolio JSONs do not change; the user-facing UI does not change.

2. How aggregation works today

Who writes aggregated bars?

Exactly one script: scripts/aggregate_catalog.py. It is a pure CLI — if __name__ == "__main__": main() at line 294, an argparse interface at line 176. Nothing else in the running app invokes it.

Verified by grep across the codebase:

  • The only references to aggregate_one and aggregate_catalog are inside the script itself and inside docs (README_APP.md, core/aggregator.py docstring).
  • Neither server.py, start.bat, nor any Flask endpoint references it. No scheduled task or hook calls it.
  • It is run manually, by hand, after a 1-MIN ingest pass — the operator triggers it.

What does the call chain look like?

scripts/aggregate_catalog.py::aggregate_one()
  → load_catalog(...).bars(bar_types=[<1-MIN-side>])    # read 1-MIN
  → core/aggregator.py::aggregate_with_features(...)     # pandas resample
  → core/nautilus_loader.py::wrangle_bars(...)
  → core/nautilus_loader.py::save_to_catalog(bars, ...)
        → ParquetDataCatalog(catalog_path).write_data(bars)  # the actual write

save_to_catalog is the only place in the project that ever calls catalog.write_data(...) for bar data. Every other code path either reads from the catalog or delegates to save_to_catalog.

How are the aggregated bars consumed?

  1. User picks a slot with bar_type_str = "EURUSD.FOREX_MS-5-MINUTE-BID-EXTERNAL" in the Multileg UI.
  2. core/backtest_runner.py reads that exact bar type from the catalog via catalog.bars(bar_types=[bt_str]).
  3. The bars are pushed to the engine via engine.add_data(all_bars).
  4. The strategy subscribes to the same 5-MINUTE-BID-EXTERNAL bar type and receives bars directly — no composition involved.
The codebase is already half-prepared for this migration. strategies/ema_cross.py:56-58 compares bar.bar_type.standard() against config.bar_type.standard() precisely so that an INTERNAL@1-MIN-EXTERNAL subscription still matches a 5-MINUTE-EXTERNAL config. Every strategy file uses the same register_indicator_for_bars + subscribe_bars(self.config.bar_type) idiom, so the switch is purely a runner-side concern.

3. Target architecture

The slot's stored bar_type_str stays in EXTERNAL form — portfolios on disk do not migrate. The runner translates internally:

load from catalog (today): EURUSD.FOREX_MS-5-MINUTE-BID-EXTERNAL
load from catalog (new): EURUSD.FOREX_MS-1-MINUTE-BID-EXTERNAL
 
strategy subscribes to (today): EURUSD.FOREX_MS-5-MINUTE-BID-EXTERNAL
strategy subscribes to (new): EURUSD.FOREX_MS-5-MINUTE-BID-INTERNAL@1-MINUTE-EXTERNAL

Nautilus's DataEngine sees the INTERNAL@... subscription, attaches a TimeBarAggregator against the 1-MIN data stream, and emits 5-MIN bars to the strategy as if they had been loaded directly. The strategy's bar.bar_type.standard() guard makes the match-up transparent.

1-MIN slots stay unchanged (no composite needed).

4. Phase A — Add transform helper

One new function in core/nautilus_loader.py next to make_bar_type_str:

def to_internal_composite(bar_type_str: str) -> tuple[str, str] | None:
    """If bar_type_str is a non-1-MINUTE EXTERNAL bar, return:
        (1-MIN-EXTERNAL data bar type,
         INTERNAL@1-MIN-EXTERNAL composite spec)
    Returns None for 1-MINUTE inputs (no composite needed)."""

Behavior: parse <instrument_id>-<timeframe>-<price_type>-EXTERNAL; emit

  • <instrument_id>-1-MINUTE-<price_type>-EXTERNAL — bar type to load from catalog
  • <instrument_id>-<timeframe>-<price_type>-INTERNAL@1-MINUTE-EXTERNAL — what strategies subscribe to

No behavior change yet — this helper is the single source of truth used by Phase B.

5. Phase B — Rewire engine build sites

Four near-symmetric engine setup functions in core/backtest_runner.py each do the same three steps today: load slot.bar_type_str bars → engine.add_data → build strategy config with that same bar_type. All four need the same edit.

FunctionPathApprox line
_run_single_slotPath A, per-slot2480 (bars load), 2590 (add_data)
_run_slot_groupPath A, grouped3234 (bars load), 3323 (add_data)
_run_single_slot_nodePath B, per-slot2251–2306
_run_slot_group_nodePath B, grouped2966–3009
run_backtesttop-level (non-portfolio)2009–2093

In each site

  1. Replace bar_type_strs_to_load = [slot.bar_type_str] with the 1-MIN form via to_internal_composite. The _pair_bid_ask_bar_type(...) call still applies but now operates on the 1-MIN string (pairing 1-MIN-BID with 1-MIN-ASK so FX matching has both quotes).
  2. The catalog read (_cached_catalog_bars / catalog.bars(...)) is now always against 1-MIN parquet. Bonus efficiency: different slots on different TFs of the same instrument share one 1-MIN cache entry.
  3. When constructing the strategy config, swap the bar_type argument from BarType.from_str(slot.bar_type_str) to the composite form returned by the helper. For 1-MIN slots, leave it alone.
  4. extra_bar_types on any strategy gets the same transform if any entry is non-1-MIN.
No strategy file is edited. Every strategy reads its bar type from self.config.bar_type and uses the standard register_indicator_for_bars / subscribe_bars pattern that handles composite specs transparently.

6. Phase C — Two semantic landmines

C1. run_on_days weekday filter

Today this filter is applied to all_bars before engine.add_data. After Phase B, all_bars is the 1-MIN list. Dropping Mondays at 1-MIN level cleanly drops Mondays at every higher TF too — weekday is constant inside a 5-MIN window in all non-boundary cases. The FX week boundary at Sun 21:00 UTC produces the same effect either way.

Verdict: safe to keep this filter at the 1-MIN level.

C2. entry_window intraday filter (entry_start_time / entry_end_time)

Today this drops bars by HH:MM-of-day from all_bars. Applied at 1-MIN level, a 5-MIN window whose boundary minute falls inside the rejected slice would be built from incomplete 1-MIN data — semantically different from current behavior.

Recommendation

Move the entry-window check into the strategy / ManagedExitStrategy.on_bar path. All 1-MIN bars flow into the engine; the aggregator builds clean higher-TF bars; the strategy ignores signal logic for bars whose ts_event falls outside the window. The result-dict tag bars_filtered_by_entry_window changes meaning (becomes "signals skipped") but keep the key for tearsheet compatibility.

C3. Path-B fallback rule

CLAUDE.md notes Path B auto-falls-back to Path A when run_on_days / entry_window are active, because filters cannot be injected into BacktestDataConfig. After C1+C2, the filter happens outside BacktestDataConfig — on the bar list for run_on_days and inside the strategy for entry_window.

Side-benefit: Path B no longer needs the auto-fallback for these filters — a meaningful coverage win for Path B. Land as a follow-up commit, not buried inside this migration.

7. Phase D — Update catalog-listing endpoints

The Multileg UI populates the bar-type dropdown from the catalog. After Phase E (cleanup), the catalog only contains 1-MIN parquets — so the dropdown would lose its 5-MIN / 15-MIN / etc. entries.

Change in server.py: wherever the catalog-status / bar-types endpoint enumerates available bar types (search for the fast-path _bar_type_range_from_files and the public listing endpoint), synthesize the standard derived TFs — 5-MINUTE, 15-MINUTE, 30-MINUTE, 1-HOUR, 2-HOUR, 1-DAY, 1-WEEK, 1-MONTH — for every (instrument, side) that has a 1-MIN parquet directory. The (start, end) range reported is the 1-MIN range. Slightly conservative at the very edges, acceptable.

Out of caution, also keep listing any already-existing aggregated parquet directories so a half-migrated catalog still works during transition.

8. Phase E — Stop persisting aggregates, clean up

  1. DELETE scripts/aggregate_catalog.py. Nothing calls it after Phase B. Update doc references in README_APP.md:116, README_APP.md:171, and CLAUDE.md.
  2. KEEP core/aggregator.py — the pandas-based math library still produces the features sidecar (RSI, ATR, EMA, VWAP, …) at catalog/features/bar/<bartype>.parquet.

    Decision needed:

    • Option E1: drop the features sidecar entirely (verify nothing reads catalog/features/bar/ via grep; if so, delete the directory and the feature-writing branch). Simplest.
    • Option E2: split the sidecar emit into a small CLI (scripts/write_features_sidecar.py) that imports aggregator.py but does not call save_to_catalog. Run on demand.
  3. ADD scripts/purge_aggregated_bars.py — one-time cleanup. Walks catalog/data/bar/ and lists any directory whose bar-type name contains a non-1-MINUTE timeframe in the EXTERNAL form. Dry-run by default; requires --apply to actually delete.
    Without this purge, the runner could still find a 5-MIN parquet and load it. Phase B's transform is therefore unconditional — it must not be gated by "is the higher-TF parquet missing." The purge ensures the catalog stays in the new shape.
  4. EDIT core/nautilus_loader.py — save_to_catalog refuses to write any bar whose bar_type contains a non-1-MIN EXTERNAL timeframe. Locks the invariant in place going forward.

9. Phase F — Verification

  1. Bit-equivalence already proven at the math level. core/aggregator.py:7 docstring and ipynb/aggregate_1min_to_5min.ipynb show pandas-resample and Nautilus's TimeBarAggregator emit bit-identical OHLCV.
  2. Strategy-level parity demonstrated in ipynb/aggregator_strategy_demo.ipynb: the same EMA-cross + bracket strategy run twice on January-2024 EUR/USD — once with Nautilus's internal aggregation, once with a manual FiveMinAggregator — produces near-identical trade counts (78 vs 80 fills, 39 vs 40 positions). The small delta is the boundary-window the on-the-fly aggregator legitimately can't emit until the next minute arrives.
  3. ADD scripts/verify_internal_aggregation_parity.py: pick a portfolio JSON with a 5-MIN slot, run it under HEAD (aggregated parquets in catalog) → record trade list + final P&L. Run the same portfolio under the new code path → compare. Tolerance: positions / fills exact; P&L to 2 decimals.
  4. Tweak existing parity harnesses — scripts/verify_grouping_parity.py, verify_aggregation.py, verify_catalog_vs_1min.py — to compare INTERNAL-aggregated bars vs catalog-stored 1-MIN re-aggregated by pandas, instead of catalog-aggregated vs 1-MIN.
  5. Run verify_session_changes.py — must stay green.

11. Open questions before implementing

  1. Features sidecar. Is anything reading catalog/features/bar/<bartype>.parquet today? If no → drop it (Option E1). If yes → split into a dedicated CLI (Option E2).
  2. Entry-window semantics. OK to move the entry_start_time / entry_end_time check from data-load to strategy-level (signal-skip rather than bar-drop)? Numerical result is identical for any reasonable case; the operational semantics shift.
  3. Migration cutover — feature flag? Recommend _USE_INTERNAL_AGGREGATION=1 behind the same pattern as _USE_GROUPING / _USE_BACKTEST_NODE. Land Phase B behind the gate, validate parity portfolio-by-portfolio, flip the default later. Keeps blast radius tight.
  4. Grouping key. Should slots that differ only in TF (e.g. 5-MIN + 15-MIN of the same EURUSD-BID) share one engine, now that both consume the same 1-MIN data? Big efficiency win, real behavior change. Recommend not now — keep the grouping key at the user-facing TF for this migration; revisit as a follow-up.
