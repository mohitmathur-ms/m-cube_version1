Containerizing m-cube for Scale

How NautilusTrader runs in a dockerized setting, how many users run backtests across containers, and what the end-to-end data flow looks like.

Research & design report · prepared for the merger_path_A_B branch · Nautilus findings from the ntm3 concept docs (nautilus_trader==1.224.0), m-cube findings from the codebase. No application code was changed — the Dockerfile/compose/queue shim below are recommendations.

0 · Executive summary

The thesis in one paragraph. Backtests on NautilusTrader are embarrassingly parallel: every BacktestEngine is a self-contained, in-process, ephemeral object — its Cache, MessageBus, Portfolio, matching engine and clock all live inside the engine and die with it. A backtest needs no database, no Redis, no message broker. That makes one backtest run a perfectly isolated unit of work — the ideal thing to hand to a container/worker. So containerizing m-cube is not a Nautilus problem; it is a web-app plumbing problem. The work is: (1) replace the Flask dev server with a production WSGI server, (2) move the CPU-bound backtest out of the HTTP request into a job queue + a pool of stateless backtest-worker containers, (3) externalize the little in-memory job state that exists today, and (4) put the shared catalog/ and the per-user portfolios/ / reports/ directories on shared volumes. The web tier is already nearly stateless (X-User-Id header, no sessions), so it replicates horizontally with no further work.

What is already container-ready
Stateless HTTP tier (header-based identity, no cookies/sessions) · isolated per-run Nautilus engines · append-only Parquet catalog · per-user data already namespaced by <user_id>.
What must change
Werkzeug dev server → gunicorn · in-request ProcessPoolExecutor → queue + worker pool · in-memory CSV-job dict → Redis · local disk → shared volumes.

1 · Why NautilusTrader is container-friendly

This is the single most important fact for the whole design, and it comes straight from the Nautilus concept docs.

1.1 — The engine is in-process and ephemeral

A BacktestEngine bundles the Cache, MessageBus, Portfolio, simulated exchange and clock as objects constructed inside it. The low-level lifecycle is just BacktestEngine() → add_venue / add_instrument / add_data / add_strategy → run() — no connection strings, no broker, no DB handle anywhere. When the data stream is exhausted the engine produces results and is discarded.

Source: Backtesting.txt — "A BacktestEngine processes a stream of historical data. When the stream is exhausted, the engine produces results…"

The high-level API (BacktestNode + a list of BacktestRunConfig) is explicit that "each run gets a fresh engine with clean state — no reset() needed." That is exactly the property you want for a worker: a job arrives, a clean engine is built, it runs, results are emitted, the process can exit. Nothing leaks between runs and nothing is shared out-of-band.

Source: Backtesting.txt — high-level API / "Each run gets a fresh engine with clean state."

1.2 — No Redis / no database required for backtests

Nautilus does have a Redis-backed Cache and an external-publishing MessageBus — but both are opt-in and aimed at live/multi-node deployments. The Cache is a "central in-memory database" whose DatabaseConfig defaults to None; the docs say a DB backend matters only for persistence across restarts, audit history, or multi-node shared state — none of which apply to an ephemeral backtest. The MessageBus's Redis backing is configured on a TradingNodeConfig (the live path) for external publishing between producer/consumer nodes.

Sources: Cache.txt — "central in-memory database", DatabaseConfig | None = None; MessageBus.txt — external publishing via Redis is configured on the live TradingNodeConfig.

Takeaway
Do not provision Redis for the Nautilus engine. We will add Redis to m-cube — but only as the application's job queue, never as a Nautilus dependency.

1.3 — Determinism (and the one cross-process caveat)

Given the same data + the same config in the same process, a backtest is deterministic — including a deterministic TradeId per fill. The probabilistic fill model's PRNG is pinned by random_seed. The caveat that matters for sharding work across containers: cross-process reruns are only "expected to match" and may differ in rare cases due to hash-ordering effects outside the fill model.

Source: Backtesting.txt — "Reproducible results: A fixed random_seed pins the … PRNG. Same-process reruns are expected to match; cross-process reruns may differ in rare cases…"

Design consequence
For audit / exact-repro of a specific run, pin random_seed and reproduce in a fresh process with the same image/environment. Treat results as near-identical across heterogeneous workers, not bitwise-identical. (Don't cite the Rust "DST" harness here — per DST_timezone.txt it explicitly excludes the Python backtest path.)

1.4 — Memory is boundable (matches m-cube's streaming flags)

For datasets that don't fit in memory the docs give two levers, both of which m-cube already mirrors: the streaming API (engine.add_data_iterator(...) for automatic chunking, or the manual add_data → run(streaming=True) → clear_data() loop), and bounded Cache capacities (bar_capacity / tick_capacity default 10,000, oldest evicted). These map onto m-cube's _USE_LAZY_STREAM / _USE_UNIFIED_STREAMING flags. The docs give no absolute memory figure — per-worker RAM must be profiled (_PROFILE_PHASES=1).

Source: Backtesting.txt — "Strategy 3: Use streaming API for very large datasets"; Cache.txt — capacities.

In-memory state audit
Most module-level caches (_CATALOG_CACHE, the session-window cache, the strategy registry built at import) are benign — they rebuild on demand, and each ProcessPoolExecutor worker already reloads the merged strategy registry. The only state that is genuinely lost on restart and invisible across replicas is the CSV-ingest job dict (and the session-PnL aggregator used by multi-portfolio session runs). Those are the two things that must move to Redis.

web service N replicas

  • gunicorn + the existing Flask app (server:app).
  • Serves the SPA + all CRUD (portfolios, catalog status, tags).
  • For a backtest: validates the user/allowlist, then enqueues a job instead of running it inline; returns a job_id.
  • Streams/polls status & results back from Redis.
  • Stateless ⇒ any replica serves any request; no session affinity.

worker service M replicas

  • Same image, different entrypoint: a loop that pulls jobs from Redis.
  • Reuses run_portfolio_backtest / _run_single_backtest_task unchanged.
  • Reads bars from catalog/ (RO, streaming), runs the engine, writes reports/<uid>/, updates job status.
  • CPU-bound ⇒ size by cores; scale M independently of N.
  • Crash-safe: an un-acked job can be requeued.

4 · Multi-user backtests across containers

"Multiple people run backtests" works because each backtest is an isolated unit and the web tier is stateless. Here is the lifecycle of one user's run in the containerized model:

  1. Request lands on any web replica. No session affinity needed — identity is the X-User-Id header, resolved per-request (server.py::_resolve_user_id). The proxy authenticates the human and injects/verifies the header.
  2. Validation stays on the web tier. The user's multiplier and allowed_instruments allow-list (core/users.py) and the portfolio allow-list check run before the job is enqueued — a bad request never reaches a worker.
  3. Job is enqueued with its user_id as part of the payload. The queue is shared, so any worker can pick up any user's job.
  4. A worker runs it in full isolation. A fresh Nautilus engine per run means User A's run cannot affect User B's — no shared engine, cache, or bus.
  5. Results land in the user's namespace. The worker writes to reports/<uid>/ (unique timestamped filenames) and reads/writes portfolios/<uid>/ — already isolated by user id.
  6. Any web replica reads back the status/result from Redis (or the shared reports volume).

Fairness & isolation

  • Per-user concurrency caps: enforce a max in-flight jobs per user_id at enqueue time (or use per-user queues) so one user's parameter sweep can't starve others. The existing multiplier field is a natural place to also encode a priority/quota.
  • No cross-user state: the only shared writable surfaces are the namespaced per-user dirs and the append-only catalog — so concurrent users don't collide.
  • Determinism note: because cross-process repro is only "expected to match" (§1.3), if two users run the identical config they should get the same answer in practice, but pin random_seed if exact equality is contractually required.
Security caveat (unchanged from today)
The X-User-Id header is spoofable — core/users.py is an identity-only layer with no auth. In a multi-container deployment exposed beyond a trusted LAN, put real authentication at the reverse proxy and have it set the header; never let clients send it directly.

Steps 3–5 are pure Nautilus and pure compute — no network, no DB. That is what makes the worker pool trivially scalable: add workers, drain the queue faster.

5.2 — CSV ingest (the write path)

 browser ──POST /api/csv/load──► web replica
   │                               │ classify entries: inline (fast) vs bulk (MID/ASK/BID)
   │                               │ enqueue bulk job ─► Redis   (today: in-memory _csv_jobs — to externalize)
   │ ◄──── { job_id } ─────────────┘
   │
   │                       Redis ──► ingest worker
   │                                   │ csv_loader → wrangle_bars → Nautilus Bar objects

   │                                   │ update_venue_session_window() ─► RMW adapter_admin/.json
   │                                   │ SET job status ─► Redis (survives restart)
   │ ◄── poll /api/csv/jobs/{id} ──────┘
Two writers, one catalog
The ingest path is the only writer to the shared catalog/. Parquet files are written append-only with non-overlapping start_iso_end_iso filenames (low collision risk), but the venue session-window update is an un-locked read-modify-write (core/venue_config.py). Run ingest through a single serialized worker/queue (or add a file lock) so two concurrent uploads can't clobber a venue config.

6.3 — The minimal code change (thin queue shim)

The point is to reuse the existing functions unchanged. The backtest endpoint enqueues instead of running inline; a worker consumes and calls the same run_portfolio_backtest that runs today.

# worker/run.py  (PROPOSED — not yet in repo)
import os, json, redis
from core.backtest_runner import run_portfolio_backtest   # unchanged public API

r = redis.from_url(os.environ["REDIS_URL"])

def main():
    while True:
        _, raw = r.brpop("mcube:jobs")          # block until a job arrives
        job = json.loads(raw)
        jid = job["job_id"]
        r.hset(f"mcube:job:{jid}", "status", "running")
        try:
            result = run_portfolio_backtest(    # SAME function the Flask request calls today
                portfolio_config=job["portfolio"],
                catalog_path=os.environ["CATALOG_PATH"],
                user_id=job["user_id"],
                # random_seed=job.get("seed"),  # pin for reproducibility
            )
            r.hset(f"mcube:job:{jid}", mapping={"status": "done",
                                                "result": json.dumps(result)})
        except Exception as e:                  # crash-safe: surface the error, optionally requeue
            r.hset(f"mcube:job:{jid}", mapping={"status": "error", "error": str(e)})

if __name__ == "__main__":
    main()

# server.py  (PROPOSED edit to the backtest endpoint — sketch)
# BEFORE: ran run_portfolio_backtest(...) inline inside the request (ProcessPoolExecutor)
# AFTER:
job = {"job_id": new_id(), "portfolio": cfg, "user_id": uid, "seed": seed}
redis_client.lpush("mcube:jobs", json.dumps(job))
return jsonify({"job_id": job["job_id"]}), 202
# a small GET /api/portfolios/jobs/ reads mcube:job: back
Why this is low-risk
The parity-tested execution paths (run_portfolio_backtest, _run_single_backtest_task, the unified/per-slot/Path-B machinery) are untouched — they still build the same engines and return the same result dicts. Only the caller moves from "inside the HTTP request" to "inside a worker loop." The same verify_grouping_parity.py / root *_parity_test.py scripts still validate correctness.

6.4 — Kubernetes mapping (brief)

Compose is the primary target; on K8s the shape is the same:

  • A Deployment per role (web, worker, ingest-worker) + a Redis StatefulSet (or managed Redis).
  • PVCs for shared data — catalog as ReadOnlyMany for runners, user-data/reports as ReadWriteMany (NFS/EFS/Filestore class).
  • HPA on the worker Deployment keyed on Redis queue depth (or CPU) → autoscale M to drain the backlog.
  • Ingress (or a gateway) terminates TLS, authenticates, and injects X-User-Id.
  • Set CPU requests/limits on workers to match the engine's profiled footprint.

8 · Phased rollout

Phase 0
Dockerize as-is. One image, gunicorn instead of the dev server, single container, local volumes. Goal: parity with today plus a production server. Run the existing pytest + verify_session_changes.py + parity scripts inside the container.
Phase 1
Externalize state & split workers. Add Redis; move CSV-ingest job state and a new backtest job queue into it; introduce the worker and ingest-worker roles (§6.3). Web tier now only enqueues.
Phase 2
Scale out. N web replicas behind a proxy/LB; M autoscaled workers (queue-depth HPA); shared RWX volumes for catalog/portfolios/reports/config. Add per-user concurrency caps.
Phase 3
(Future) Live trading path. Out of scope here — needs exchange adapters, the live reconciliation subsystem, and (typically) a Redis-backed Cache/MessageBus. Fundamentally a stateful service, scaled differently from the backtest pool.
