Manual Verification v2 — SL/Target Features & Order Types (MIS · Indian Market)

Indian-market framing: MIS trade type, NIFTY session 09:15–15:30 IST, hard square-off at the NSE close 15:29 IST (fires every session). Fire at the open · let the FEATURE decide the intraday exit · prove the time and price match the asset data — by hand, against the order book. Companion to portfolios/testing2/.

Principle. For every trade you re-derive the expected SL/Target level, the expected trigger second, and the expected fill from the order book's own logged fill + bar data + config — never from what the engine claims. The two must agree to the tick / to the second. Attach a screenshot for each.

0 · How this set works — three engine facts everything rests on

All verified against core/managed_strategy.py + core/backtest_runner/ for this build (nautilus_trader 1.224.0, default Path A, no LatencyModel):

FactWhat actually happensYour "expected" value
Entry fill priceThe EMA signal fires on a (composite) bar; the entry is a MARKET / GTC order (_submit_order). With no latency model it fills at that signal bar's CLOSE — not the next bar's open.signal-bar close
SL / Target exit fillWhen low ≤ SL (long) the engine does not fill at the SL level — it submits a reduce-only MARKET close (close_all_positions), which fills at the trigger bar's CLOSE.trigger-bar close (≠ the level)
MIS square-off timingFires on the first bar whose local (IST) time ≥ the cutoff minute, and runs before SL/TP (outer envelope). At 15:29 IST it fires on the closing-minute bar (15:29:00–15:29:59) every session — any open position is force-closed (reason squareoff), re-entry blocked until next session. (A literal 15:30:00 would be dormant — the data's last bar is 15:29:59.)square-off exit at 15:29 IST each day
Trigger ≠ fill. The SL/Target level decides when (the trigger bar); the realised fill is that bar's close. Always check both and expect them to differ. The optional vwap_exit_fill / directional_close_fill repricers are OFF in every testing2/ file, so this base behaviour is what you test.

1 · The 3-axis verification loop + worked example

Run the portfolio → export the order book (fills, exits, reasons, per-bar current_sl) → for every row run:

AxisThe check
A · TIMEFrom the logged bar data, find the first bar the trigger condition is true. The event's second must equal that bar — not earlier (look-ahead), not later (lag) — unless a Wait/Safety delay applies. If several levels fire the same bar, precedence is User → Portfolio → Leg.
B · LOGICThe reason matches the condition actually true (SL only if price reached SL). The correct action dispatched. Exactly one outcome where only one is valid (never both SL & Target same trade). Guards held (trail only-tightens, re-exec count capped).
C · PRICERecompute the level from entry_price + config, tick-snap to 0.01; the logged current_sl/current_tp must equal it. The fill must match the fill model (§0). PnL = (exit − entry) × multiplier × lots ties to leg_pnl.

Worked example (real data) — VP-01, long SL 0.5%

NIFTY spot, 2026-03-02, session opens 03:45:00 UTC (09:15 IST); the open second prints O 24741.00 / H 24747.80 / L 24645.10 / C 24722.00. Say the first bullish EMA cross of the session enters long, filling at the signal bar's close F = 24722.00:

expected_sl = round( F × (1 − 0.5/100) , tick 0.01 )
= round( 24722.00 × 0.995 , 0.01 ) = 24598.39
AxisWhat to confirm
TIMESL exit second = the first second-bar where low ≤ 24598.39. Nothing fired before it.
LOGICreason = SL; leg ACTIVE → CLOSED; no Target on this file.
PRICELogged current_sl == 24598.39 to the tick. Realised exit fill = the trigger bar's close (record it; it will sit at/just below 24598.39, not exactly on it). PnL = (fill − 24722.00) × 1 × 1.
The brief's "entered at 100 → SL at 95 (5%)" rule is exactly this, scaled: replace F=24722, 0.5% with your fill and pct. The point is you can compute the SL the moment you read the fill, then watch the chart for the bar that touches it.

2 · MIS trade type + 15:29 IST hard square-off (NSE close)

Every testing2/ portfolio is product="MIS" (intraday trade type) with a hard square-off at the NSE close, 15:29 IST (squareoff_time="15:29:00", squareoff_tz="Asia/Kolkata"). The NIFTY session is 09:15–15:30 IST (= 03:45–10:00 UTC). The intra-day entry window is left open (the session already bounds the data), so the feature can exit any time within the session — and the square-off is the daily outer envelope.

The square-off FIRES every session. Any position still open at 15:29 IST is force-closed (reason squareoff) on the first 15:29 bar, re-entry blocked until the next session. The check runs before SL/TP, so on a bar where both would trigger the square-off wins (outer envelope). A position the feature never exits is squared off daily at the close — not carried overnight.
Why 15:29 and not 15:30. The square-off fires when a bar's IST minute ≥ the cutoff minute. The NSE close is 15:30 IST, but this 1-second feed's last bar each day is 15:29:59 IST (minute 29) — a literal 15:30:00 cutoff (minute 30) would never be reached and would be dormant (the same reason the earlier 23:59 never fired). 15:29:00 lands on the closing-minute bars (15:29:00–15:29:59), firing at the session close as intended. Only a position opened on the final session and not yet at 15:29 is flattened by on_stop at the backtest data end (m-cube's own close; Nautilus does not auto-flatten).

This surfaces flaws — both the feature and the daily square-off are checkable:

  • A position that should have exited on its SL/Target intraday but didn't → the feature is broken (the square-off would still catch it at 15:29, but the feature exit is missing/late).
  • A square-off that fires at the wrong time or doesn't block re-entry → visible on VP-11 (which has no feature, so the only exits are the daily square-offs).
Changing the cutoff: edit squareoff_time / squareoff_tz in _generate_portfolios.py and re-run — e.g. 15:20:00 for an earlier intraday auto-square-off, or a post-session time to make it dormant. If you reload data whose last bar is exactly 15:30:00 IST, use 15:30:00 to match.

VP-03Multiple conditions — which one stopped the trade, and when? RUN

Why it matters (brief): "if testing for multiple conditions — which condition caused the feature stop and at what time." SL 0.3% sits below entry, Target 0.5% above. For each trade:

  1. Compute SL = F×0.997 and TGT = F×1.005 (tick 0.01).
  2. Scan bars after entry: note the first second low ≤ SL and the first second high ≥ TGT.
  3. The earlier one should be the exit. Same-bar collision: the engine checks SL before TP, so if one bar's range spans both levels the reason must be SL.
  4. Confirm never both fire on one trade, and the reason matches your earlier-touch finding.

VP-10Precedence — leg SL vs portfolio Combined Loss RUN

2 legs (EMA 9/21 + 5/13), each leg SL 0.5%, plus portfolio Combined Loss = 250. On a drawdown that trips both: the portfolio sqoff (reason PORTFOLIO_LOSS) should flatten both legs on the same bar, before the individual leg SLs would. Record, per exit row, which level caused it and the second. Pass: portfolio precedes leg; both legs close together.

VP-05 · VP-06 · VP-07Dynamic features — walk per-bar state

  • VP-05 Trailing SL: log current_sl every bar. It must only tighten (long: never decrease). Each ratchet lands on the bar profit crosses the next step (0.2), by the offset (0.1). A stale or loosening SL is a red.
  • VP-06 ATR SL: read the logged ATR-at-entry; SL = F − 2.0×ATR snapped. Warm-up trades (first ~14 bars, ATR not initialised) must arm no SL and carry — confirm they don't exit on a phantom level.
  • VP-07 SL Wait: on the first low ≤ SL the exit is held; it fires only at trigger + 3 bars. If a bar inside the wait prints low > SL the wait clears and there's no exit. Verify both the delayed-exit and the cleared path.

4 · Zero-value deep dive — "what if SL and TP are 0?"

The brief asks this explicitly. The answer depends on the type, and the two cases are split into VP-11 vs VP-12 so you can see the difference:

VP-12stop_loss_type="percentage", value=0

Flaw to flag: a value = 0 with a real type does not disable the feature — it places the level exactly on the entry price, forcing a near-instant exit. Arguably a 0 value should be treated as "off" (like type="none"). VP-12 is the probe that demonstrates this; capture the orderbook showing entry and exit on the same/adjacent second at ~0 PnL.

5 · Order types — live-market verification

Engine reality. core/managed_strategy.py submits only MARKET / GTC orders for entries and exits. Limit / Stop-Limit exits are not wired — they are blocked at save (server._validate_portfolio_sl → HTTP 400). "Good till triggered" is not even a Nautilus time-in-force. So the order-type tests are: one real fill-verification (market), two rejection tests, and three documented mappings.

Nautilus 1.224.0 order-type map (from the ntm3 docs)

Desk termNautilus type / paramIn this backtest
Market orderMarketOrder (no price/trigger)wired — fills at bar close (no latency)
Limit orderLimitOrder(price=…)blocked at save (live-only)
Stop-loss (market)StopMarketOrder(trigger_price=…)emulated by the SL feature → market close
Stop-loss (limit)StopLimitOrder(trigger_price, price)blocked at save (can miss on a gap)
Good-till-triggered (GTT)not a TIF — conditional trigger + GTCemulated by per-bar level monitoring
Good-till-cancelledTimeInForce.GTC (the default)default on every order

Time-in-force values that exist: GTC, IOC, FOK, GTD, DAY, AT_THE_OPEN, AT_THE_CLOSE. There is no GTT. "Good till cancelled" = GTC.

OT-01Market order — expected vs ACTUAL fill RUN

The brief's live test: "fire at market expecting price X — when/at what price did it actually execute?" Procedure:

  1. Find the EMA signal bar. Your expected entry price = that bar's close (record it / screenshot).
  2. Read the entry's OrderFilled.last_px and ts_event from the order book.
  3. Confirm last_px == signal-bar close and ts_event = that bar's timestamp. With no LatencyModel there is no delay; if you ever add latency, the fill moves to the next bar's close — note which regime you ran.
  4. Repeat for the SL exit (0.5%): expected fill = trigger-bar close.
If the actual fill differs from the signal-bar close, the culprits to check (in order): a configured LatencyModel, a non-default FillModel (slippage), or bar_adaptive_high_low_ordering changing intrabar sequencing. All are off/default in this build.

OT-02 · OT-03Limit & Stop-Limit — rejection tests MUST 400

Load each file and attempt to save it. Expected: HTTP 400 with "Exit Order Type '…' is not implemented in the backtest engine — only MARKET exits are supported (spec §8.1)." These are negative tests: the file is the fixture, the rejection is the pass. (Verified: OT-02 Limit and OT-03 SL_Limit are the only two of the 18 that fail save-validation.)

OT-04 · OT-05 · OT-06Stop-Market · GTT · GTC RUN

  • OT-04 Stop-loss (market): the SL feature is a stop-market — watch the level, fire a market close on touch. Same verification as VP-01 (trigger second = first low≤SL; fill = trigger-bar close).
  • OT-05 Good-till-triggered: SL 0.4% + Target 0.6% act as two resting triggers. The engine has no native conditional order; it emulates "rest until triggered" by monitoring each bar. Verify each fires on the first bar its level is touched, and not before.
  • OT-06 Good-till-cancelled: no SL/Target. Every order is GTC by default; the entry holds intraday until the opposite EMA signal flips ("cancels") it or the 15:29 IST MIS square-off force-closes it at the session close. Verify the order never expires on its own (no GTD/DAY expiry) — it ends only by signal-flip or the daily square-off.

6 · Screenshot checklist (per trade)

The brief asks for a screenshot at each step. Capture and file under the case ID:

  1. Entry shot: the chart at the signal bar with your computed SL/Target drawn on, + the orderbook entry row (last_px, ts_event).
  2. Trigger shot: the bar where low ≤ SL / high ≥ Target — show the wick touching your level + the bar's timestamp.
  3. Exit shot: the orderbook exit row (reason, current_sl, fill, leg_pnl).
  4. Dynamic features (VP-05/06/07/10): a shot of the per-bar current_sl column at each ratchet / the wait window / the portfolio sqoff bar.
